## Задача

У гномика G единиц золота, и каждый год банк оставляет себе p процентов
в качестве комиссии (1 ≤ p ≤ 99), так что золота становится
(100 − p)/100 от прежнего. Когда золота не больше L, жизнь гномика
теряет смысл. G и L — целые числа не больше 2³¹ − 1. Сколько лет
осталось?

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

G, L и p.

## Выходные данные

Число лет.

## Примеры

### Пример 1

Ввод:

```
19 10 50
```

Вывод:

```
1
```

### Пример 2

Ввод:

```
1000 1 1
```

Вывод:

```
688
```

## Решение

Через k лет золота ровно G · ((100 − p)/100)^k, и ответ — первое k, при
котором это не больше L. В целых числах проверка выглядит так:

```text
G · (100 − p)^k ≤ L · 100^k
```

поэтому каждый год обе части умножаются — на 100 − p и на 100, пока
левая не перестанет быть больше. Цикл выполняется не больше примерно
2140 раз, при G = 2³¹ − 1, L = 1 и p = 1, а числа вырастают до
нескольких тысяч цифр. `O(Y²)` операций над цифрами при Y годах.

Оценка числа итераций предполагает положительные G и L, а нижних границ
для них в условии нет: при G > 0 и L = 0 золото остаётся положительным
через любое конечное число лет, и конечного ответа нет.

Тонкие места:

- золото может попасть ровно на предел, и плавающая точка это
  пропускает: 300 · 0,81 получается 243,00000000000003, на год больше
  при L = 243 (тест 05), а ln(9801/10000) / ln(0,99) округляется вверх
  до трёх лет вместо двух (тест 06);
- если золота уже не больше L, ответ 0 (тесты 03, 04).

## Оптимизированные решения

Оптимизированное решение на Java хранит каждую сторону как массив цифр
по основанию 10⁹ и умножает его на месте, увеличивая массив только при
появлении новой цифры, вместо создания двух новых объектов `BigInteger`
каждый год; цифра, умноженная не более чем на 100, плюс перенос остаётся
меньше 10¹¹ и помещается в `long`. G, L и p читаются по цифрам прямо из
`System.in` в `int`, которого хватает, ведь они не больше 2³¹ − 1,
вместо создания `Scanner`: {1283_math_optimized.java}.
