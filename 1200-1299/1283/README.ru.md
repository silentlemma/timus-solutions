# 1283. Гномик

[Timus 1283](https://acm.timus.ru/problem.aspx?space=1&num=1283) · сложность 116 · math

Автор оригинальной задачи — Леонид Волков (подготовил Иван Дашкевич); личное первенство УрГУ 2004 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

У гномика G единиц золота, и каждый год банк оставляет себе p процентов
в качестве комиссии (1 ≤ p ≤ 99), так что золота становится
(100 − p)/100 от прежнего. Когда золота не больше L, жизнь гномика
теряет смысл. G и L — целые числа не больше 2³¹ − 1. Сколько лет
осталось?

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

G, L и p.

## Выходные данные

Число лет.

## Проверка

Тесты репозитория точно сравнивают токены вывода; пробельные разделители между ними несущественны.

## Примеры

### Пример 1

Ввод:

```
81 64 20
```

Вывод:

```
2
```

### Пример 2

Ввод:

```
625 256 20
```

Вывод:

```
4
```

## Решение

Через k лет золота ровно G · ((100 − p)/100)^k, и ответ — первое k, при
котором это не больше L. В целых числах проверка выглядит так:

```text
G · (100 − p)^k ≤ L · 100^k
```

поэтому каждый год обе части умножаются — на 100 − p и на 100, пока
левая не перестанет быть больше. Цикл выполняется не больше примерно
2140 раз, при G = 2³¹ − 1, L = 1 и p = 1, а числа вырастают до
нескольких тысяч цифр. При `Y` годах и ограниченных положительных
начальных данных каждое произведение содержит `O(Y+1)` цифр или
разрядов фиксированного основания. Простые версии требуют `O((Y+1)²)`
операций над цифрами и `O(Y+1)` одновременно используемых дополнительных
цифр/разрядов, включая временные произведения. `+1` учитывает немедленный
ответ за ноль лет. Отдельно учитываются вход и буферы: Rust сохраняет
строку входа, Python — прочитанную строку, остальные простые версии
используют ограниченные буферы scanner/stdio. По заданному формату
вход содержит лишь три ограниченных числа.

Оценка числа итераций предполагает положительные G и L, а нижних границ
для них в условии нет: при G > 0 и L = 0 золото остаётся положительным
через любое конечное число лет, и конечного ответа нет.

Тонкие места:

- золото может попасть ровно на предел, и плавающая точка это
  пропускает: 300 · 0,81 получается 243,00000000000003, на год больше
  при L = 243 (тест 05), а ln(9801/10000) / ln(0,99) округляется вверх
  до трёх лет вместо двух (тест 06);
- если золота уже не больше L, ответ 0 (тесты 03, 04).

## Оптимизированные решения

`1283_binary_search_math.py`. Первый год Y с G(100−p)^Y≤L100^Y находится удвоением границы и двоичным поиском по точным целым степеням. Логарифм, импорт gcd/math и цикл умножения длинных чисел для каждого года не нужны. G≤L сразу даёт ноль, включая нулевые значения; точные равенства сохранены. При длине операндов до D бит и стоимости умножения M(D) консервативно O(log²(Y+2)·M(D)) времени, O(D) памяти. Поисковый алгоритм имеет отдельное имя файла, простая погодовая версия сохранена.

По сравнению с `1283_math.py`: время 0.078 s → 0.125 s; память 480 KB → 264 KB.

Оптимизированное решение на Java хранит каждую сторону как массив цифр
по основанию 10⁹ и умножает его на месте, увеличивая массив только при
появлении новой цифры, вместо создания двух новых объектов `BigInteger`
каждый год; цифра, умноженная не более чем на 100, плюс перенос остаётся
меньше 10¹¹ и помещается в `long`. G, L и p читаются по цифрам прямо из
`System.in` в `int`, которого хватает, ведь они не больше 2³¹ − 1,
вместо создания `Scanner`: [1283_math_optimized.java](1283_math_optimized.java).

### Измеренный выигрыш

Проценты ниже описывают парные исторические посылки из таблиц, а не ещё
одно правило допуска с улучшением на 30%. Содержательные простые версии
сохранены. Java использует то же точное ежегодное сравнение с изменяемыми
разрядами: при ограниченных начальных данных одновременно нужна память
`O(Y+1)` разрядов и буферов, включая временные массивы при росте ёмкости.

- `1283_math_optimized.java`: сокращение времени +0.00%; сокращение
  памяти +93.57%; база: `1283_math.java`.

`1283_math_optimized.rs`. Сохраняется точное сравнение G*(100-p)^Y и L*100^Y, но сначала дроби G/L и (100-p)/100 сокращаются на НОД. Оба произведения хранятся в u128, пока проверяемое умножение успешно; при переполнении оба неизменённых значения до умножения переводятся в разряды u32 по основанию 10^9. Проверка G<=L возвращает ноль до сокращения. Граница остановки не зависит от логарифмов, плавающей точки или epsilon. При Y годах и не более D разрядах время O((Y+1)·D), память O(D); узкие разряды и быстрый путь целой арифметики снижают накладные расходы. Rust-версия читает и пишет через среду выполнения C, без сохранения декодированной входной String и построения форматированной строки ответа. Простой исходник с Accepted сохранён.

По сравнению с `1283_math.rs`: время 0.015 s → 0.031 s; память 232 KB → 68 KB.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

В текущем Go только вынесен неизменный размер выходного буфера 24 байта
в именованную константу для структурного линтера. Остальные
исходники решений не менялись.

`1283_parsing_optimized.go`. Простой `1283_math.go` использует `math/big`
и несокращённые множители `100-p` и `100`. Быстрая версия вводит
изменяемые разряды `[]uint32` по основанию 10⁹, младшими вперёд. Перед
ростом точных произведений годовые множители делятся на их НОД; начальное
отношение `G/L` не сокращается. Поразрядное умножение и сравнение длины,
затем старших разрядов заменяют универсальную длинную арифметику. Входной
буфер на 256 байтов разбирает три числа с локальной позицией и отрицательным
десятичным накоплением, фиксированные временные буферы форматируют ответ.
Неравенство остановки, включая равенство, не меняется. При не более `D`
разрядах время — `O((Y+1)·D)`, используемая дополнительная память —
`O(D+B)`, где `B` — фиксированные буферы ввода-вывода. Ограниченные
начальные данные дают `D = O(Y+1)`.

Accepted #11329132 (Go 1.14 x64): **0.015 s / 812 KB**. Архивное сравнение: `1283_math.go` (Go 1.14 x64) — 0.031 s / 1276 KB (#11284478).

## Особенности языков

Для всех языков действуют общие [рейтинговые критерии](../../RATING_CRITERIA.md):
обычные топ-10 или топ-15% по нужным метрикам, с заменой на сравнение
эталона при 1–10 чужих посылках на том же компиляторе. Ниже 1024 КБ
сравнивается только время. Чужие результаты быстрее `0.015 s` исключаются;
до этого значения снизу ограничивается только наше время. Нет отдельного
требования первого места, улучшения на 30% или ограничений по дате и ID.

Сохранённый аудит допускает оба Rust по обычному рейтингу времени, включая
быстрый Rust (`0.031 s / 68 KB`); прежнее объяснение отсутствием эталона
устарело. C++, простой CPython и быстрый Java тоже проходят обычный рейтинг
по времени. Быстрый Go проходит сравнение малой группы того же компилятора
только по времени. Простые Go и Java не проходят нужное сравнение, но
сохранены для обучения. Дополнительный двоичный поиск на PyPy не проходит
порог времени, его маркер сохранён; позицию Python уже закрывает CPython.
Прежнее обсуждение среза от 18 ноября 2026 года историческое, все парные
измерения Accepted внизу сохранены.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
