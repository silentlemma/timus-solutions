# 1263. Выборы

[Timus 1263](https://acm.timus.ru/problem.aspx?space=1&num=1263) · сложность 42 · implementation

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

N кандидатов (1 ≤ N ≤ 10 000) и M избирателей (1 ≤ M ≤ 10 000); каждый
избиратель называет одного кандидата. Для каждого кандидата вывести долю
голосов в процентах с двумя знаками после точки и знаком `%`.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

N и M, затем M номеров кандидатов от 1 до N.

## Выходные данные

N строк с процентами.

## Примеры

### Пример 1

Ввод:

```
3 6
1
2
3
2
1
1
```

Вывод:

```
50.00%
33.33%
16.67%
```

## Решение

Посчитать голоса каждого кандидата и вывести 100 · голоса / M с двумя
знаками. `O(N + M)`.

Тонкие места:

- кандидаты без голосов тоже получают строку, `0.00%` (тест 03);
- доля может оканчиваться ровно половиной последнего выводимого знака,
  например 1/32 = 3.125% (тесты 04, 05). Эти решения округляют такие
  случаи к чётному, как `printf` в C: 3.12%;
- построчный вывод в некоторых языках медленный при N = 10 000: лучше
  сначала собрать весь вывод.

## Оптимизированные решения

Оптимизированное решение на Python читает голоса построчно через
генератор, а не разбивает весь ввод сразу, и форматирует процент для
каждого различного числа голосов только один раз: кандидаты с одинаковым
числом голосов получают одну и ту же готовую строку. Строки выводятся по
одной через буферизованный `sys.stdout.write`, а не склеиваются заранее:
856 КБ вместо 1948 КБ при том же времени.

Оптимизированное решение на C++ разбирает числа через `getchar` вместо
`scanf` и считает голоса в массиве фиксированного размера из 16-битных
счётчиков: 128 КБ вместо 252 КБ при том же времени. Оптимизированное
решение на Rust разбирает числа вручную из байтов `stdin().lock()`
вместо чтения всего ввода в строку, считает в 16-битных счётчиках и
выводит через буфер на 1 КБ: 252 КБ вместо 468 КБ при том же времени.

## Особенности языков

- C++, Go, Python и Rust форматируют double напрямую; все четыре
  округляют точное значение double половину к чётному.
- `String.format` в Java округляет половину вверх, поэтому Java берёт
  `BigDecimal` от того же double и округляет его с `HALF_EVEN`.
