# 1207. Прямая через две точки, делящая остальные пополам

[Timus 1207](https://acm.timus.ru/problem.aspx?space=1&num=1207) · сложность 117 · geometry

Автор оригинальной задачи — Павел Атнашев; командное соревнование УрГУ, март 2002 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Дано чётное число `4 ≤ N ≤ 10000` точек с целыми координатами не больше
`10⁶` по модулю, никакие три не лежат на одной прямой. Выбрать две из
них так, чтобы прямая через них делила остальные точки на две равные
половины.

Ограничение времени: 0.5 секунды. Ограничение памяти: 64 МБ.

## Входные данные

`N` в первой строке, затем `N` строк, в каждой координаты `x y` одной
точки.

## Выходные данные

Номера двух выбранных точек.

## Проверка

Подходит много пар, поэтому принимаются любые две разные точки, если их
прямая оставляет по `(N − 2)/2` точек с каждой стороны.

## Примеры

### Пример 1

Ввод:

```
4
0 0
1 0
0 1
1 1
```

Вывод:

```
1 4
```

## Решение

Берём самую нижнюю точку, а из двух на одной высоте — левую. Все
остальные точки лежат выше неё или правее на той же высоте, в пределах
полуоборота, поэтому их можно отсортировать по углу вокруг неё одним
знаком векторного произведения, без плавающей точки. В таком порядке все
точки до `k`-й лежат по одну сторону прямой от нижней точки к `k`-й, а
все после — по другую. Среди `N − 1` остальных точек у той, что стоит на
месте `(N − 2)/2` при счёте с нуля, по `(N − 2)/2` точек до и после.
`O(N log N)`.

Тонкие места:

- если выбирать опорную точку произвольно, лучи могут занимать больше
  полуоборота и сломать порядок;
- векторные произведения доходят до `4·10¹²`, больше 32 бит;
- компаратор должен возвращать «равно» при сравнении элемента с самим
  собой, иначе некоторые сортировки его отвергают.

Каждый ответ проверен подсчётом точек с каждой стороны, а отдельно
написанное решение проходит тот же чекер на всех тестах.

## Оптимизированные решения

Оптимизированное решение на Java хранит координаты в массивах `int`,
ведь по модулю они не больше `10⁶`, сортирует массив примитивных
индексов собственной пирамидальной сортировкой вместо сортировки
упакованных `Integer` лямбдой, считает векторные произведения в `long` и
разбирает ввод вручную из блоков по 4 КБ вместо `BufferedReader` и
`StringTokenizer`: {1207_geometry_optimized.java}.

Оптимизированное решение на Python один раз вычисляет для каждой точки
целый ключ и сортирует по ключам, а не вызывает компаратор на Python
`O(N log N)` раз. Ключ — это `−dx/dy`, умноженное на `2⁴²` и округлённое
вниз, где `dx`, `dy` — смещения от опорной точки; `−dx/dy` растёт вместе
с углом относительно опорной точки. Смещения по модулю не больше
`2·10⁶`, поэтому две разные дроби отличаются хотя бы на `1/(2·10⁶)²`, а
`2⁴²` больше `(2·10⁶)²`, так что округлённые ключи остаются различными и
в том же порядке; точки на высоте опорной получают ключ меньше всех
остальных. Координаты читаются построчно в массивы 32-битных целых:
{1207_geometry_optimized.py}.

Оптимизированное решение на Rust читает ввод построчно, а не держит весь
текст и вектор всех его чисел, хранит каждую точку как две координаты
`i32` и её номер в одной структуре, ведь координаты по модулю не больше
`10⁶`, один раз сдвигает точки так, чтобы опорная оказалась в начале
координат, и сортирует их через `sort_unstable_by` по векторным
произведениям в `i64`: {1207_geometry_optimized.rs}.
