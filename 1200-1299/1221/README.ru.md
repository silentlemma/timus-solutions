# 1221. Наибольший чёрный квадрат с белым ромбом внутри

[Timus 1221](https://acm.timus.ru/problem.aspx?space=1&num=1221) · сложность 424 · implementation

Автор оригинальной задачи — Никита Шамгунов; VII студенческое соревнование по программированию УрГУ.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Лист из `N × N` клеток, `N ≤ 100`, раскрашен в чёрный (1) и белый (0).
Вырезать наибольший квадрат со сторонами по линиям сетки, чёрный везде,
кроме белого квадрата, повёрнутого на 45 градусов, вершины которого
касаются середин сторон. Вывести его размер или `No solution`. Во входе
несколько листов, в конце `0`.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

Для каждого листа целое `1 ≤ N ≤ 100`, затем N строк по N двоичных клеток (`1` чёрная, `0` белая). Клетки могут идти с пробелами или без. Финальный `0` завершает ввод и не является листом.

## Выходные данные

Для каждого листа — размер наибольшей такой фигуры или `No solution`.

### Пример 1

Ввод:

```
4
1011
0001
1011
1111
1
0
0
```

Вывод:

```
3
No solution
```

## Решение

У белого ромба есть центральная клетка, и он достаёт до середины каждой
стороны, так что размер фигуры нечётный, `2r + 1` при `r ≥ 1`: клетка со
смещениями `(d, e)` от центра белая ровно тогда, когда `|d| + |e| ≤ r`.
Значит, строка `d` фигуры — это `|d|` чёрных клеток, белый отрезок из
`2(r − |d|) + 1` клеток и снова `|d|` чёрных, и с префиксными суммами
чёрных клеток по каждой строке строка проверяется за константу.

Перебираем радиусы от наибольшего вниз и для каждого все центры; первая
найденная фигура и есть ответ. Большинство кандидатов отсекаются сразу по
трём отдельным клеткам (центр и верхняя вершина должны быть белыми,
левый верхний угол — чёрным), а остальные обычно отпадают на первой же
проверенной строке. `O(N⁴)` в худшем случае, на практике гораздо меньше.

Тонкие места:

- одна белая клетка — не фигура: ромбу нужно место внутри чёрного
  квадрата, так что наименьшая фигура — 3 × 3;
- размеры фигур только нечётные;
- листы идут один за другим до `0`.

Ответы сверены с отдельно написанным решением на 300 файлах со
случайными листами, листами с вставленными фигурами и одноцветными.

Для S листов с наибольшей стороной N проверка строк хранит `O(N²)` живых ячеек поля/префиксов и требует до `O(Σ N_i⁴)` времени поиска плюс чтение I байт. C++/Go обрабатывают один лист и выводят ответы потоком с ограниченными буферами. Java хранит все ответы, добавляя `O(S)` памяти. Простые Python и Rust также сохраняют весь ввод: ещё `O(I + S)` к текущим `O(N²)`; Python временно хранит и плоский список клеток. Быстрая Python читает ограниченные блоки, хранит поле/префиксы байтами (суммы строк ≤100), но сохраняет все S ответов: `O(N² + S + B + T)` памяти при блоке B и максимальном токене T, без всего ввода. Поиск остаётся O(N⁴), это не преобразованные префиксы. Go-префиксы логически занимают O(N²), но фактические массивы фиксированы на M=100: 101²+200² элементов uint16 плюс буферы. Их очистка стоит O(M²) на лист, затем O(N²) построения и O(N³) поиска; выделенная память O(M²+B) даже для малого листа.

## Оптимизированные решения

Новый Go-алгоритм считает белые клетки двумя двумерными префиксными таблицами: в исходной сетке и после u=row+column, v=row−column+N−1. Ромб радиуса r превращается в прямоугольник; неиспользуемые позиции другой чётности содержат нули. В ромбе A=2r(r+1)+1 настоящих клеток. Требуем A белых клеток в преобразованном прямоугольнике и ровно A в окружающем квадрате (2r+1). Первое условие делает ромб целиком белым, второе — остальные клетки квадрата чёрными. Два запроса O(1), поэтому перебор центров и радиусов занимает O(N³), подготовка и память O(N²). Количества не больше 10000 помещаются в uint16.

Принятая версия Go 1.14 x64 заняла 0.031 с при 0.001 с у базовой и использовала 352 KB при 2116 KB у базовой.

Кэш точных исходников и общие [рейтинговые критерии](../../RATING_CRITERIA.md) подтверждают все версии, кроме простой Python. Быстрый Python покрывает №11328771 за 0.156 с / 924 КБ: ниже 1024 КБ нужно только время. База №11283692 за 0.140 с / 1908 КБ проходит время, но не обязательную память эталона (предел 901.6 КБ). Чуть более медленный записанный запуск проходит без заявления об алгоритмическом ускорении. C++/Java/Rust и быстрая Go сравниваются только по времени; простой Go с 2116 КБ нужны обе метрики и выборка всего того же языка. Python/Rust используют применимые эталоны точных компиляторов. Все содержательные учебные версии сохранены без звёздочек, пары замеров не изменены.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1221_implementation_optimized.py`. Строки сетки хранятся в байтах, префиксные суммы строк — в компактных байтовых массивах. Сетки читаются последовательно; поиск наибольшей фигуры и его условия сохранены. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.

Accepted #11328771 (Python 3.12 x64): **0.156 s / 924 KB**. Архивное сравнение: `1221_implementation.py` (Python 3.12 x64) — 0.14 s / 1908 KB (#11283692).

Accepted №11328771 и его численный допуск относятся к историческому точному исходнику. Линтер требует назвать прежний предел пробельных символов 32 как `WHITESPACE_LIMIT`; обратная подстановка константы точно восстанавливает старые байты. Алгоритм, комментарии и простая Python сохранены. Новому хэшу нужен свой Accepted в будущей пачке; старая пара не подтверждает новые байты.

## Проверка

В `tests/tests.json` задан `lines`: сохраняются порядок листов и отдельная строка каждого ответа, без учёта начальных/конечных и повторных пробелов внутри строки. Число строк, написание/регистр (`No solution`) и порядок токенов значимы; на завершающий 0 ответа нет. Собственный пример и малые тесты проверены прямым сравнением каждой клетки кандидата с цветом по манхэттенскому расстоянию, без префиксов.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
