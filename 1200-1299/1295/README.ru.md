# 1295. Бред

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Сколькими нулями оканчивается десятичная запись числа
1ⁿ + 2ⁿ + 3ⁿ + 4ⁿ при 1 ≤ n ≤ 300 000?

Ограничение времени: 0.5 секунды. Ограничение памяти: 64 МБ.

## Входные данные

Одно целое число n, `1 ≤ n ≤ 300000`.

## Выходные данные

Количество нулей на конце.

## Проверка

Тесты репозитория точно сравнивают токены вывода; пробельные разделители между ними несущественны.

## Примеры

### Пример 1

Ввод:

```
8
```

Вывод:

```
0
```

### Пример 2

Ввод:

```
7
```

Вывод:

```
2
```

## Решение

При наибольшем n в сумме больше 180 000 цифр, но нули на конце
ограничены степенью двойки в ней. Пусть S = 1ⁿ + 2ⁿ + 3ⁿ + 4ⁿ.

- n = 1: S = 10, один ноль.
- Чётное n: 1ⁿ + 3ⁿ ≡ 1 + 1 = 2 (mod 4), а 2ⁿ и 4ⁿ кратны 4, так что S
  делится на 2, но не на 4.
- Нечётное n ≥ 3: 3ⁿ ≡ 3 (mod 8), поэтому 1ⁿ + 3ⁿ ≡ 4 (mod 8), а 2ⁿ и
  4ⁿ кратны 8; S делится на 4, но не на 8.

Значит, трёх нулей на конце не бывает, и всё решает S mod 100: два
нуля, если остаток равен 0, один ноль, если он оканчивается на 0, и ни
одного иначе. Четыре степени по модулю 100 считаются быстрым
возведением в степень. `O(log n)`.

На самом деле ответ зависит только от n mod 20: 0, если n делится на 4,
2, если n даёт остаток 3 по модулю 4 или 5 по модулю 20, и 1 в
остальных случаях. Решения вычисляют ответ напрямую, не опираясь на эту
таблицу.

Тонкие места:

- n с остатком 1 по модулю 4 обычно даёт один ноль, но n = 5, 25, …
  дают два (тесты 05 и 06);
- полную сумму можно построить длинной арифметикой, но это не нужно:
  важны только две последние цифры.

Результаты сравнивались с точной суммой в длинной арифметике для всех
n до 3000.

## Оптимизированные решения

`1295_math.java`. Вместо модульного возведения в степень используется формула сравнений: при делимости n на 4 конечных нулей нет; при n mod 4=3 или n mod 20=5 их два; иначе один. Модуль 5 определяет наличие нуля, разложение нечётного случая по модулю 25 — второго, модуль 8 исключает третий (n=1 отдельно даёт 10). Таблицы ответов нет. Арифметика и память O(1), плюс чтение десятичных цифр. Другой алгоритм назван math; модульная альтернатива и учебная версия сохранены. Фактическая формула проверена для всех n=1..300000 независимыми модульными степенями.

Accepted точного исходника Java 1.8 #11327403 — `0.078 s / 340 KB`,
сохранённые места от 20 ноября 2026 года: 2/67 по времени и памяти.
Ниже 1024 КБ нужно только время, поэтому формула проходит. Отдельный
вариант модульных степеней #11305839 имеет `0.109 s / 324 KB`; его
место времени 12/67 не входит ни в топ-10, ни в топ-15% с отсечкой 11,
поэтому звёздочка сохранена. Отдельной языковой цели первого места нет.

- `1295_math.java`: 0.078 s / 340 KB; сохранённая учебная база `1295_number_theory.java` (Java 1.8): 0.125 s / 1600 KB.

У неизменённого Python выбран CPython 3.12 #11327024
`0.062 s / 660 KB`, места времени 1/57 и памяти 30/57. Он проходит
только по времени. База #11284644 — `0.093 s / 464 KB`: выбранный
запуск быстрее, но требует больше памяти. Прежний записанный PyPy
3.10 #11325070 — `0.125 s / 200 KB`, медленнее с меньшей памятью.
Пары разных запусков и компиляторов не смешиваются; далее замечания
об экономии памяти относятся к историческому PyPy. Один файл
переиспользуется без дубликата или отдельной языковой цели допуска.

Оптимизированное решение на Java разбирает `n` вручную из буфера на
4 КБ, заполняемого из `System.in`, а не создаёт `Scanner`, так что JVM
не загружает сканер и его регулярные выражения; степени по модулю 100 те
же: {1295_number_theory_optimized.java}.

### Измеренный выигрыш

Ниже приведены отдельные парные измерения, а не общее улучшение на 30%
или другой критерий допуска. У Go #11328536 относительно базы
#11284638 время осталось `0.031 s`, память снизилась с 1080 до
936 КБ, то есть на 13.3%. Он проходит сравнение времени малой группы,
а не требование экономии 30%. Отрицательное сокращение означает рост
расхода; учебные и прежние отличающиеся реализации сохранены.

- `1295_number_theory_optimized.java`: сокращение времени +12.80%;
  сокращение памяти +79.75%; база: `1295_number_theory.java`.

`1295_number_theory_optimized.py`. Сохраняется рассуждение по модулю 100 для числа конечных нулей. 1+pow(2,n,100)+pow(3,n,100)+pow(4,n,100) считается напрямую вместо генератора четырёх оснований. Модульное возведение не строит огромные степени. Доказанная граница в два конечных нуля означает: нулевой остаток даёт два, делимость на десять — один, иначе ноль. Время O(log n) ограниченных модульных операций, состояние O(1). Самостоятельная программа для судьи явно сбрасывает stdout перед os._exit(0), пропуская обычное завершение интерпретатора. Выигрыш памяти подтверждён её собственным Accepted. Сама смена способа завершения не улучшает асимптотику, а её эффект в среде выполнения не гарантируется на других платформах. Простая версия сохранена без изменений.

По сравнению с `1295_number_theory.py`: время 0.093 s → 0.125 s; память 464 KB → 200 KB.

## Особенности языков

Общие [рейтинговые критерии](../../RATING_CRITERIA.md) одинаковы для языков:
обычные топ-10 или топ-15% по нужным метрикам, заменяемые эталоном
при 1–10 допустимых соперниках того же компилятора. Ниже 1024 КБ
нужно только время. Чужие времена быстрее `0.015 s` исключаются;
лишь наше время ограничивается этим порогом снизу. Ничьи делят место,
процентная отсечка округляется вверх. Нет ограничения по дате/ID,
отдельного первого места или допуска только за улучшение на 30%.
Все алгоритмы, комментарии и пары ячеек Accepted сохранены.

Прежние места PyPy от 18 ноября: время 37/57 и память 1/57 — исторические.
Замороженный аудит точных исходников допускает C++, Java с формулой,
выбранный CPython, быструю Go и простую Rust. Порог времени Go по трём
соперникам — `0.062 s`; база Go превышает порог памяти 1076.40 КБ.
Rust проходит порог `0.062 s` по одному сопернику. Простые Go, Java
и Python сохранены для обучения, хотя нужное сравнение не пройдено.

В текущей Go только вынесена разрядность преобразований 64 в `numericBits`
по требованию строгого линтера. #11328536 и сравнения выше относятся
к прежним точным байтам.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
