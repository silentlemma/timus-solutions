# 1279. Склад

[Timus 1279](https://acm.timus.ru/problem.aspx?space=1&num=1279) · сложность 424 · binary_search

Авторы оригинальной задачи — Сергей Волченков, Владимир Пинаев и Михаил Копачёв; четвертьфинал ACM ICPC 2003–2004, центральный регион России, Рыбинск, 15–16 октября 2003 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Склад из N × M секций (N, M ≤ 100) хранит стопки контейнеров высотой
от 1 до 1000. Приходит K ≤ 10⁷ новых контейнеров, и их по одному ставят
на одну из самых низких секций. Найти наименьшую высоту после того, как
все они поставлены.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

Первая строка содержит целые `N`, `M`, `K`: `1 ≤ N, M ≤ 100`,
`1 ≤ K ≤ 10⁷`. Далее идут `N` строк по `M` целых высот в диапазоне
`1..1000`.

## Выходные данные

Наименьшая высота после размещения контейнеров.

## Проверка

Сравнение по токенам, как в `tests.json`: один десятичный целочисленный
токен, равный итоговой минимальной высоте. Пробелы вокруг несущественны;
лишние токены и другая запись того же числа не совпадают с ответом.

## Примеры

### Пример 1

Ввод:

```
1 4 5
2 2 8 8
```

Вывод:

```
4
```

### Пример 2

Ввод:

```
2 3 26
1 2 3
4 5 6
```

Вывод:

```
7
```

## Решение

Добавление всегда на самую низкую секцию похоже на заливку водой: в
конце все секции ниже некоторого уровня h подняты до h, а оставшиеся
контейнеры подняли часть из них до h + 1, но не все. Чтобы поднять всё
до уровня h, нужно need(h) = Σ max(0, h − высота) контейнеров, и это
число растёт с h. Значит, ответ — наибольшее h с need(h) ≤ K; его
находит двоичный поиск между наименьшей высотой и ею же плюс K.
`O(N · M · log(K+1))`.

Тонкие места:

- ответ может превышать 10⁷, а need(h) до 10⁴ · 10⁷ требует 64 бит
  (тесты 03, 12);
- оставшиеся контейнеры не поднимают минимум, если не достаются каждой
  секции этого уровня (тест 05);
- моделировать контейнеры по одному при K = 10⁷ слишком медленно.

Все девять исходников проходят 19 тестов. Каждый ответ независимо
подтверждён точной стоимостью этой и следующей высоты; малые случаи
также проверены размещением контейнеров по одному с помощью кучи.

## Оптимизированные решения

Новые Go и Rust используют ограничение исходной высоты H=1000. Считаем стопки каждой высоты, затем поднимаем уровень от 1. Перед переходом с высоты h добавляем её стопки к активным; следующий полный слой требует по контейнеру на каждую активную стопку. Если остатка не хватает, h и есть итоговый минимум. Когда активны все стопки, сразу прибавляем остаток, делённый на N·M; неполный слой минимум не меняет. Время O(N·M+H), память O(H), без сортировки и повторных проверок. Бюджет хранится в 64 битах. Исходные бинарные поиски сохранены; C++, Java и Python также закрывают быстрый набор.

Сохранённый срез допускает базовые [1279_binary_search.cpp](1279_binary_search.cpp)
и [1279_binary_search.java](1279_binary_search.java) по обычному правилу
топ-10 или топ-15% только по времени: их посылки используют 280 и 600 КБ.
Базовый [1279_binary_search.py](1279_binary_search.py) использует 1344 КБ
и проходит сравнение с эталоном малой группы того же компилятора по
времени и памяти. Эти содержательные базовые исходники покрывают быстрый
набор без одинаковых копий. Простой Go требует обеих метрик по обычному
рейтингу, жадный Go — только времени по обычному рейтингу. Все три Rust
проходят сравнение малой группы только по времени. Сортирующий Python
тоже требует обеих метрик при сравнении с эталоном малой группы.

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1279_sorting_optimized.py`. Высоты сортируются, затем минимальный префикс поднимается до следующего уровня, пока хватает контейнеров. Остаток делится на размер префикса. Вместо двоичного поиска по высоте выполняется один проход после сортировки: O(nm log(nm+1)) времени и O(nm) памяти. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1279_binary_search_implementation_optimized.rs`. Точка входа C напрямую вызывает решение и сбрасывает вывод Rust перед возвратом. Также стандартный разбор целых заменён на `parse_integer`: цифры накапливаются умножением на десять и сложением/вычитанием, с поддержкой знака. Токены по-прежнему берутся из строки всего входа, двоичный поиск не изменён. Версия с обычной точкой входа сохранена.

Accepted #11328966 (Rust 1.75 x64): **0.015 s / 460 KB**. Архивное сравнение: `1279_binary_search.rs` (Rust 1.75 x64) — 0.031 s / 512 KB (#11284398).


Для двоичного поиска `I` — число байтов входа, `B` — фиксированные
буферы ввода-вывода. Время — `O(I + N·M·log(K+1))`, дополнительная
память — `O(N·M+B)` у потоковых C++/Go/Java и `O(I+N·M+B)` у Python/Rust,
читающих весь вход, включая вариант Rust с другой точкой входа.
Сортирующий Python также хранит вход и срез хвоста массива: память
`O(I+N·M+B)`, время `O(I+N·M·log(N·M+1))`. Гистограммные Go/Rust требуют
`O(I+N·M+H)` времени и `O(H+B)` памяти; входной массив содержит 256 байтов,
выходной — 20 байтов.

В семи исходниках уточнён только комментарий об уровне воды: изначально
более высокие стопки не меняются. Оба гистограммных исходника не менялись и сохраняют точные
привязки к своим Accepted.
