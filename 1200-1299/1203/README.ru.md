# 1203. Сколько докладов может посетить один человек

[Timus 1203](https://acm.timus.ru/problem.aspx?space=1&num=1203) · сложность 78 · greedy

Автор оригинальной задачи — Магаз Асанов; командное соревнование УрГУ, март 2002 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

На конференции `N ≤ 10⁵` интересных докладов, каждый идёт с минуты `Ts`
по минуту `Te`, `1 ≤ Ts < Te ≤ 30000`. Посещённые доклады не могут
пересекаться, и между ними должна быть хотя бы минута: после доклада,
кончающегося в 15, следующий может начаться не раньше 16. Найти наибольшее
число докладов, которые может посетить один человек.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

Первая строка содержит целое N, 1 ≤ N ≤ 100000. Каждая из следующих N строк содержит целые времена начала и конца Ts Te: 1 ≤ Ts < Te ≤ 30000.

## Выходные данные

Наибольшее число докладов.

## Проверка

Тесты репозитория точно сравнивают целочисленный токен ответа, игнорируя пробелы и переводы строк.

## Примеры

### Пример 1

Ввод:

```
7
8 10
1 2
5 8
3 5
6 7
10 11
12 14
```

Вывод:

```
5
```

## Решение

Классическая жадность для выбора интервалов: раз за разом берём доклад,
который кончается раньше всех среди начинающихся после конца последнего
выбранного. Любое оптимальное расписание может заменить свой первый
доклад на этот без потерь, и рассуждение повторяется.

Времена маленькие, поэтому сортировка не нужна: для каждой минуты `e`
храним самое позднее начало среди докладов, кончающихся в `e`. Идём по
минутам по порядку; если самое позднее начало в `e` позже конца
последнего выбранного, доклад, кончающийся в `e`, можно взять, и он
кончается раньше всех доступных. `O(N + T)` при `T = 30000`.

Массиву последних начал нужна O(T) память. Базы C++/Go/Java читают доклады постепенно с фиксированной буферизацией, их память O(T + B), где B — ограниченный размер буфера. Простая Python дополнительно сохраняет O(I) входа/токенов и O(N) ссылок срезов; простая Rust — входной String длины O(I) и O(N) разобранных чисел: всего O(T + I + N). Быстрая Go тоже сохраняет весь вход в байтах, используя O(T + I). Буферные быстрые C++/Rust и блочная Python с массивом требуют O(T + B + L), где L — длина наибольшего токена. 16-битные начала уменьшают константу, не меняя O(T) размера таблицы. В оценки включено хранение входа; работа с временными корзинами у всех O(N + T).

Тонкие места:

- доклад, начинающийся в ту же минуту, когда кончается предыдущий,
  нельзя, так что проверка строгая: «начало > последний конец»;
- повторяющиеся одинаковые доклады засчитываются не больше одного раза.

Ответы сверены с отдельно написанным решением на 300 случайных входах и
на всех тестах.

## Оптимизированные решения

Оптимизированные решения (C++, Rust) разбирают числа вручную прямо из
буфера ввода вместо `scanf` или чтения всего ввода в строку и хранят
самые поздние начала 16-битными числами, поскольку все времена не больше
30 000. C++ укладывается в 0.001 с вместо 0.109 с и 164 КБ вместо
304 КБ; Rust занимает 276 КБ вместо 4176 КБ, а парное время растёт с 0.015 с до 0.031 с.

Оптимизированное решение на Python читает ввод блоками по 16 КБ и
разбирает его по мере надобности, а поздние начала хранит в `array`
16-битных чисел вместо списка: 980 КБ вместо 14476 КБ, хотя время растёт
с 0.109 с до 0.140 с.

Ввод целиком хранится в байтовом буфере: это обмен памяти под ввод на меньшие накладные расходы универсального ввода-вывода.

## Особенности языков

При этом ревью в `1203_greedy_optimized.go` только названы существующие 64-битные параметры преобразований целых и вещественных чисел; подстановка констант воспроизводит исходный исполняемый текст. Простая Go и все содержательные комментарии не менялись.

Ничего особенного не требуется.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
