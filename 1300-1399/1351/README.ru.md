# 1351. Хороший гнусмас - мёртвый гнусмас

[Timus 1351](https://acm.timus.ru/problem.aspx?space=1&num=1351) · сложность 518 · geometry

Автор оригинальной задачи — Денис Мусин; чемпионат школьников, март 2005 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Пулемёт в начале координат простреливает сектор между двумя лучами:
правая граница проходит через (X1, Y1), левая — через (X2, Y2); сектор
меньше половины оборота. Дальность стрельбы D ≤ 30 000. Для каждой из
N ≤ 30 000 точек нужно вывести `YES`, если точка лежит в секторе и не
дальше D, и `NO` иначе.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

Целые D, X1, Y1, X2, Y2, затем N и N пар координат;
1 ≤ D, N ≤ 30000, абсолютные значения координат не больше 30000.
Цели не совпадают с началом координат, векторы обоих лучей ненулевые.
В сохранённом условии написана нижняя граница 1 для модуля каждой
компоненты границы, но официальный пример содержит нули. Следуя
примеру, реализации разрешают осевые ненулевые лучи. Сектор против
часовой стрелки от правой границы к левой строго меньше 180°.

## Выходные данные

N строк с `YES` или `NO`.

## Проверка

Сравнение токенов (`judging: tokens`): ровно N ответов `YES` или
`NO` в порядке точек, с учётом регистра. Лучи и окружность дальности
включены; пробельные разделители несущественны.

## Примеры

### Пример 1

Ввод:

```
5 1 0 0 1
6
1 1
5 6
3 0
-1 2
0 5
-3 0
```

Вывод:

```
YES
NO
YES
NO
YES
NO
```

## Решение

Сектор идёт против часовой стрелки от правой границы R к левой границе
L. Точка P лежит в нём, если она не по часовой стрелке от R и не против
часовой стрелки от L:

- cross(R, P) = X1·y − Y1·x ≥ 0;
- cross(P, L) = x·Y2 − y·X2 ≥ 0.

Каждое условие задаёт полуплоскость, и раз сектор меньше половины
оборота, две полуплоскости пересекаются ровно по сектору, с одним
исключением: если обе границы лежат на одном луче (сектор нулевой
ширины), обратное продолжение этого луча тоже проходит оба условия.
Поэтому точка на прямой границы, но позади пулемёта, с нулевым
векторным и отрицательным скалярным произведением, отбрасывается
отдельно. Дальность
проверяется как x² + y² ≤ D², всё в целых числах, без корней. `O(N)`.

Тонкие места:

- точки на границах и на окружности считаются: `3 0` и `0 5` в
  примере;
- у точки на луче, противоположном границе, векторное произведение с
  этой границей равно нулю; её отсекает второе условие, кроме сектора
  нулевой ширины, где это делает только отдельная проверка (тесты 02 и
  06);
- произведения доходят до 1,8·10⁹ и помещаются в знаковые 32-битные целые;
- при D = 30 000 точка (30 000, 1) чуть дальше дальности (тест 04).

Ответы сравнивались с проверкой углов через `atan2` на 18
сгенерированных тестах и с независимым решением на 300 случайных
секторах, включая секторы нулевой ширины.

## Оптимизированные решения

C++, Go и Rust сохраняют проверку двух векторных произведений и квадрата расстояния. Для сектора шириной от 0 до 180° без крайних значений две замкнутые полуплоскости пересекаются ровно по сектору. Когда лучи границ совпадают, обе проверки пропускают всю прямую. На этой прямой отрицательное скалярное произведение исключает точки позади начала луча. Модуль каждой координаты не превосходит 30 000. Сумма или разность двух произведений координат по модулю не больше 2·30 000² = 1,8·10⁹ и помещается в знаковое 32-битное целое. Каждая точка обрабатывается сразу. Буферы ввода на 4096 и вывода на 8192 байта заменяют растущие строки Rust, накопление ответов C++ и Scanner с разбором токенов Go. Время O(N), дополнительная память постоянна; углы с плавающей точкой не нужны. Простые исходники сохранены, Java использует подходящую базу, Python — отдельную потоковую версию.

Java использует базу: обе обязательные метрики, время 8/17 и память
5/17, проходят топ-10. Python закрывает
[1351_geometry_optimized.py](1351_geometry_optimized.py), Accepted
#11328774 `0.093 с / 1172 КБ`, а не база с 6832 КБ. Пять точных
соперников CPython дают третий эталон с пределами
`0.109 с / 5170.40 КБ`; при 1172 КБ обе метрики обязательны и проходят.
База не проходит память. Действуют общие
[критерии](../../RATING_CRITERIA.md); полезные простые файлы сохранены
без одинаковых копий.

## Особенности языков

Геометрический проход O(N) не означает постоянную память всех баз.
C++/Java сохраняют O(N) вывода; Go выводит потоково с памятью O(B).
Python хранит ввод, токены, целые и ответы: O(I+N+B), где I — байты
ввода. Простая Rust сохраняет входную и выходную String: O(I+N+B).
B — ограниченные буферы парсера/ввода-вывода; C++/Java используют
O(N+B). Быстрые C++/Go/Rust потоковые с фиксированными буферами O(B).
Быстрая Python хранит блок ввода и пачку 1024 ответов, плюс частичный
токен. Полное время O(I+N), геометрическое состояние O(1).

Эти замечания относятся к базовым реализациям.

- Векторные произведения и квадраты считаются в 64-битных целых в C++,
  Go, Java и Rust, а в Python — в целых произвольной точности.
- Java читает через `StreamTokenizer`; его значения double хранят эти
  целые точно.

В `1351_geometry_optimized.py` только именованы требуемые линтером константы; значения, алгоритм и комментарии прежние. Accepted #11328774 и парные метрики относятся к предыдущим точным байтам.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
