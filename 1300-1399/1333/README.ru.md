# 1333. Джинн-бомбардировки 2

[Timus 1333](https://acm.timus.ru/problem.aspx?space=1&num=1333) · сложность 219 · geometry

Автор оригинальной задачи — Ден Расковалов; X командный чемпионат школьников Свердловской области по программированию, 16 октября 2004 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

До 10 бомб падают на единичный квадрат 0 ≤ x, y ≤ 1. Каждая поражает
круг с центром (x, y) и радиусом r, все числа от 0 до 1. Нужно вывести
долю квадрата, поражённую хотя бы одной бомбой, в процентах, с ошибкой
не больше одного процента.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

N, затем N строк с x, y и r.

## Выходные данные

Процент поражённой площади квадрата.

## Проверка

Выводится процент, не доля. По условию достаточно точности
в один процентный пункт. Репозиторный проверяющий модуль использует
`|actual−expected|≤0.01·max(1,|expected|)` в процентах; это отдельное
локальное правило, не универсальная граница квадратуры. Каждый кандидат
прошёл 12 архивных и 206 дополнительных полных входов в Docker, получив
собственный Accepted точного SHA. Независимый эталон строит адаптивные
нижние/верхние прямоугольные оценки всех сечений внутри ячейки и
использует площади целого/половины/четверти круга, а не сетку середин
кандидата. Максимальное отклонение от концов оценок на этом наборе —
меньше 0,004001 пункта; это результат набора, не всеобщая гарантия.
Важны отсутствие кругов, нулевые радиусы, обрезка, вложенность/повторы,
почти касающиеся круги, малые радиусы и оба примера.

## Решение

При фиксированном x круг `(cx,cy,r)` задаёт отрезок
`cy±sqrt(r²−(x−cx)²)`, если `|x−cx|<r`. Ограничиваем его `[0,1]`.
Сортируем отрезки по нижнему концу и считаем объединение, прибавляя
только часть за наибольшим уже покрытым верхним концом. Перекрытия,
повторы и вложенные круги учитываются один раз; нулевой радиус площади
не даёт. Для длины объединения f(x) ответ равен `100∫₀¹ f(x)dx`.

Пять простых исходников берут S=20000 равных полос и их середины:
`area≈Σ f((k+1/2)/S)/S`. Время `O(SN log N)`, вспомогательная память
O(N) плюс ввод/вывод. Все пять принятых файлов побайтово сохранены.

Вместо эмпирической оценки докажем границу погрешности. Отрезок одного
круга до центра расширяется по включению, после — сужается. Суммарная
длина его изменений, измеренных симметрической разностью, не больше 4r;
обрезка квадратом её не увеличивает. Изменение объединения содержится
в объединении изменений отдельных отрезков. Значит, полная вариация f
не больше `4Σr`. На полосе ширины h интеграл отклонения от значения
в середине не больше h/2, умноженного на вариацию на полосе: каждое
изменение слева/справа затрагивает не больше половины полосы. Суммируя,
получаем `|area−midpoint|≤2Σr/S`. При N≤10,r≤1 и S=20000 это не больше
0,1 процентного пункта в точной арифметике — внутри допуска задачи
в один пункт.

## Особенности языков

Метрики связаны с точными Accepted-исходниками. Срез от 2 ноября 2026 года:
быстрый C++ имеет места 1/1 среди 69 отфильтрованных чужих посылок,
Java — 1/1 среди 4, Python — 1/2 среди 8, поэтому допустимый по времени
Python отмечен звёздочкой. У Go/Rust нет конкурентов после фильтрации:
формальное покрытие не доказывает превосходства. Установленная цель
C++ — верхние 15% или первые десять мест по обоим показателям,
других семейств — первое место по обоим. Все пять позиций имеют
допустимое улучшение либо прежнюю базу, уже достигшую цели.

## Оптимизированные решения

Алгоритм середин и объединения отрезков прежний, но S=4096.
Доказанная граница равна `100·20/4096=0,48828125` процентного пункта,
что меньше одного. Она учитывает обрезку, перекрытия, узкие круги
и касания; успешной случайной проверки для уменьшения числа полос
недостаточно. Округление процента до шести знаков добавляет не больше
0,0000005 пункта. Используем double и сначала сравниваем квадраты,
не извлекая корень из неположительного подкоренного выражения.

Квадраты радиусов считаются один раз. C++/Go/Java повторно используют
ограниченные массивы отрезков и сортировку вставками без выделения
объектов на каждой полосе: время `O(SN²)`, память O(N) при N≤10.
Python сохраняет сортировку: `O(SN log N)` и O(N). Это улучшения
реализации того же алгоритма, поэтому имена имеют `_optimized`.

C++ допущен по экономии памяти 39,3%; разница 0,031→0,015 с — один тик
и не считается достоверным ускорением. Go экономит 67,4% времени
и 81,2% памяти, Java — 50,3% и 90,9%. Python быстрее на 30,1% (0,156→0,109 с),
но памяти стало на 11,9% БОЛЬШЕ (504→564 КБ): допуск только по времени,
рейтинговый недобор отмечен звёздочкой. Rust при прежнем времени
сэкономил лишь 1,5% памяти (268→264 КБ), поэтому новый файл не добавлен.
Прежний Rust уже закрывает формальный критерий при пустой выборке
конкурентов.
