# 1399. 节俭的经理

[Timus 1399](https://acm.timus.ru/problem.aspx?space=1&num=1399) · 难度 9494 · dp

原题作者 Alexander Ipatov。

[English](README.md) · [Русский](README.ru.md) · **中文** · [Español](README.es.md)

## 任务

一辆载重 Lmax ≤ 3000 的卡车从仓库向 M ≤ 20 个客户运送 N ≤ 50 件货物。每件货
物有重量和客户，仓库与客户之间的距离已给出且满足三角不等式，每趟运输都从仓
库出发并回到仓库。要安排各趟运输使总距离较小：只要不比评测程序找到的方案
长，就被接受。

时间限制：2 秒。内存限制：64 MB。

## 输入

M、N 和 Lmax，(M+1)×(M+1) 距离矩阵（仓库为 0），然后是每件货物的重量和客户。

## 输出

运输趟数；然后每趟给出其货物、载重、从 0 出发回到 0 的路线和长度；最后是总长
度，各块之间按样例用空行分隔。

## 解法

一趟运输的代价只取决于它的客户集合的最短回路，所以解答先对全部 2ᴹ 个集合算出
这个值。Held-Karp 表保存从仓库出发、经过每个集合、终止于每个客户的最短路，
共 2²⁰·20 个 16 位数；路径只从集合内的客户延伸到集合外的客户。

接下来，方案就是为每件货物选一趟运输。先用最廉价插入：每件货物放入回路增长
最少的那一趟，或新开一趟，并遵守载重。然后进行 300 000 轮大邻域搜索：取出若
干货物（几件随机货物、一整趟或某个客户的全部货物），按随机顺序用最廉价插入逐
件放回；若总长增加超过一个阈值就撤销这一轮，阈值从初始方案的 2% 线性降到零。
输出见过的最佳方案，各路线从表中读回。插入一件货物对每趟只需查一次表，所以搜
索相对于建表很便宜：`O(2ᴹ·M²)` 加上各轮。

注意事项：

- 同一客户的货物可能需要好几趟（测试 03 和生成测试 6），所以方案按货物而不是
  按客户来定；
- 先复用空出来的运输再新开一趟，否则搜索中趟数会无限增长；
- 随机数来自同一个 xorshift 生成器，接受与否只用整数判断，所以 C++、Go、Java 和 Rust 输出完全相同的方案，测试可以要求总长不超过它；Python 对一趟或两趟的情形精确求解，可能输出更短的方案。

在 300 个随机小规模实例上与枚举所有货物划分得到的精确最优解做了比较，全部达
到最优；样例的总长为 34，与评测相同。测试由检查程序判定：验证方案合法，并要
求总长不超过测试中给出的值。

## 各语言说明

- Java 只为终点在集合内部的路径保存子集表，同一集合的路径相邻存放，并通过从去掉最后一个客户的集合拉取值来填表，因此按顺序读写；为每个客户和集合都留一格时会超过 64 MB 限制。此外它跳过没有货物的客户和一趟运不完的集合，不用 BigInteger 生成随机数，并在第一个方案可证明最优时直接停止：评测用时 1.48 秒，而早期版本在第 25 个测试上超时。

- Python 在 PyPy 下运行，只为搜索实际询问的集合计算环路长度：对可互换客户的数量做动态规划，并用带一棵树下界的分支限界；一两趟就够时直接求出最优方案，否则执行与其他语言相同的搜索。四轮这样的改进使它从评测第 17 个测试推进到第 24 个测试，但在那里仍然超时（2.03 秒）：在这里最难的情形下，即二十个客户且几乎装满货车，子集表仍需约 10⁸ 步，仅 PyPy 就约 0.7 秒。因此保留并标为 TLE：它通过了这里的全部测试，但不保证在评测的每个测试上都足够快。
