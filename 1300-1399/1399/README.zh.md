# 1399. 节俭的经理

[Timus 1399](https://acm.timus.ru/problem.aspx?space=1&num=1399) · 难度 8299 · dp, local_search

原题作者 Alexander Ipatov。

[English](README.md) · [Русский](README.ru.md) · **中文** · [Español](README.es.md)

## 任务

一辆载重 Lmax ≤ 3000 的卡车从仓库向 M ≤ 20 个客户运送 N ≤ 50 件货物。每件货
物有重量和客户，仓库与客户之间的距离已给出且满足三角不等式，每趟运输都从仓
库出发并回到仓库。要安排各趟运输使总距离较小：只要不比评测程序找到的方案
长，就被接受。

时间限制：2 秒。内存限制：64 MB。

## 输入

M、N 和 Lmax，(M+1)×(M+1) 距离矩阵（仓库为 0），然后是每件货物的重量和客户。

## 输出

运输趟数；然后每趟给出其货物、载重、从 0 出发回到 0 的路线和长度；最后是总长
度，各块之间按样例用空行分隔。

## 解法

一趟运输的最小代价只取决于客户集合。C++、Go 和 Rust 用 Held-Karp 对全部
2ᴹ 个集合求值：最多 2²⁰·20 个 16 位数保存从仓库经过集合到每个客户的最短路径，且只向集合
外延伸。Java 保存可行集合及其内部终点；Python 按需估计回路。

接下来，方案就是为每件货物选一趟运输。先用最廉价插入：每件货物放入回路增长
最少的那一趟，或新开一趟，并遵守载重。然后进行至多 300 000 轮大邻域搜索：取出若
干货物（几件随机货物、一整趟或某个客户的全部货物），按随机顺序用最廉价插入逐
件放回；若总长增加超过一个阈值就撤销这一轮，阈值从初始方案的 2% 线性降到零。
输出见过的最佳方案，DP 版本的各路线从表中读回。
表中 R 为轮数，T 为运输槽数，S 为缓存的客户集合数，B 为分支限界调用次数。

注意事项：

- 同一客户的货物可能需要好几趟（测试 03 和生成测试 6），所以方案按货物而不是
  按客户来定；
- 先复用空出来的运输再新开一趟，否则空运输槽可能随搜索轮数不断积累；
- 随机数来自同一个 xorshift 生成器，接受与否只用整数判断，所以 C++、Go、Java 和 Rust 输出完全相同的方案；Python 在时间预算内搜索，方案长度会因运行时和机器而异。

在 300 个随机小规模实例上与枚举所有货物划分得到的精确最优解做了比较，全部达
到最优；样例的总长为 34，与评测相同。检查程序验证方案合法，并允许总长比测试
给出的值最多长 10 %。Python 获得接受并不提供一般的近似保证。

## 各语言说明

- Java 只为终点在集合内部的路径保存子集表，同一集合的路径相邻存放，并通过从去掉最后一个客户的集合拉取值来填表，因此按顺序读写；早期为每个客户和集合都留一格的版本曾超过 64 MB 限制。此外它跳过没有货物的客户和一趟运不完的集合，不用 BigInteger 生成随机数，并在第一个方案可证明最优时直接停止：评测用时 1.48 秒，而早期版本在第 25 个测试上超时。

- Python 在 PyPy 下运行，不建曾使搜索在评测第 24 个测试上耗时 2.03 秒的稠密
  子集表。它移除没有货物的客户，缓存由相邻集合或最廉价插入得到的回路，再用
  2-opt、移动至多三个客户的片段以及在三处切分后交换相邻片段的重启来改进。
  若全部货物可一趟运完，或活跃客户的每个真子集及其全部货物都可一趟运完，
  则用 1-树下界和分支限界尝试精确求出一趟或两趟方案，超过 10 000 个节点后
  退回启发式算法。主搜索以总处理器时间 1.4 秒为目标，每 256 轮检查一次，达到
  下界时提前停止；阈值按轮次或时间下降，取先耗尽者。精确求解和最终回路改进
  不受此计时检查中断：评测用时 1.39 秒。
