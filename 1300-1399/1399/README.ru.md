# 1399. Экономный директор

[Timus 1399](https://acm.timus.ru/problem.aspx?space=1&num=1399) · сложность 9494 · dp

Автор оригинальной задачи — Александр Ипатов.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Один грузовик грузоподъёмностью Lmax ≤ 3000 развозит N ≤ 50 товаров со
склада M ≤ 20 клиентам. У каждого товара есть масса и клиент,
расстояния между складом и клиентами заданы и удовлетворяют неравенству
треугольника, а каждый рейс начинается и заканчивается на складе. Нужно
спланировать рейсы с небольшим суммарным расстоянием: план принимается,
если он не длиннее найденного программой жюри.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

M, N и Lmax, матрица расстояний (M+1)×(M+1), где склад — 0, затем масса
и клиент каждого товара.

## Выходные данные

Число рейсов; затем для каждого рейса его товары, загрузка, маршрут от 0
обратно к 0 и длина; затем общая длина, с пустыми строками между блоками,
как в примере.

## Решение

Стоимость рейса — это лишь кратчайший объезд его множества клиентов,
поэтому решения сначала находят его для каждого из 2ᴹ множеств. Таблица
Хелда — Карпа хранит кратчайший путь от склада через каждое множество с
концом в каждом клиенте — 16-битные числа в 2²⁰·20 ячейках; пути
продлеваются только от клиентов множества к клиентам вне его.

Дальше план — это выбор рейса для каждого товара. Начинаем с дешёвой
вставки: каждый товар идёт в рейс, объезд которого растёт меньше всего,
или в новый рейс, с соблюдением грузоподъёмности. Затем 300 000 кругов
поиска с большой окрестностью: вынимаем несколько товаров (несколько
случайных, целый рейс или все товары одного клиента), возвращаем их по
одному в случайном порядке дешёвой вставкой и отменяем круг, если сумма
выросла больше порога, который линейно падает от 2% первого плана до
нуля. Выводится лучший встреченный план, маршруты восстанавливаются по
таблице. Вставка товара стоит одного обращения к таблице на рейс, так
что поиск дёшев по сравнению с таблицей: `O(2ᴹ·M²)` плюс круги.

Подводные камни:

- товарам одного клиента может понадобиться несколько рейсов (тест 03 и
  сгенерированный тест 6), поэтому план строится по товарам, а не по
  клиентам;
- опустевший рейс используется раньше нового, иначе число рейсов во
  время поиска растёт без конца;
- случайные числа берутся из одного и того же генератора xorshift, а
  решение о принятии — только в целых числах, так что все языки выводят
  один и тот же план, и тесты могут требовать эталонную длину.

Планы сравнивались с точным оптимумом, найденным перебором всех
разбиений товаров, на 300 случайных маленьких наборах, и все оказались
оптимальными; на примере сумма равна 34, как у жюри. Тесты проверяются
программой, которая проверяет план и требует сумму не длиннее эталонной.

## Особенности языков

- Java хранит таблицу подмножеств только для обходов, кончающихся внутри
  своего множества, обходы одного множества подряд, и заполняет её,
  забирая значения у множества без последнего клиента, так что таблица
  читается и пишется по порядку; с ячейкой на каждую пару «клиент,
  множество» она превышала лимит 64 МБ. Лимит времени она всё равно
  превышает на тесте 25 жюри (2,02 с) и оставлена с пометкой TLE.
- Python запускается в PyPy, и на самых больших здешних тестах ему нужно
  около 1,8 с; на сервере он превышает лимит времени на тесте 17 и
  оставлен с пометкой TLE.
- Оба решения проходят все наши тесты, но не претендуют на то, что
  успеют на каждом тесте жюри.
