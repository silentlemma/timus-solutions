# 1399. Экономный директор

[Timus 1399](https://acm.timus.ru/problem.aspx?space=1&num=1399) · сложность 8299 · dp, local_search

Автор оригинальной задачи — Александр Ипатов.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Один грузовик грузоподъёмностью Lmax ≤ 3000 развозит N ≤ 50 товаров со
склада M ≤ 20 клиентам. У каждого товара есть масса и клиент,
расстояния между складом и клиентами заданы и удовлетворяют неравенству
треугольника, а каждый рейс начинается и заканчивается на складе. Нужно
спланировать рейсы с небольшим суммарным расстоянием: план принимается,
если он не длиннее найденного программой жюри.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

M, N и Lmax, матрица расстояний (M+1)×(M+1), где склад — 0, затем масса
и клиент каждого товара.

## Выходные данные

Число рейсов; затем для каждого рейса его товары, загрузка, маршрут от 0
обратно к 0 и длина; затем общая длина, с пустыми строками между блоками,
как в примере.

## Решение

Минимальная цена рейса зависит только от множества его клиентов. C++,
Go и Rust считают её для всех 2ᴹ множеств динамикой Хелда — Карпа:
до 2²⁰·20 16-битных ячеек хранят кратчайшие пути со склада через множество
с концом в каждом клиенте, продолжая их только за его пределы. Java хранит допустимые
множества и концы внутри них; Python оценивает объезды по необходимости.

Дальше план — это выбор рейса для каждого товара. Начинаем с дешёвой
вставки: каждый товар идёт в рейс, объезд которого растёт меньше всего,
или в новый рейс, с соблюдением грузоподъёмности. Затем до 300 000 кругов
поиска с большой окрестностью: вынимаем несколько товаров (несколько
случайных, целый рейс или все товары одного клиента), возвращаем их по
одному в случайном порядке дешёвой вставкой и отменяем круг, если сумма
выросла больше порога, который линейно падает от 2% первого плана до
нуля. Выводится лучший встреченный план, маршруты восстанавливаются по
таблице в версиях с ДП.
Здесь R — число раундов, T — ячейки рейсов, S — закешированные
множества клиентов, B — вызовы поиска ветвями и границами.

Подводные камни:

- товарам одного клиента может понадобиться несколько рейсов (тест 03 и
  сгенерированный тест 6), поэтому план строится по товарам, а не по
  клиентам;
- опустевший рейс используется раньше нового, иначе пустые ячейки
  рейсов могут накапливаться с числом раундов поиска;
- случайные числа берутся из одного и того же генератора xorshift, а
  решение о принятии — только в целых числах, так что C++, Go, Java и
  Rust выводят один и тот же план; Python ищет в пределах бюджета
  времени, поэтому длина его планов может отличаться в зависимости от
  среды исполнения и машины.

Планы сравнивались с точным оптимумом, найденным перебором всех
разбиений товаров, на 300 случайных маленьких наборах, и все оказались
оптимальными; на примере сумма равна 34, как у жюри. Проверяющая программа
проверяет план и допускает сумму до 10 % длиннее заданной в тесте.
Принятие Python не даёт общей гарантии близости к оптимуму.

## Особенности языков

- Java хранит таблицу подмножеств только для обходов, кончающихся внутри
  своего множества, обходы одного множества — подряд, и заполняет её,
  вытягивая значения из множества без последнего клиента, так что
  таблица читается и пишется по порядку; с ячейкой для каждой пары
  клиента и множества она превышала лимит 64 МБ. Кроме того, она
  пропускает клиентов без грузов и множества, которые не увезти за один
  рейс, получает случайные числа без BigInteger и останавливается сразу,
  если первый план заведомо оптимален: у жюри 1,48 с, тогда как прежняя
  версия превышала лимит времени на тесте 25.

- Python запускается под PyPy без плотной таблицы подмножеств, которая
  вместе с поиском давала 2,03 с на тесте 24 жюри. Он удаляет клиентов
  без товаров и кеширует объезды, построенные из соседних множеств или
  дешёвой вставкой, улучшая их 2-opt, переносами до трёх клиентов и
  перезапусками с обменом соседних отрезков в трёх точках разреза.
  Если все товары помещаются в один рейс либо любое собственное
  подмножество активных клиентов помещается со всеми своими товарами,
  он пытается точно найти план из одного или двух рейсов с оценками по
  1-деревьям и ветвями и границами, переходя к эвристике после 10 000
  узлов. Основной поиск ориентируется на 1,4 с общего процессорного
  времени с проверкой каждые 256 раундов и остановкой на нижней оценке;
  порог убывает по раундам или времени — что кончается быстрее. Точное
  решение и итоговое улучшение объездов вне проверки часов: у жюри 1,39 с.
