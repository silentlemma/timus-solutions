# 1008. Перевод между двумя кодировками связной фигуры из пикселей

[Timus 1008](https://acm.timus.ru/problem.aspx?space=1&num=1008) · сложность 367 · bfs

Оригинальная задача — Third Open USTU Collegiate Programming Contest (PhysTech Cup), 2000.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Фигура — непустое множество чёрных пикселей с координатами `1 ≤ x, y ≤ 10`,
связное по сторонам (пиксели с общей стороной — соседи). Её можно записать
двумя способами:

1. **Список**: число пикселей, затем по строке `x y` на пиксель,
   отсортированные по `x`, затем по `y`.
2. **Описание**: строка `x y` *стартового* пикселя — с наименьшим `x`, а среди
   таких с наименьшим `y`, — затем по строке на каждый пиксель в порядке
   обхода в ширину от старта. Строка пикселя перечисляет в порядке `R` (x+1),
   `T` (y+1), `L` (x-1), `B` (y-1) тех его соседей, которые ещё не
   упоминались; в этом же порядке они добавляются в очередь. Каждая строка,
   кроме последней, оканчивается `,`, последняя — `.`.

По одной кодировке выведите другую.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

Одна из двух кодировок. В строках нет ведущих и концевых пробелов; `x` и `y`
разделены одним пробелом.

## Выходные данные

Другая кодировка.

## Проверка

Вывод сравнивается по токенам; лишние пробельные символы не важны.

## Примеры

### Пример 1

Ввод:

```
7
2 5
3 3
3 4
3 5
4 3
5 3
5 4
```

Вывод:

```
2 5
R,
B,
B,
R,
R,
T,
.
```

### Пример 2

Ввод:

```
2 5
R,
B,
B,
R,
R,
T,
.
```

Вывод:

```
7
2 5
3 3
3 4
3 5
4 3
5 3
5 4
```

## Решение

Описание *и есть* обход в ширину, поэтому оба направления — один и тот же
обход.

- **Список → описание**: отмечаем пиксели на сетке, находим старт, запускаем
  BFS; для каждого извлечённого пикселя пробуем четыре направления в порядке
  `R T L B`, и каждый чёрный ещё не виденный сосед отмечается, ставится в
  очередь и записывается.
- **Описание → список**: проигрываем обход. Очередь начинается со старта;
  строка `i` относится к `i`-му пикселю очереди, и каждая буква добавляет
  соседа в этом направлении. В конце в очереди все пиксели; сортируем их по
  `(x, y)`.

Какая кодировка дана: точкой оканчивается только описание, так что достаточно
посмотреть на последний токен. Чтение токенов, разделённых пробельными
символами, заодно справляется с пустой строкой `,` (это токен) и с концами
строк CRLF.

Пикселей не больше 100, всё работает за `O(100)`; сетка с рамкой из пустых
клеток (индексы `0..11`) избавляет от проверок границ.

Подводные камни:

- один пиксель описывается своими координатами и строкой из одной `.`;
- старт — самый нижний среди *самых левых* пикселей, а не самый нижний вообще;
- сосед записывается один раз — тем пикселем, который нашёл его первым.

## Оптимизированные решения

C++, Go и Rust кодируют пиксель одним индексом в плоской карте 12 × 12 с нулевой рамкой и используют очередь байтовых индексов. При кодировании пиксель снимается с карты сразу при добавлении в очередь, поэтому находится один раз. Декодирование отмечает пиксели и просматривает карту в порядке координат без отдельной сортировки. S = 10 — сторона изображения, P ≤ 100 — число чёрных пикселей. Go читает заголовок и последующие токены постепенно через фиксированный байтовый буфер и выводит десятичные цифры напрямую. Он обращается прямо к стандартным дескрипторам, повторяет прерванные вызовы и завершает частичные записи.

Принятые базовые реализации [1008_bfs.java](1008_bfs.java), [1008_bfs.py](1008_bfs.py) также закрывают быстрый набор: в сохранённом срезе сравнения они уже удовлетворяют рейтинговому критерию включения — топ 15% или первые десять мест одновременно по времени и памяти. Используются те же исходники без одинаковых копий. Звёздочка отмечает версию, которая пока не достигла целевого рейтинга своего языка.

## Особенности языков

Эти замечания относятся к базовым реализациям.

Во всех языках один и тот же BFS. Версия на Java при проигрывании описания
заполняет сетку и печатает её по столбцам — это сразу даёт отсортированный
порядок без сортировки.
