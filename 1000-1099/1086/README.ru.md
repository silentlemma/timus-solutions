# 1086. n-е простое число

[Timus 1086](https://acm.timus.ru/problem.aspx?space=1&num=1086) · сложность 107 · number_theory

Оригинальная задача — фольклор; третье командное соревнование школьников Свердловской области по программированию, 4 марта 2001 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Для каждого из `k` чисел `n` (`1 ≤ n ≤ 15000`) выведите `n`-е по счёту
простое число. 1 не является простым.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

`k` (`1 ≤ k ≤ 15000`), затем `k` строк с `n`.

## Выходные данные

`n`-е простое для каждого `n`, по одному в строке.

## Проверка

Вывод сравнивается по токенам; лишние пробельные символы не важны.

## Примеры

### Пример 1

Ввод:

```
4
3
2
5
7
```

Вывод:

```
5
3
11
17
```

## Решение

15000-е простое число — 163 841, поэтому одно решето Эратосфена до этого
числа даёт все простые, о которых могут спросить, а каждый запрос — это
индекс в списке. `O(L log log L)` на решето при `L = 163 842` и `O(1)` на
запрос.

Подводные камни:

- первое простое — 2, а не 1;
- граница решета должна захватывать само 15000-е простое; его можно один
  раз найти любым способом и вписать в программу;
- запросов может быть до 15000, поэтому простые вычисляются один раз, а
  не для каждого запроса.

Ответы сверены с простыми, найденными по одному пробным делением.

## Оптимизированные решения

Оптимизированное решение на Go просеивает только нечётные числа, отчего
решето вдвое меньше, хранит ровно 15000 простых в `uint32`, которого
хватает, ведь все они меньше 163 842, вместо растущего среза `int`, а
числа читает побайтово и печатает через `strconv` вместо `fmt`:
{1086_number_theory_optimized.go}.

Оптимизированное решение на Java просеивает только нечётные числа,
отчего решето вдвое меньше, держит массив ровно из 15000 простых вместо
163 842 ячеек, разбирает ввод из блоков по 8 КБ вместо `StreamTokenizer`
и печатает цифры через байтовый буфер на 8 КБ, а не собирает весь вывод
в `StringBuilder`: {1086_number_theory_optimized.java}.

Оптимизированное решение на Python просеивает только нечётные числа,
отчего `bytearray` вдвое меньше, хранит простые в `array` из 32-битных
беззнаковых целых, которых хватает, ведь все они меньше 163 842, вместо
списка целых Python, читает запросы построчно, а не разбивает весь ввод
сразу, и печатает ответы пачками по 1024:
{1086_number_theory_optimized.py}.

Оптимизированное решение на Rust просеивает только нечётные числа,
отчего решето вдвое меньше, хранит ровно 15000 простых в `u32`, которого
хватает, ведь все они меньше 163 842, в заранее зарезервированном
векторе вместо растущего `Vec<usize>` и пишет ответы через `BufWriter`,
а не создаёт строку на каждый ответ с последующим склеиванием:
{1086_number_theory_optimized.rs}.

Оптимизированная версия C++ сохраняет тот же алгоритм решета, но хранит только нечётные числа в упакованном битовом массиве (около 10 КБ). В отсортированном списке сохраняются младшие 16 бит каждого из 15000 простых чисел — всего 30 КБ. Все простые меньше трёх `2^16`; два граничных индекса, вычисляемые при построении списка, определяют, нужно ли прибавить ноль, одну или две величины `2^16` при ответе. Запрос остаётся константным, заранее вычисленной таблицы ответов нет. Общее время — `O(L log log L + k)`, память — `O(L + P)` для границы решета `L` и количества простых `P`. Обычная реализация с векторами сохраняется как базовая.

Accepted для соответствующих исходников: базовая версия 0.031 с / 212 КБ; эта версия 0.015 с / 148 КБ (посылка 11307512). Память уменьшилась на 30.19%; разница времени в один тик не используется как доказательство ускорения. По свежему рейтингу цель достигнута.

{1086_number_theory_optimized.cpp}.

## Особенности языков

- Python вычёркивает кратные присваиванием среза в `bytearray`.
- C++, Go, Java и Rust начинают вычёркивание с `p²`; C++ и Java считают
  его в 64 битах в базовой версии C++ и в Java, чтобы не опасаться переполнения.
