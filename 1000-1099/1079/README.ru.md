# 1079. Наибольший член последовательности Штерна до n

[Timus 1079](https://acm.timus.ru/problem.aspx?space=1&num=1079) · сложность 112 · dp

Автор оригинальной задачи — Emil Kelevedzhiev; турнир по информатике Зимнего математического фестиваля, Варна, 2001 год.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Последовательность задана так: `a₀ = 0`, `a₁ = 1`, `a₂ᵢ = aᵢ` и
`a₂ᵢ₊₁ = aᵢ + aᵢ₊₁` при `i ≥ 1`. Для каждого данного `n`
(`1 ≤ n ≤ 99 999`) выведите наибольшее из `a₀, a₁, …, aₙ`.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

До десяти строк с `n`, затем строка с 0.

## Выходные данные

Максимум для каждого `n`, по одному в строке.

## Проверка

Вывод сравнивается по токенам; лишние пробельные символы не важны.

## Примеры

### Пример 1

Ввод:

```
5
10
0
```

Вывод:

```
3
4
```

## Решение

Каждый член ссылается только на члены с меньшими номерами, поэтому один
проход от 2 до 99 999 заполняет всю таблицу, а бегущий максимум
`best[i] = max(best[i − 1], aᵢ)` сразу отвечает на все запросы. `O(N)`
на таблицу, `O(1)` на запрос.

Это двухатомная последовательность Штерна. Некоторые рекорды — числа Фибоначчи,
которые достигаются при целых `n = (2^k ± 1)/3`; наибольшее значение до
99 999 равно 2584, так что 32-битных целых хватает с запасом.

Подводные камни:

- запросы идут в любом порядке и заканчиваются нулём, который запросом не
  является;
- формула для нечётных номеров использует `aᵢ₊₁`, номер которого всё равно
  меньше `2i + 1`, так что порядок прохода правильный.

Ответы сверены с вычислением по определению рекурсией с запоминанием и
простым перебором для каждого запроса.

## Оптимизированные решения

Оптимизированное решение на C++ хранит члены только до номера 50 000,
потому что формула для номера до 99 999 не заглядывает дальше, а члены и
бегущие максимумы держит в 16-битных целых, которых достаточно, ведь ни
один член до 99 999 не превышает 2584: {1079_dp_optimized.cpp}.

Оптимизированное решение на Go хранит члены только до номера 50 000,
потому что формула для номера до 99 999 не заглядывает дальше, держит
члены и бегущие максимумы в `uint16`, которого достаточно, ведь ни один
член до 99 999 не превышает 2584, и читает запросы побайтово вместо
`fmt.Fscan`: {1079_dp_optimized.go}.

Оптимизированное решение на Java хранит члены только до номера 50 000,
потому что формула для номера до 99 999 не заглядывает дальше, держит
члены и бегущие максимумы в 16-битных массивах `char`, которых
достаточно, ведь ни один член до 99 999 не превышает 2584, и разбирает
запросы вручную из `BufferedInputStream` вместо `Scanner`:
{1079_dp_optimized.java}.

Оптимизированное решение на Python хранит члены только до номера 50 000,
потому что формула для номера до 99 999 не заглядывает дальше, а члены и
бегущие максимумы держит в объектах `array` из 16-битных целых вместо
списков целых Python; этого достаточно, ведь ни один член до 99 999 не
превышает 2584: {1079_dp_optimized.py}.

Оптимизированное решение на Rust хранит члены только до номера 50 000,
потому что формула для номера до 99 999 не заглядывает дальше, а члены и
бегущие максимумы держит в `u16` вместо `u32`; 16 бит достаточно, ведь
ни один член до 99 999 не превышает 2584: {1079_dp_optimized.rs}.
