# 1021. Пара из двух упорядоченных списков с заданной суммой

[Timus 1021](https://acm.timus.ru/problem.aspx?space=1&num=1021) · сложность 148 · two_pointers, hashing

Оригинальная задача — второе командное соревнование школьников Свердловской области по программированию, 7 октября 2000 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Даны два списка целых чисел: первый упорядочен по возрастанию, второй — по
убыванию (в каждом `1 ≤ N_i ≤ 50 000` чисел, каждое от -32768 до 32767).
Определите, можно ли выбрать по одному числу из каждого списка так, чтобы
их сумма была ровно 10000.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

Первый список: его размер, затем числа, по одному в строке. Затем второй
список в том же формате.

## Выходные данные

`YES`, если такая пара есть, иначе `NO`.

## Проверка

Вывод сравнивается по токенам; лишние пробельные символы не важны.

## Примеры

### Пример 1

Ввод:

```
3
-5
3
9998
3
10
7
2
```

Вывод:

```
YES
```

### Пример 2

Ввод:

```
3
1
2
3
3
9000
50
0
```

Вывод:

```
NO
```

## Решение

**Два указателя.** Ставим указатель `i` в начало возрастающего списка и `j`
в начало убывающего, так что `up[i]` — наименьшее оставшееся число первого
списка, а `down[j]` — наибольшее второго. Сравниваем `up[i] + down[j]` с
10000:

- равно — пара найдена;
- меньше — `up[i]` не входит ни в одну пару, ведь даже наибольшего
  оставшегося `down[j]` не хватает: двигаем `i`;
- больше — `down[j]` не входит ни в одну пару, ведь даже наименьшее
  оставшееся `up[i]` даёт перебор: двигаем `j`.

Когда указатель выходит за конец списка, пары нет. Каждый шаг отбрасывает
одно число: `O(N_1 + N_2)`.

**Хеширование.** Кладём `10000 - b` для каждого `b` второго списка в
множество и проверяем, есть ли в нём какое-нибудь число первого списка —
тоже линейно в среднем и не требует упорядоченности.

Подводные камни:

- второй список упорядочен в обратную сторону: идите по обоим спискам с
  начала;
- для суммы 10000 могут понадобиться крайние значения, например
  `32767 + (-22767)`.

## Оптимизированные решения

Оптимизированное решение на C++ разбирает числа вручную из буфера на
4 КБ, который пополняется через `fread`, вместо `scanf`. Оно хранит
только возрастающий список, в `int16_t`, куда помещается любое число от
-32768 до 32767, и двигает его указатель прямо во время чтения
убывающего списка, так что второй список не хранится вовсе:
{1021_two_pointers_optimized.cpp}.

Оптимизированное решение на Go разбирает числа побайтно из
`bufio.Reader` вместо `fmt.Fscan`. Оно хранит только возрастающий
список, в `int16`, куда помещается любое число от -32768 до 32767, и
двигает его указатель прямо во время чтения убывающего списка, так что
второй список не хранится вовсе: {1021_two_pointers_optimized.go}.

Оптимизированное решение на Java разбирает числа вручную из буфера на
4 КБ, который пополняется из `System.in`, вместо `StreamTokenizer`. Оно
хранит только возрастающий список, в `short`, куда помещается любое
число от -32768 до 32767, и двигает его указатель прямо во время чтения
убывающего списка, так что второй список не хранится вовсе:
{1021_two_pointers_optimized.java}.

Оптимизированное решение на Python полагается на то, что каждое число
стоит в своей строке, и преобразует строки по мере чтения, а не
разбивает весь ввод в список. Вместо множества оно отмечает числа
первого списка в `bytearray` из 65536 ячеек, по одной на каждое
возможное значение от -32768 до 32767. Для каждого `b` второго списка
оно сначала проверяет, что `10000 - b` попадает в этот диапазон, и
только тогда ищет его там: {1021_hashing_optimized.py}.

Оптимизированное решение на Rust разбирает числа вручную из буфера на
4 КБ, который пополняется со стандартного ввода, вместо чтения всего
ввода в `String`. Оно хранит только возрастающий список, в `i16`, куда
помещается любое число от -32768 до 32767, и двигает его указатель прямо
во время чтения убывающего списка, так что второй список не хранится
вовсе: {1021_two_pointers_optimized.rs}.
