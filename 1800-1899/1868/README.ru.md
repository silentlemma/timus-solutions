# 1868. Конкурс прогнозов

[Timus 1868](https://acm.timus.ru/problem.aspx?space=1&num=1868) · сложность 158 · implementation

Автор оригинальной задачи — Денис Дублённых; Открытый командный чемпионат УрФУ по программированию, 2011 год.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

На финале чемпионата мира первые четыре команды получают золото,
следующие четыре — серебро и следующие четыре — бронзу. Несколько
ветеранов сделали прогнозы вида «команда X получит медаль Y», и Вадик
платит по пять долларов каждому ветерану с наибольшим числом верных
предположений. По двенадцати призёрам в порядке мест и всем прогнозам
определите, сколько заплатит Вадик.

## Входные данные

Двенадцать названий команд с первого места по двенадцатое, затем n
(1 ≤ n ≤ 100) и n прогнозов. Прогноз начинается с числа предположений
kᵢ, за которым идут kᵢ строк «команда : медаль», где медаль — «gold»,
«silver» или «bronze». Ни один прогноз не даёт команде двух медалей и не
даёт медаль одного достоинства больше чем четырём командам. Названия —
от 1 до 30 латинских букв, подчёркиваний, точек и запятых. Каждое
название, число и предположение стоит на отдельной строке.

## Выходные данные

Сумма, которую платит Вадик, в долларах.

## Примеры

### Пример 1

Ввод:

```
North_A
North_B
North_C
North_D
East_A
East_B
East_C
East_D
West_A
West_B
West_C
West_D
3
3
North_A : gold
East_A : silver
West_A : bronze
4
North_B : gold
East_C : silver
West_D : bronze
Other : gold
3
North_C : silver
East_B : gold
Other : bronze
```

Вывод:

```
10
```

## Решение

В названиях нет пробелов, так что вход — поток слов: двенадцать
названий, затем на каждое предположение название, двоеточие и медаль.
Словарь из двенадцати названий в их медали (места 1–4 — золото, 5–8 —
серебро, 9–12 — бронза) говорит, верно ли предположение; команда,
которой в нём нет, ничего не выиграла. Считаем верные предположения
каждого ветерана и платим по пять долларов каждому, у кого их больше
всех. `O(n·k)` обращений к словарю.

В примере у каждого ветерана три верных предположения, так что
выигрывают все трое, и Вадик платит 15 долларов.

Подводные камни:

- медаль определяется местом: названия идут по порядку, первые четыре
  — золото и так далее;
- прогноз может называть команды, не получившие медали вовсе;
- регистр в названиях важен, и название может состоять из одних точек
  и запятых;
- если никто ничего не угадал, все ветераны делят первое место с нулём,
  и платить надо всем.

Суммы совпадают с независимой принятой реализацией на 150 случайных
конкурсах.

## Оптимизированные решения

`1868_implementation_optimized.java`. Сохраняются точное сопоставление призёров медалям, лучший результат прогнозов и число его повторов. ASCII-токены читаются через буфер 1024 байта без StringTokenizer на строку; имена и медали сравниваются полностью. Новый запуск: 0.078 с / 956 КБ, быстрее прежнего оптимизированного 0.109 с / 900 КБ, но с небольшим ростом памяти. Сохранённая простая Java-версия: 0.093 с / 1196 КБ. Экономия памяти относительно прежней оптимизированной ревизии не заявляется.

Accepted точного исходника Java 1.8 №11326969: 0.078 с / 956 КБ. Сохранённое сравнение актуального Java от 2026-11-20: место по времени 2/57, по памяти 9/57. При памяти меньше 1024 КБ строгий критерий учитывает только время.

- `1868_implementation_optimized.java`: 0.078 s / 956 KB; сохранённая учебная база `1868_implementation.java`: 0.093 s / 1196 KB; изменение времени -16.1%; изменение памяти -20.1%.

Оптимизированное решение на C++ хранит двенадцать названий в массивах
`char` фиксированного размера по 31 байту, ведь в названии не больше 30
символов, читает каждое предположение через `scanf` в буферы на 31 и
7 байт (в названии медали не больше 6 букв) и сравнивает его с
двенадцатью названиями через `strcmp` вместо `map` из `string`.
Наибольшее число верных предположений и количество ветеранов с ним
ведутся по ходу вместо `vector` всех счётов, и используется `stdio`
вместо `iostream`: {1868_implementation_optimized.cpp}.

Оптимизированное решение на Python читает ввод построчно, ведь каждое
название, число и предположение стоит на отдельной строке, а не
разбивает весь ввод на список слов; наибольшее число верных
предположений и количество ветеранов с ним ведутся по ходу вместо списка
всех счётов: {1868_implementation_optimized.py}.

Оптимизированное решение на Rust читает ввод построчно в одну и ту же
`String`, ведь каждое название, число и предположение стоит на отдельной
строке, а не читает весь ввод сразу; оно сравнивает каждое предположение
прямо с двенадцатью сохранёнными названиями вместо `HashMap` и ведёт
наибольшее число верных предположений и количество ветеранов с ним по
ходу вместо вектора всех счётов: {1868_implementation_optimized.rs}.

### Измеренный выигрыш

Каждая сохранённая оптимизированная версия имеет Accepted. Она проходит по первым десяти местам или топ 15% одновременно по времени и памяти, по топ 30% по обеим метрикам с улучшением места базы хотя бы по одной из них либо по сокращению времени или памяти минимум на 30% относительно базы на том же языке. Отрицательное сокращение означает рост расхода. Звёздочка относится к отдельной рейтинговой цели языка.

- `1868_implementation_optimized.cpp`: сокращение времени +0.00%;
  сокращение памяти +75.45%; база: `1868_implementation.cpp`.

- `1868_implementation_optimized.py`: сокращение времени -19.23%;
  сокращение памяти +42.20%; база: `1868_implementation.py`.

- `1868_implementation_optimized.rs`: сокращение времени +0.00%;
  сокращение памяти +60.45%; база: `1868_implementation.rs`.

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1868_implementation_parsing_optimized.py`. Названия медалей читаются в байтах; лучший результат и число победителей находятся одним проходом без повторных преобразований текста и обходов. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.
