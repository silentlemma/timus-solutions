# 1826. Минное поле

[Timus 1826](https://acm.timus.ru/problem.aspx?space=1&num=1826) · сложность 309 · greedy

Автор оригинальной задачи — Дмитрий Теряев; XII открытое личное первенство УрГУ, 19 марта 2011 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Разведгруппа из n человек переходит минное поле с одним миноискателем:
двое переходят вместе, затем один возвращается с миноискателем, и так
далее. У каждого своё время перехода, а пара движется со скоростью
более медленного. Найти наименьшее общее время перехода всей группы.

## Входные данные

n (2 ≤ n ≤ 100), затем n времён перехода — положительные целые не
больше 600.

## Выходные данные

Наименьшее общее время.

## Проверка

Тесты репозитория точно сравнивают токены вывода; пробельные разделители между ними несущественны.

## Примеры

### Пример 1

Ввод:

```
4
1
10
5
2
```

Вывод:

```
17
```

## Решение

Это задача о мосте и фонарике. Отсортируем времена a ≤ b ≤ … ≤ y ≤ z.
Пока ждут больше трёх человек, переводим двух самых медленных одним из
двух способов и берём более дешёвый:

- самый быстрый сопровождает каждого: z + a + y + a = 2a + y + z;
- переходят двое самых быстрых, a возвращается, двое самых медленных
  переходят вместе, b возвращается: b + a + z + b = a + 2b + z.

В обоих случаях двое самых быстрых снова на исходном берегу, а
оставшихся на два меньше. Трое переходят за a + b + c (a сопровождает
обоих), двое — за время более медленного. Обменный аргумент показывает,
что некоторый оптимальный план всегда переводит двух самых медленных
именно так. Алгоритм работает за `O(n log n)`, но реализация на Python —
за `O(n^2)`, поскольку каждый срез `times[:-2]` копирует оставшийся список.
Пиковая память во всех пяти реализациях — `O(n)`.

В примере (1, 2, 5, 10) пара стоит 1 + 2·2 + 10 = 15 против
2 + 5 + 10 = 17 при сопровождении, а последние двое — 2: итого 17.

Подводные камни:

- всегда сопровождать самым быстрым не оптимально: 1, 2, 5, 10 заняли
  бы 19;
- всегда объединять медленных тоже не оптимально, если второй по
  скорости медленный;
- выбор делается заново в каждом раунде;
- срезы списков Python копируют элементы: в тесте 07 при n = 100
  копируется 98 + 96 + … + 2 = 2450 элементов, поэтому сортировка
  не определяет асимптотику времени этой реализации.

Ответы совпадают с поиском Дейкстры по всем состояниям для групп до 7
человек и с независимой принятой реализацией на случайных группах.

## Оптимизированные решения

`1826_greedy_optimized.java`. Java сохраняет алгоритм и структуры данных, описанные для простой версии. Фиксированный байтовый буфер и FastInput заменяют Scanner с его регулярными выражениями и обработкой локали. Целые числа разбираются напрямую; строки при необходимости по-прежнему декодируются из UTF-8, десятичные токены явно преобразуются в числа. Предварительный просмотр хранит токен только при необходимости. Алгоритм вывода не меняется. Убираются накладные расходы универсального разбора; в таблице указана работа алгоритма, а чтение линейно по числу байтов с ограниченным буфером.

По сравнению с `1826_greedy.java`: время 0.109 s → 0.078 s; память 1764 KB → 516 KB.

Go и Rust сортируют времена в массивах фиксированного размера и на каждом шаге переводят двух самых медленных солдат. При двух самых быстрых временах a, b и двух самых медленных оставшихся y, z прибавляется z + min(2a+y, a+2b). Для двух солдат остаётся b, для трёх — a+b+c. Обе версии хранят входные времена в 16 битах. Go применяет пирамидальную сортировку на месте, Rust хранит сумму в 32 битах. Для ввода и десятичного вывода используются фиксированные байтовые буферы. Go обращается напрямую к дескрипторам ввода и вывода, Rust использует библиотеку времени исполнения C.

Принятые базовые реализации [1826_greedy.cpp](1826_greedy.cpp), [1826_greedy.java](1826_greedy.java), [1826_greedy.py](1826_greedy.py) также закрывают быстрый набор: в сохранённом срезе сравнения они уже удовлетворяют рейтинговому критерию включения — топ 15% или первые десять мест одновременно по времени и памяти. Используются те же исходники без одинаковых копий. Звёздочка отмечает версию, которая пока не достигла целевого рейтинга своего языка.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Учебные алгоритмы сохранены. Перепроверенные базовые версии используют собственные новые метрики и ID Accepted точного исходника; эти проверки не считаются оптимизациями.

`1826_greedy_optimized.java`: место по времени 1/28, по памяти 5/28 в этой сопоставимой выборке.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
