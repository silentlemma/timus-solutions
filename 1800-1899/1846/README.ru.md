# 1846. НОД 2010

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Мультимножество целых положительных чисел вначале пусто. Каждая
операция добавляет число или удаляет одну копию лежащего там числа.
После каждой операции вывести наибольший общий делитель всего
мультимножества; НОД пустого мультимножества объявлен равным 1.

## Входные данные

q (1 ≤ q ≤ 10⁵), затем q строк вида «+ x» или «- x», где
1 ≤ x ≤ 10⁹. Удаляются только имеющиеся числа.

## Выходные данные

НОД после каждой операции, по одному в строке.

## Примеры

### Пример 1

Ввод:

```
5
+ 8
+ 6
+ 8
- 8
- 8
```

Вывод:

```
8
2
2
2
6
```

## Решение

НОД нельзя «отменить», поэтому для удаления нужна структура. Дадим
каждому добавлению свой лист дерева отрезков над операциями и будем
хранить для каждого значения стек листьев, где оно лежит. Добавление x
записывает x в лист этой операции; удаление x опустошает верхний лист
его стека, записывая 0, что не меняет никакой НОД, ведь
НОД(a, 0) = a. Каждый внутренний узел хранит НОД детей, так что корень —
НОД мультимножества, а корень 0 означает пустое мультимножество:
выводим 1. Обновление листа пересчитывает его предков, и подъём можно
остановить на первом узле, значение которого не изменилось: выше тогда
ничего не меняется. `O(q log q log x)`.

В примере листья хранят 8, 6 и 8, так что НОД равен 2. Удаление двух
восьмёрок опустошает два листа и оставляет 6.

Подводные камни:

- пустое мультимножество даёт 1, а не 0;
- равные числа могут добавляться несколько раз и удаляться по одному;
- при половине секунды важны и ранняя остановка подъёма, и быстрое
  чтение; простое решение на Python работает на PyPy.

Ответы совпадают с независимой принятой реализацией на тридцати
случайных файлах до 10⁵ операций.

## Оптимизированные решения

Оптимизированное решение на C++ сначала читает все операции, сортирует и
убирает повторы среди их значений и даёт каждому различному значению
один лист со счётчиком его копий вместо листа на каждое добавление и
хеш-таблицы стеков листьев. Лист хранит x, пока счётчик положителен, и 0
иначе, так что дерево меняется, только когда значение появляется или
исчезает. Операция хранится одним знаковым `int`, +x или −x, что
помещается, ведь x ≤ 10⁹; лист значения находится двоичным поиском.
Числа разбираются вручную из буфера на 4 КБ, который пополняется через
`fread`: {1846_segment_tree_optimized.cpp}.

Оптимизированное решение на Go сначала читает все операции, сортирует и
убирает повторы среди их значений и даёт каждому различному значению
один лист со счётчиком его копий вместо листа на каждое добавление и
`map` срезов листьев. Лист хранит x, пока счётчик положителен, и 0
иначе, так что дерево меняется, только когда значение появляется или
исчезает. Операция хранится одним `int32`, +x или −x, что помещается,
ведь x ≤ 10⁹, а дерево и счётчики — срезы `int32`; лист значения
находится двоичным поиском. Числа разбираются вручную из читателя
`bufio` вместо разбиения ввода на слова:
{1846_segment_tree_optimized.go}.

Оптимизированное решение на Java сначала читает все операции, разбирая
их вручную из буфера на 64 КБ вместо `StreamTokenizer`. Оно нумерует
значения двоичным поиском в отсортированной копии и хранит листья
каждого значения связными стеками в двух массивах `int`, верхний лист
каждого значения и лист под каждым листом, вместо `HashMap` из
`ArrayDeque<Integer>`, так что ни одно число не упаковывается в объект;
у каждого добавления по-прежнему свой лист:
{1846_segment_tree_optimized.java}.

Оптимизированное решение на Python читает ввод целиком и делит его на строки,
убирая обращение к буферизованному потоку на каждой операции. У каждого
различного значения один лист и счётчик кратности, поэтому повторные копии
не меняют дерево. Дерево и счётчики хранятся в списках целых вместо
`array("I")`, чтобы не преобразовывать ячейки массива при каждом обращении
во внутреннем цикле обновления. Значение ищется в словаре один раз; ответы
по-прежнему выводятся пачками по 1024. Используется PyPy 3.10: прежняя
построчная версия под CPython превысила лимит времени:
{1846_segment_tree_optimized.py}.

Оптимизированное решение на Rust сначала читает все операции и
освобождает текст ввода, сортирует и убирает повторы среди значений и
даёт каждому различному значению один лист со счётчиком его копий вместо
листа на каждое добавление и `HashMap` стеков `Vec`. Лист хранит x, пока
счётчик положителен, и 0 иначе, так что дерево меняется, только когда
значение появляется или исчезает. Операция хранится одним `i32`,
+x или −x, что помещается, ведь x ≤ 10⁹, а дерево и счётчики — `u32`;
ответы выводятся через `BufWriter`, а не собираются в `String`:
{1846_segment_tree_optimized.rs}.
