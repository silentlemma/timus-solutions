# 1864. Посиделки у Дена

[Timus 1864](https://acm.timus.ru/problem.aspx?space=1&num=1864) · сложность 177 · math

Оригинальная задача — фольклор (подготовка — Даниил Айзенштейн); Открытый командный чемпионат УрФУ по программированию, 2011 год.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

К Дену пришли n друзей; i-й купил aᵢ литров сока, и все, включая Дена,
выпили поровну. Затем Ден платит 100 рублей за сок, выпитый не теми,
кто его покупал, справедливо разделив их между друзьями, купившими
больше, чем выпили. Сколько рублей получит каждый друг с округлением
вниз?

## Входные данные

n (2 ≤ n ≤ 100), затем a₁, …, aₙ (0 ≤ aᵢ ≤ 100) с положительной суммой.

## Выходные данные

Рубли каждого друга с округлением вниз.

## Проверка

Тесты репозитория точно сравнивают токены вывода; пробельные разделители между ними несущественны.

## Примеры

### Пример 1

Ввод:

```
3
10 10 10
```

Вывод:

```
33 33 33
```

### Пример 2

Ввод:

```
2
10 0
```

Вывод:

```
100 0
```

## Решение

Если всего S литров, каждый из n + 1 человек выпивает S/(n + 1), так что
друг i купил для других aᵢ − S/(n + 1) литров, если это положительно, и
ничего иначе. Деньги делятся пропорционально этим количествам. Умножив
все на n + 1, остаёмся в целых числах: eᵢ = max(0, aᵢ(n + 1) − S), и
друг i получает ⌊100·eᵢ / Σ e⌋. Сумма никогда не равна 0: друзья вместе
купили S, а выпили только nS/(n + 1). `O(n)`; в Python — `O(n²)`.

В первом примере каждый выпил 7,5 литра, а каждый друг оплатил Дену
2,5 литра, так что деньги делятся на троих: по 33 после округления.

Подводные камни:

- Ден тоже пьёт, поэтому доля — S/(n + 1), а не S/n;
- друзья, купившие меньше, чем выпили, не получают ничего;
- точные целые числа снимают сомнения насчёт округления вниз.

Доли совпадают с независимой принятой реализацией на двухстах
случайных посиделках.

## Оптимизированные решения

`1864_math_optimized.java`. Сохраняется точная нормализация вкладов: c_i=max(0,a_i(N+1)−sum(a)), доля_i=floor(100c_i/sum(c)). Целые читаются напрямую. Процент лежит в 0..100: одна, две или три цифры с разделителем кодируются максимум четырьмя байтами на человека и выводятся одним блоком. Вклады, деление вниз и сумма прежние; проценты не округляются ради суммы 100. O(N) времени и O(N) памяти вкладов/вывода. Учебная версия сохранена.

Accepted точного исходника Java 1.8 №11327834: 0.093 с / 368 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 7/59, память 1/59. При памяти меньше 1024 КБ строгий допуск учитывает только время: первые десять мест или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка: первого места по обеим метрикам. Прежний документированный оптимизированный запуск №11307325: 0.125 с / 520 КБ; это отдельная историческая пара, не текущий замер данного исходника. Учебные версии сохранены без изменений.

- `1864_math_optimized.java`: 0.093 s / 368 KB; сохранённая учебная база `1864_math.java`: 0.125 s / 1720 KB.

`1864_math_optimized.py`. Сохраняются точные масштабированные переплаты credit[i]=max(0,(N+1)*bought[i]-total) и floor(100*credit[i]/sum(credits)). По условию total положителен; до обрезания отрицательных значений сумма credit равна total, поэтому знаменатель после обрезания строго положителен. Целая арифметика исключает ошибки округления. Время O(N) при однократном вычислении общего знаменателя. Базовый генератор пересчитывал sum(over) для каждого друга за O(N²); сумма сохраняется один раз. Покупки, переплаты и склеенный вывод по-прежнему занимают O(N) памяти. Самостоятельная программа для судьи явно сбрасывает stdout перед os._exit(0), пропуская обычное завершение интерпретатора. Выигрыш памяти подтверждён её собственным Accepted. Сама смена способа завершения не улучшает асимптотику, а её эффект в среде выполнения не гарантируется на других платформах. Простая версия сохранена без изменений.

По сравнению с `1864_math.py`: время 0.093 s → 0.14 s; память 412 KB → 212 KB.

`1864_math_optimized.rs`. Сохраняются точные масштабированные переплаты credit[i]=max(0,(N+1)*bought[i]-total) и floor(100*credit[i]/sum(credits)). По условию total положителен; до обрезания отрицательных значений сумма credit равна total, поэтому знаменатель после обрезания строго положителен. Целая арифметика исключает ошибки округления. Время O(N) при однократном вычислении общего знаменателя. Один фиксированный массив100 значений i64 повторно используется для покупок и переплат вместо отдельных векторов и строк ответа. Явная память массива800байт плюс постоянное состояние; при N<=100,bought<=100 произведения безопасны. Rust-версия читает и пишет через среду выполнения C, без сохранения декодированной входной String и построения форматированной строки ответа. Простой исходник с Accepted сохранён.

По сравнению с `1864_math.rs`: время 0.031 s → 0.046 s; память 236 KB → 48 KB.

Оптимизированное решение на C++ считает те же доли, но хранит покупки и
излишки в двух массивах фиксированного размера на 100 чисел, чего
хватает, так как `n ≤ 100`, вместо двух векторов в куче:
{1864_math_optimized.cpp}.

Отрицательное накопление поддерживает минимальное знаковое число и устраняет выбор знака либо вызов читателя на каждой цифре; EOF и необязательные знаки сохранены.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Приведённые ниже места относятся к новым версиям; прежние исходники сохраняют собственные исторические метрики Accepted.

`1864_math_optimized.py`: место по времени 18/20, по памяти 1/20 в этой сопоставимой выборке.

`1864_math_optimized.rs`: сопоставимых чужих результатов недостаточно для рейтингового вывода; допуск основан на измеренном улучшении относительно простой версии.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
