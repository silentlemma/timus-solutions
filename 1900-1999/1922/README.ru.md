# 1922. Команды, запрещающие любое одиночное добавление

[Timus 1922](https://acm.timus.ru/problem.aspx?space=1&num=1922) · difficulty 322 · sorting

Автор оригинальной задачи — Григорий Назаров; Уральская региональная командная олимпиада по программированию 2012.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Есть n участников. Участник i согласен на команду общей численности
не меньше aᵢ, включая самого участника. Непустая команда эффективна,
если все её участники согласны с размером. Эффективная команда сплочённая,
если добавление любого одного постороннего делает её неэффективной.
Эффективная команда из всех участников также сплочённая.
Нужно перечислить все такие команды. Пустая команда не учитывается.
Лимиты: 1 секунда, 64 МБ.

## Входные данные

В первой строке n, 1≤n≤1000. В следующих n строках aᵢ, 1≤aᵢ≤1000.
Порог может превышать n. Исходные номера участников от 1 до n.

## Выходные данные

Вывести число k команд. Затем для каждой из k команд в отдельной строке
указать размер и исходные номера участников. Порядок команд и номеров
произвольный. Если команд нет, вывести `0` без описаний.

## Проверка

Специальная проверка контролирует непустоту, различные допустимые номера,
эффективность, невозможность каждого одиночного добавления, отсутствие
повторных команд и полноту списка. Порядок команд и их участников
не важен; единственного канонического вывода нет.

## Примеры

```
5
1
3
3
6
6
```

```
2
1 1
3 2 1 3
```

## Решение

Пусть эффективная команда S имеет размер s. Для каждого участника
внутри aᵢ≤s, поэтому увеличение размера до s+1 никому внутри не мешает.
Добавление постороннего j удаётся тогда и только тогда, когда aⱼ≤s+1.
Сплочённость равносильна тому, что у всех посторонних порог больше s+1.

Значит, каждый участник с aᵢ≤s обязательно входит в S. Порог s+1
невозможен вообще: внутри нарушается эффективность, снаружи получается
допустимое добавление. Поэтому для каждого размера существует не более
одной сплочённой команды: все участники с порогом не больше s, если
их ровно s и никто не имеет порога s+1.

Сортируем пары (порог, исходный номер). Для каждого s=1..n проверяем:

```text
максимальный порог среди первых s пар ≤ s;
и либо s=n, либо следующий порог > s+1.
```

При выполнении условий выводим первые s номеров. Первое условие
гарантирует эффективность, второе запрещает всех посторонних.
Обратно, доказанное свойство вынуждает любую сплочённую команду быть
таким префиксом, поэтому нет пропусков и повторов. Равные пороги
нельзя разделить допустимой границей, их порядок не создаёт новых команд.

При s=n остаётся проверить эффективность. Полная команда не всегда
эффективна: некоторые пороги могут превышать n.

Речь идёт об одном добавлении, а не о максимальности среди всех
эффективных надмножеств. Для порогов 1,3,3 подходят и одиночная команда,
и все трое: по одному участники с порогом 3 присоединиться не могут,
хотя вместе присоединились бы.

Пусть R — суммарное число выводимых номеров. Время O(n log n+R),
память O(n+R) при хранении ответов и буферизации. Вывод бывает
квадратичным: 2,2,4,4,…,1000,1000 дают 500 команд и 250 500 номеров.
Их перечисление неизбежно требует соответствующего времени.

Порог снаружи должен быть строго больше s+1, а не просто s.
Внутри равенство s допустимо. Не учитывайте пустую команду, допускайте
нулевой ответ и сохраняйте нумерацию с единицы. Равные пороги относятся
к разным участникам, но не создают альтернативных команд одного размера.
Не подменяйте одиночное добавление общей максимальностью и не забывайте R.

## Оптимизированные решения

`1922_sorting_optimized.java`. Надёжные команды по-прежнему задаются подходящими отсортированными префиксами: порог последнего участника не больше size, порог следующего постороннего, если он есть, строго больше size+1. Порог и исходный ID упакованы в long, сохраняются лишь длины подходящих префиксов. Участники выводятся из порядка сортировки при необходимости, без копий всех префиксов и всего ответа. При Z выведенных ID и стоимости сортировки S(N) время O(N+S(N)+Z), обычно O(N log N+Z), память O(N) даже при квадратичном Z. При отсутствии команд выводится только ноль. Равные пороги упорядочены по ID; любой порядок команд и участников допустим.

По сравнению с `1922_sorting.java`: время 0.109 s → 0.125 s; память 9 504 KB → 512 KB.

Версии C++, Go и Rust упаковывают порог и исходный номер в одно целое число. Номер занимает младшие десять бит, поэтому сортировка этих чисел упорядочивает участников прежде всего по порогу. Проверка границы остаётся прежней. Храним только размеры надёжных команд, а затем выводим нужные префиксы отсортированного массива. Если выводится R номеров, время O(n log n + R), память O(n).

Обновлённая версия C++ сохраняет упакованную сортировку и ту же проверку подходящих префиксов, используя буферы ввода и вывода по 16 КБ. Accepted точного исходника: 0.015 с / 152 КБ; учебная база: 0.015 с / 1452 КБ. Рейтинг C++ проверен по сохранённому срезу от 20 ноября 2026 года.

Принятые базовые реализации [1922_sorting.java](1922_sorting.java), [1922_sorting.py](1922_sorting.py) также закрывают быстрый набор: в сохранённом срезе сравнения они уже удовлетворяют рейтинговому критерию включения — топ 15% или первые десять мест одновременно по времени и памяти. Используются те же исходники без одинаковых копий. Звёздочка отмечает версию, которая пока не достигла целевого рейтинга своего языка.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1922_sorting_optimized.py`. Хранится и сортируется только надёжный префикс команд. Остальные записи читаются поточно и сразу обновляют ответ; правило упорядочивания сохранено. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.

Accepted #11328776 (Python 3.12 x64): **0.078 s / 1788 KB**. Архивное сравнение: `1922_sorting.py` (Python 3.12 x64) — 0.093 s / 7584 KB (#11325598).

## Особенности языков

Предыдущие добавления сравнивались по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Учебные алгоритмы сохранены. Перепроверенные базовые версии используют собственные новые метрики и ID Accepted точного исходника; эти проверки не считаются оптимизациями.

`1922_sorting_optimized.java`: место по времени 4/18, по памяти 1/18 в этой сопоставимой выборке.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
