# 2063. Одинаковые цвета вслепую

[Timus 2063](https://acm.timus.ru/problem.aspx?space=1&num=2063) · сложность 432 · constructive

Автор оригинальной задачи — Алексей Данилюк; Уральская региональная командная олимпиада по программированию 2015.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

В ряд лежат n шариков, чёрных и белых, в неизвестном порядке. Запрос
`? v u` меняет местами шарики на позициях v и u, если на v чёрный, а на
u белый, и ничего не делает иначе; программе не сообщают, что
произошло. После любого числа запросов она делает одно утверждение
`! v u`: две позиции, где теперь лежат шарики одного цвета.

В одном тесте несколько игр, в i-й из них n = i + 1. Во всех тестах,
кроме первого, 99 игр, n = 2, …, 100, и нужно выиграть хотя бы 80 из
них; тесты зафиксированы заранее и не подстраиваются под программу.
Первый тест — пример, в нём проверяется только формат. В одном тесте
можно вывести не больше 500 000 строк. Ограничения: 1 секунда и 64 МБ.

## Входные данные

Число игр m (99 во всех тестах, кроме первого), затем начальные ряды в
закодированном виде, который программа не должна пытаться прочитать.

## Выходные данные

m описаний игр: каждое — строки `? v u`, за которыми одна строка
`! v u`, где 1 ≤ v, u ≤ n и v ≠ u.

## Проверка

Проверяющая программа разыгрывает каждую игру. При 99 играх не меньше
80 утверждений должны быть верными; в примере проверяется только формат.

## Примеры

### Пример 1

Ввод:

```
2
01
101
```

Вывод:

```
? 1 2
? 2 1
? 1 2
! 2 1
? 1 2
? 3 1
! 1 2
```

## Решение

Отсортируем шарики вслепую. Запрос к соседям `? i i+1` сдвигает белый
шарик влево за чёрный, поэтому запросы сортировки пузырьком — для
каждого конца от n − 1 до 1 пары (1, 2), (2, 3), …, (end, end + 1) —
ставят все белые шарики перед всеми чёрными при любом начальном ряде.
На игру нужно n (n − 1) / 2 запросов, всего 166 650 запросов для
n = 2, …, 100. Вместе с 99 утверждениями получается 166 749 строк,
что укладывается в ограничение.

Теперь ряд — несколько белых шариков, за которыми несколько чёрных.
Соседи (j, j + 1) различаются только на единственной границе цветов, а
если ряд одноцветный, границы нет вовсе. Утверждение о соседней паре,
выбранной равновероятно случайно, проигрывает с вероятностью не больше
1 / (n − 1) для любого фиксированного ряда. При независимом равномерном
выборе пар в 99 играх ожидаемое число
проигрышей не больше 1/1 + 1/2 + … + 1/99 ≈ 5.2, а 20 и более
проигрышей случаются с вероятностью не больше примерно 2.6·10⁻⁹.

Ловушка — всегда выбирать пару (1, 2): в тесте gen9, где в каждом ряду
один белый шарик стоит первым, это проигрывает все игры. Постоянная пара
(n − 1, n) аналогично проваливает тест gen10. Программы меняют пару с
помощью генератора splitmix64, начальное значение которого — хеш FNV-1a
от всего входа; закодированные ряды не расшифровываются. Для фиксированного
входа результат детерминирован. Такое начальное значение не обеспечивает
независимый равномерный выбор, поэтому оценка вероятности выше относится
к идеальной случайной модели и не является гарантией для этих программ.

В тесте 01 проверяется только формат, но команда всё равно должна быть
ровно `?` или `!`; ошибочная команда `?!` должна отклоняться.

Пример лишь показывает формат: в первой игре утверждение (2, 1) неверно,
во второй верно.

## Оптимизированные решения

`2063_constructive_sorting.py`. Python тоже получает сеть нечётно-чётного слияния Бэтчера с дополнением, рядом с обеими пузырьковыми версиями. Компараторы с правым концом в виртуальном чёрном дополнении пропускаются; реальный префикс всё равно точно сортируется. Полный FNV-хеш исходных байтов и заявления соседей splitmix64 прежние, значит исход каждой фиксированной игры тот же; независимая случайность и гарантированная победа на игру не заявляются. Чтение блоками 4096 байт, вывод через bytearray со сбросом при пороге 4096 вместо сохранения списков запросов для каждого размера. Для I байтов и размеров nᵢ<=100 работа O(I+Σ nᵢ log² nᵢ), дополнительная память O(B+log n_max), B=4096; ширина десятичного вывода ограничена этими границами. Старые пузырьковые исходники и их метрики сохранены.

Компараторы с правым концом в виртуальном чёрном дополнении пропускаются; реальный префикс сортируется так же. Сохраняются все исходные байты FNV-seed и прежний беззнаковый выбор соседей splitmix64, поэтому исход каждой фиксированной игры тот же. Вероятностное ограничение прежнее, детерминированной гарантии победы на игру нет. Ввод хешируется блоками 1024 байта, команды идут через буфер 16384 байта. `2063_constructive_sorting.cpp`. C++ теперь выдаёт команды прежней сети Бэтчера через фиксированный буфер 16 КиБ. Ввод читается блоками по 16 КиБ; каждый исходный байт обновляет тот же FNV-1a seed, разбирается лишь начальное число игр. Splitmix64, порядок компараторов и заявления о соседях идентичны при одинаковых байтах ввода. Полный ввод и растущий вывод больше не хранятся; исходная вероятностная стратегия с seed из ввода не меняется и независимая случайность не заявляется. Для I байтов и размеров nᵢ время O(I+Σ nᵢ log² nᵢ), дополнительная память O(log n_max) на рекурсию и фиксированные буферы; вывод потоковый. Учебные пузырьковые версии сохранены. Индексы в этой задаче не больше 100, поэтому вывод компаратора содержит ограниченное число десятичных цифр.

Accepted точного исходника №11326647: 0.015 s / 124 KB. Сохранённая выборка актуальных компиляторов C/C++ от 2026-11-20: место по времени 1/56, по памяти 1/56.

`2063_constructive_optimized.java`. Сохраняются прежняя вероятностная стратегия и воспроизводимое зерно от ввода. Все B байт потоково проходят то же обновление FNV-1a, разбирается только начальное число игр, расстановки не декодируются. Splitmix64 и полная пузырьковая сеть сравнений прежние, поэтому одинаковые входные байты дают те же заявления о соседней паре. После сортировки плохая соседняя граница не больше одна, но заявление может проиграть: гарантии каждого раунда нет. Для99 игр судья требует хотя бы80 успехов. При размерах2..100 выводятся166650 запросов и99 заявлений, меньше500000 строк. Время O(B+Σ nᵢ²), память O(1) фиксированных буферов вместо копий всего ввода и растущего построителя ответа.

По сравнению с `2063_constructive.java`: время 0.14 s → 0.156 s; память 9 992 KB → 580 KB.

`2063_constructive_optimized.py`. Сохраняются исходная пузырьковая сеть команд, точный FNV-1a по всем сырым байтам и тот же выбор splitmix64 на игру. Хеширование идёт блоками 4096 байт, разбирается только число игр, кодированные расклады не декодируются. Хранятся только байтовые соседние запросы одной игры, команды выводятся ограниченным буфером вместо списка всех строк. При m играх вывод требует O(m³ log(m+2)), хеширование O(I), память O(B+m log(m+2)); последовательность запросов/заявлений и победы на фиксированном входе прежние. Ограничения детерминированного seed сохраняются, независимая случайность не заявляется.

По сравнению с `2063_constructive.py`: время 0.125 s → 0.187 s; память 8008 KB → 2 776 KB.

C++, Go и Rust заменяют пузырёк [сетью слияния чётных и нечётных подпоследовательностей Бэтчера](https://doi.org/10.1145/1468075.1468121). Дополняем до степени двойки виртуальными чёрными шарами и пропускаем сравнения с виртуальным правым концом. Каждый компаратор направлен от меньшего индекса к большему, поэтому виртуальный чёрный шар не меняется: сравнение реального значения с правым чёрным заполнением ничего не делает. Реальная часть сортируется как в полной сети. Рекурсивно сливаются чётные и нечётные подпоследовательности, затем сравниваются промежуточные соседние пары. Команд на игру O(n log² n) вместо O(n²). FNV-seed по всем исходным байтам входа и один выбор splitmix64 на игру сохранены. Обе сети оставляют одинаковый отсортированный ряд и одинаковое заявление, поэтому результат на фиксированном входе тот же. Независимость случайных выборов из хеша входа по-прежнему не следует. Go хеширует вход блоками и форматирует команды в фиксированный буфер без выделения строк на команду; C++ выдаёт ту же сеть потоково, как описано выше; Rust сохраняет уменьшенный текст команд. Простые пузырьки сохранены; для Java и Python ниже описаны отдельные компактные версии.

Принятая версия Rust 1.75 x64 заняла 0.046 с при 0.031 с у базовой и использовала 1 124 KB при 3208 KB у базовой.

Прежние базовые файлы Java и Python сохранены как учебные. У отдельных новых версий ниже есть собственные строки Accepted; одинаковых копий нет.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Учебные алгоритмы сохранены. Перепроверенные базовые версии используют собственные новые метрики и ID Accepted точного исходника; эти проверки не считаются оптимизациями.

`2063_constructive_optimized.py`: место по времени 3/46, по памяти 22/46 в этой сопоставимой выборке.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
