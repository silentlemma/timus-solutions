# 2033. Выбор модели по частоте и минимальной цене

[Timus 2033](https://acm.timus.ru/problem.aspx?space=1&num=2033) · сложность 104 · hashing

Автор оригинальной задачи — Илья Кучумов; Уральская региональная командная олимпиада по программированию 2014.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Даны ровно шесть записей о покупках: имя человека, модель устройства и цена.
Нужно выбрать модель с наибольшим числом записей. При равенстве частот
предпочитается модель с наименьшей из зафиксированных для неё цен.
При равенстве обоих критериев допустима любая из лучших моделей.
Одинаковые имена людей не объединяют записи: каждая учитывается отдельно.

Имя содержит 1–20 строчных латинских букв, модель — 1–20 строчных латинских
букв или цифр. Цена — целое от 1 до `1000000`. Лимиты: 1 секунда, 64 МБ.

## Входные данные

Ровно шесть описаний по три строки: имя, модель, цена. Количества записей
в начале входа нет.

## Выходные данные

Одно название оптимальной модели. Строка модели сохраняется вместе с
ведущими нулями.

## Проверка

Проверяющая программа принимает любую модель с наибольшим числом записей
и среди них с наименьшей ценой.

## Примеры

```

13000

kurtka
20000

nexus4

```

```
nexus4
```

## Решение

В хеш-таблице по строке модели храним число появлений и минимальную цену.
Имя читаем, но в ключ не включаем. Новую запись модели создаём с нулевой
частотой и ценой текущей покупки; затем увеличиваем частоту и обновляем минимум.

Перебираем модели, выбирая большую частоту, при её равенстве — меньшую цену.
При полной ничьей реализации выбирают лексикографически меньшее название
для определённости; по условию все полностью равные модели допустимы.

После каждого префикса входа поля таблицы равны числу записей модели и
минимуму её цен в этом префиксе. Инициализация, прибавление единицы и
взятие минимума сохраняют инвариант. После шести записей оценки точны.
При переборе текущий ответ является лучшим среди уже просмотренных
моделей; сравнение двух критериев сохраняет это свойство, поэтому итог
глобально оптимален.

В примере `nexus4` встречается три раза, минимум — 12000; `htc` два раза,
минимум — 9500; `kurtka` один раз за 20000. Частота важнее цены,
поэтому побеждает `nexus4`, хотя менее частая модель дешевле.

Для `k` записей ожидаемое время хеширования `O(k)`, память `O(k)`,
при длине слова до 20. Здесь `k=6` фиксировано, поэтому фактические
время и память ограничены константами. Более шести записей не предполагается.

Подводные камни:

- Считать нужно записи, а не различные имена.
- Цена модели — минимум, а не сумма, среднее, последнее или максимум.
- Частота сравнивается раньше цены.
- Первую цену надо взять из записи, а не оставить нулём по умолчанию.
- Цифровое название остаётся строкой с сохранением ведущих нулей.

## Оптимизированные решения

`2033_hashing_optimized.py`. Сохраняется группировка шести записей по модели: максимум частоты, затем минимум наблюдаемой цены. Токены сразу поступают в словарь без кортежей записей и декодирования ASCII-имён моделей. Байтовый лексикографический порядок сохраняет прежний выбор при равенстве, хотя принимается любая равнооптимальная модель. Токены входа остаются: ожидаемое время и память O(I) для длины входа I, записей всего шесть. В строке Accepted указаны фактическая среда судьи и парные время/память. Вывод сбрасывается до os._exit(0), пропускающего завершение интерпретатора; измеренный выигрыш памяти относится к этой среде и не означает асимптотического ускорения.

По сравнению с `2033_hashing.py`: время 0.109 s → 0.125 s; память 452 KB → 228 KB.

`2033_implementation.java`. Группировка хешированием заменена прямым просмотром не более шести строк моделей в фиксированных массивах. Считается каждая покупка, даже при повторении имени человека, сохраняется минимум цены модели. Строки моделей, включая ведущие нули, не меняются; лексикографический порядок используется лишь как допустимая развязка равенства количества и цены. При шести записях суммарная работа с символами O(L), память ограничена шестью именами моделей, без объектов Record и элементов HashMap. Публичное имя implementation отражает отсутствие хеширования; принятые байты и исходная учебная hashing-версия сохранены.

По сравнению с `2033_hashing.java`: время 0.125 s → 0.109 s; память 628 KB → 572 KB.

Оптимизированное решение на C++ обходится без хеш-таблицы: записей всего
шесть, поэтому каждая сравнивается со всеми шестью, считая записи той же
модели и беря их наименьшую цену, всего 36 сравнений, а лучшая запись
выбирается с тем же правилом при равенстве. Названия читаются через
`scanf` в массивы фиксированной длины по 21 байту, которых хватает на
20 символов и завершающий ноль, вместо `std::string` и `iostream`:
{2033_bruteforce.cpp}.

Оптимизированное решение на Rust обходится без хеш-таблицы: записей
всего шесть, поэтому каждая сравнивается со всеми шестью, считая записи
той же модели и беря их наименьшую цену, всего 36 сравнений, а лучшая
запись выбирается с тем же правилом при равенстве. Шесть моделей
остаются срезами входного текста в массиве фиксированной длины, а не
копиями в `HashMap`: {2033_bruteforce.rs}.

### Измеренный выигрыш

Каждая оптимизированная версия имеет Accepted и проходит рейтинговый критерий
либо критерий сокращения ресурса.
Базовые исходники сохранены. Отрицательное сокращение означает рост
расхода. Звёздочка относится только к рейтинговой цели.

- `2033_bruteforce.cpp`: сокращение времени +0.00%; сокращение памяти
  +67.71%; база: `2033_hashing.cpp`.

- `2033_bruteforce.rs`: сокращение времени +0.00%; сокращение памяти
  +47.71%; база: `2033_hashing.rs`.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Приведённые ниже места относятся к новым версиям; прежние исходники сохраняют собственные исторические метрики Accepted.

`2033_implementation.java`: место по времени 24/207, по памяти 32/207 в этой сопоставимой выборке.

`2033_hashing_optimized.py`: место по времени 49/61, по памяти 2/61 в этой сопоставимой выборке.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
