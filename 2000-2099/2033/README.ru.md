# 2033. Выбор модели по частоте и минимальной цене

[Timus 2033](https://acm.timus.ru/problem.aspx?space=1&num=2033) · сложность 104 · hashing

Автор оригинальной задачи — Илья Кучумов; Уральская региональная командная олимпиада по программированию 2014.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Даны ровно шесть записей о покупках: имя человека, модель устройства и цена.
Нужно выбрать модель с наибольшим числом записей. При равенстве частот
предпочитается модель с наименьшей из зафиксированных для неё цен.
При равенстве обоих критериев допустима любая из лучших моделей.
Одинаковые имена людей не объединяют записи: каждая учитывается отдельно.

Имя содержит 1–20 строчных латинских букв, модель — 1–20 строчных латинских
букв или цифр. Цена — целое от 1 до `1000000`. Лимиты: 1 секунда, 64 МБ.

## Входные данные

Ровно шесть описаний по три строки: имя, модель, цена. Количества записей
в начале входа нет.

## Выходные данные

Одно название оптимальной модели. Строка модели сохраняется вместе с
ведущими нулями.

## Проверка

Проверяющая программа принимает любую модель с наибольшим числом записей
и среди них с наименьшей ценой.


## Решение

В хеш-таблице по строке модели храним число появлений и минимальную цену.
Имя читаем, но в ключ не включаем. Новую запись модели создаём с нулевой
частотой и ценой текущей покупки; затем увеличиваем частоту и обновляем минимум.

Перебираем модели, выбирая большую частоту, при её равенстве — меньшую цену.
При полной ничьей реализации выбирают лексикографически меньшее название
для определённости; по условию все полностью равные модели допустимы.

После каждого префикса входа поля таблицы равны числу записей модели и
минимуму её цен в этом префиксе. Инициализация, прибавление единицы и
взятие минимума сохраняют инвариант. После шести записей оценки точны.
При переборе текущий ответ является лучшим среди уже просмотренных
моделей; сравнение двух критериев сохраняет это свойство, поэтому итог
глобально оптимален.

В примере `nexus4` встречается три раза, минимум — 12000; `htc` два раза,
минимум — 9500; `kurtka` один раз за 20000. Частота важнее цены,
поэтому побеждает `nexus4`, хотя менее частая модель дешевле.

Для `k` записей ожидаемое время хеширования `O(k)`, память `O(k)`,
при длине слова до 20. Здесь `k=6` фиксировано, поэтому фактические
время и память ограничены константами. Более шести записей не предполагается.

Подводные камни:

- Считать нужно записи, а не различные имена.
- Цена модели — минимум, а не сумма, среднее, последнее или максимум.
- Частота сравнивается раньше цены.
- Первую цену надо взять из записи, а не оставить нулём по умолчанию.
- Цифровое название остаётся строкой с сохранением ведущих нулей.

## Особенности языков

C++ использует `unordered_map`, Go — `map`, Rust и Java — `HashMap`,
Python — `dict`. Значение Go-таблицы извлекается копированием,
изменяется и записывается обратно. Rust и остальные языки инициализируют
минимум первой ценой. Частота не больше шести, цены помещаются в обычное
знаковое целое. Java читает заданные три строки, остальные реализации
разбирают пробельные токены.
