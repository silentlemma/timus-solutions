# 2021. Как отложить очевидную победу

[Timus 2021](https://acm.timus.ru/problem.aspx?space=1&num=2021) · сложность 462 · sorting

Автор оригинальной задачи — Олег Долгоруков; NEERC 2014, четвертьфинал Восточного подрегиона.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

В двух командах по `n` участников, каждому заранее известен целый результат
от 0 до 6 очков. Нужно устроить `n` раундов, по одному участнику каждой
команды в раунде, использовав всех ровно один раз. Оба результата раунда
объявляются одновременно. Побеждает команда с большей итоговой суммой,
а при равенстве получается ничья. Зрители заранее знают лишь границы очков.

Выберите порядки так, чтобы как можно позже наступил первый раунд, после
которого по объявленным результатам можно гарантировать победу команды.
После `k` раундов при `r=n−k` оставшихся и разности очков `d` победа
гарантирована ровно при `|d| > 6r`. При равенстве ещё возможна ничья.
Если победитель не определён раньше, весь исход становится известен после
последнего раунда, включая случай итоговой ничьей.

Ограничения: `2 ≤ n ≤ 1000`, результат каждого участника от 0 до 6.
Лимиты: 1 секунда, 64 МБ.

## Входные данные

Первая строка содержит `n`, вторая — `n` очков первой команды, третья —
`n` очков второй. В каждой команде участники независимо пронумерованы
от 1 до `n` в порядке ввода.

## Выходные данные

Выведите `n` строк, в каждой — номера участников первой и второй команды
данного раунда. Каждый номер должен встретиться один раз в своём столбце.
Допустим любой глобально оптимальный порядок.

## Проверка

Проверяющая программа сверяет обе перестановки, проигрывает счёт и
принимает любые порядки, при которых первый решающий раунд наступает как
можно позже.

## Примеры

```
5
0 1 4 3 6
6 5 1 3 0
```

```
5 1
1 5
4 4
2 3
3 2
```

## Решение

Сравним **итоговые суммы**, которые не зависят от перестановок. Если первая
команда побеждает, поставим её участников по возрастанию очков, а вторую
команду — по убыванию. Если побеждает вторая, направления меняются местами.
При равных суммах годятся любые порядки; используем возрастание обеих команд.
Совместим полученные списки по позициям, сохранив исходные номера.

Докажем оптимальность для итоговой разности `D>0` в пользу первой
команды. После любого префикса при `r` оставшихся раундах обозначим
через `R` разность, которую дадут фактически оставшиеся участники. Один
раунд добавляет от −6 до 6, поэтому `R≤6r` и `d=D−R≥D−6r>−6r`. Будущая
проигравшая команда не может получить гарантированную победу ни при
каком порядке этих участников. Значение имеет только верхний порог
`d>6r`.

Для каждой длины префикса `k` возрастание первой команды даёт наименьшую
возможную сумму её `k` первых результатов, а убывание второй — наибольшую
сумму соперника. Их сочетание минимизирует `d(k)` среди **всех** порядков
сразу для каждого `k`. Если в этом порядке победа впервые гарантирована
в раунде `k<n`, в любом другом порядке разность в этом раунде не меньше,
поэтому победа там уже определена. Отложить её дольше нельзя. Если дошли
до последнего раунда, достигнута максимально возможная задержка.
Для победы второй команды доказательство симметрично.

При `D=0` любой префикс даёт `d=−R`, значит, `|d|≤6r`. Ни один порядок
не гарантирует победителя до раскрытия итоговой ничьей, так что любой оптимален.
Даже большой временный отрыв будущей проигравшей команды безопасен:
реальные оставшиеся очки не позволяют превысить порог определённости.

В примере итоговые суммы равны 14 и 15. Показанные первые четыре пары
приносят командам одинаковые очки, а последняя — 4 и 5. Победитель
определяется лишь в пятом раунде, что оптимально.

Сортировка двух массивов номеров занимает `O(n log n)` времени и `O(n)`
памяти. Модули сумм и разностей не больше 6000, обычного целого типа достаточно.

Подводные камни:

- Направления сортировки определяются итоговыми суммами, а не текущим отрывом.
- Сравнение `|d| > 6r` строгое: равенство ещё допускает ничью.
- Очки пары объявляются вместе; каждый участник используется один раз в
  своей команде.
- Выводятся исходные номера с единицы, а не очки или позиции после сортировки.
- Принимайте любой оптимальный порядок, в том числе произвольный при
  равных итогах.

## Оптимизированные решения

`2021_sorting_greedy.java`. То же жадное упорядочение крайних оценок теперь реализовано семью связанными корзинами. Для каждой команды хранятся только массив следующих номеров и головы оценок, суммы считаются при чтении. Команда с меньшей суммой идёт по убыванию, с большей — по возрастанию; при ничьей обе возрастают. Равные оценки получают обратный порядок номеров из-за вставки в голову: это допустимо, поскольку оценки и момент определённости не меняются. O(N+7) времени и памяти плюс ввод/вывод по 1024 байта, без массивов префиксных смещений, сортировки объектов и общей матрицы или строки ответа. Имя sorting_greedy; стабильная альтернатива с префиксными суммами и учебная сортировка сохранены. Условие определённости строгое: |difference|>6*remaining.

Точный исходник: Java 1.8 Accepted #11327334: 0.093 s / 524 KB. Сохранённые места в группе компилятора от 2026-11-20, время затем память: 2/47; 1/47. Строгий допуск учитывает только время при памяти меньше 1024 КБ: первые десять или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка — первого места по обеим метрикам. Сохранённый прежний вариант имеет собственную парную посылку #11325033 (Java 1.8): 0.14 s / 496 KB; замеры и рантаймы не смешиваются. Все учебные исходники сохранены без изменений.

- `2021_sorting_greedy.java`: 0.093 s / 524 KB; сохранённая учебная база `2021_sorting.java` (Java 1.8): 0.14 s / 2824 KB.

`2021_sorting_prefix_sums.java`. Сохраняется прежний экстремальный порядок оценок, задерживающий определённость, но объектная сортировка сравнением заменена устойчивой сортировкой подсчётом по семи значениям0..6. Префиксные концы частот и обратное заполнение сохраняют порядок ID равных оценок. Команда с меньшей суммой идёт по убыванию, с большей — по возрастанию; при равных суммах обе по возрастанию. Разворот делается индексированием без копий и перестановок списков. Вариант sorting_prefix_sums требует O(n+7) времени, O(n) памяти, без объектов ID, матрицы пар ответа и всей строки вывода. Строгая граница определённости прежняя: |difference|>6·remaining.

По сравнению с `2021_sorting.java`: время 0.14 s → 0.14 s; память 2 824 KB → 496 KB.

Новые C++, Go и Rust заменяют сортировку сравнением S=7 корзинами оценок. Исходные ID добавляются в связный список своей оценки; на участника нужен один 16-битный указатель следующего. Сравниваем итоговые суммы: корзины победителя обходим по возрастанию, проигравшего — по убыванию, при ничьей обе по возрастанию. По одному курсору корзины на команду выдаёт один ID за раунд. Каждый участник и корзина посещаются один раз: время и память O(n+S). Исходное доказательство минимизации префикса сохраняется, порядок ID с равной оценкой произволен. Буфер Go/Rust на 10000 байтов вмещает 1000 строк по два ID до четырёх цифр. Простые файлы сохранены; Java/Python используют подходящие базы.

Принятые базовые реализации [2021_sorting.java](2021_sorting.java), [2021_sorting.py](2021_sorting.py) также закрывают быстрый набор: в сохранённом срезе сравнения они уже удовлетворяют рейтинговому критерию включения — топ 15% или первые десять мест одновременно по времени и памяти. Используются те же исходники без одинаковых копий. Звёздочка отмечает версию, которая пока не достигла целевого рейтинга своего языка.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Учебные алгоритмы сохранены. Перепроверенные базовые версии используют собственные новые метрики и ID Accepted точного исходника; эти проверки не считаются оптимизациями.

`2021_sorting_prefix_sums.java`: место по времени 22/47, по памяти 1/47 в этой сопоставимой выборке.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
