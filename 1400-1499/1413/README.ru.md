# 1413. Марсопрыг

[Timus 1413](https://acm.timus.ru/problem.aspx?space=1&num=1413) · сложность 180 · simulation

Автор оригинальной задачи — Станислав Васильев; чемпионат Уральского государственного университета, 29 октября 2005 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Аппаратом управляют с цифровой клавиатуры: каждая клавиша от 1 до 9,
кроме 5, — прыжок ровно на один метр в направлении этой клавиши от
центральной 5 (8 — север, 6 — восток, 9 — северо-восток и так далее),
5 — взятие пробы грунта, 0 — самоуничтожение. По последовательности из
не более 10⁶ нажатий нужно вывести, где окажется аппарат: в точке
первого нажатия 0 или, если его не было, после последней клавиши.
Ответ — смещение на восток и на север с абсолютной или относительной
погрешностью не более 10⁻¹⁰.

Ограничение времени: 0.5 секунды. Ограничение памяти: 64 МБ.

## Входные данные

Цифры нажатых клавиш.

## Выходные данные

X и Y — смещение на восток и на север.

## Примеры

### Пример 1

Ввод:

```
1236987412369870234567890123456789
```

Вывод:

```
1.0000000000 0.0000000000
```

## Решение

Считаем, сколько раз нажата каждая клавиша до первого 0. Прямой прыжок
сдвигает одну координату на целый метр, а диагональный — обе на 1/√2,
так что конечная точка по каждой оси — (сумма прямых) + (сумма
диагональных) / √2, вычисленная из целых сумм. Подсчёт устраняет
округление на каждом прыжке, но итоговые умножение и сложение с
плавающей точкой и вывод десяти знаков после запятой всё ещё округляют;
абсолютная погрешность может немного превышать 10⁻¹⁰. `O(n)`.

Подводные камни:

- клавиши после первого 0 нужно игнорировать (тесты 01, 05, gen2);
- диагональный прыжок имеет длину один метр, а не √2 (тест 04);
- диагональные координаты иррациональны, поэтому подсчёт не делает
  итоговые координаты точными (тест 04);
- чтение миллиона символов с медленным вызовом ввода на каждый может
  занять заметную часть 0.5 секунды, поэтому решения читают целые
  токены, строки или весь ввод сразу.

## Оптимизированные решения

Оптимизированное решение на Go считает клавиши в повторно используемом
буфере на 4 КБ вместо чтения всех нажатий, которых до 10⁶, в память
сразу: {1413_simulation_optimized.go}.

Оптимизированное решение на Java считает клавиши прямо по байтам
`BufferedInputStream` и останавливается на первом 0, вместо того чтобы
декодировать ввод в строки `String` длиной до миллиона символов через
`BufferedReader`: {1413_simulation_optimized.java}.

Оптимизированное решение на Python читает ввод кусками по 8 КБ и считает
цифры каждого куска через `bytes.count` вместо чтения всех нажатий,
которых до 10⁶, в память сразу; после первого 0 остаток ввода читается,
но не считается: {1413_simulation_optimized.py}.

Оптимизированное решение на Rust считает клавиши в повторно используемом
буфере на 4 КБ вместо чтения всех нажатий, которых до 10⁶, в вектор
сразу: {1413_simulation_optimized.rs}.
