# 1413. Марсопрыг

[Timus 1413](https://acm.timus.ru/problem.aspx?space=1&num=1413) · сложность 180 · simulation

Автор оригинальной задачи — Станислав Васильев; чемпионат Уральского государственного университета, 29 октября 2005 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Аппаратом управляют с цифровой клавиатуры: каждая клавиша от 1 до 9,
кроме 5, — прыжок ровно на один метр в направлении этой клавиши от
центральной 5 (8 — север, 6 — восток, 9 — северо-восток и так далее),
5 — взятие пробы грунта, 0 — самоуничтожение. По последовательности из
не более 10⁶ нажатий нужно вывести, где окажется аппарат: в точке
первого нажатия 0 или, если его не было, после последней клавиши.
Ответ — смещение на восток и на север с абсолютной или относительной
погрешностью не более 10⁻¹⁰.

Ограничение времени: 0.5 секунды. Ограничение памяти: 64 МБ.

## Входные данные

Цифры нажатых клавиш.

## Выходные данные

X и Y — смещение на восток и на север.

## Проверка

Тесты репозитория сравнивают числовые токены по условию |ответ-эталон| <= 0.0000000002·max(1,|эталон|), отклоняют бесконечности и NaN, а нечисловые токены сравнивают точно.

## Примеры

### Пример 1

Ввод:

```
1236987412369870234567890123456789
```

Вывод:

```
1.0000000000 0.0000000000
```

## Решение

Считаем, сколько раз нажата каждая клавиша до первого 0. Прямой прыжок
сдвигает одну координату на целый метр, а диагональный — обе на 1/√2,
так что конечная точка по каждой оси — (сумма прямых) + (сумма
диагональных) / √2, вычисленная из целых сумм. Подсчёт устраняет
округление на каждом прыжке, но итоговые умножение и сложение с
плавающей точкой и вывод десяти знаков после запятой всё ещё округляют;
абсолютная погрешность может немного превышать 10⁻¹⁰. `O(n)`.

Подводные камни:

- клавиши после первого 0 нужно игнорировать (тесты 01, 05, gen2);
- диагональный прыжок имеет длину один метр, а не √2 (тест 04);
- диагональные координаты иррациональны, поэтому подсчёт не делает
  итоговые координаты точными (тест 04);
- чтение миллиона символов с медленным вызовом ввода на каждый может
  занять заметную часть 0.5 секунды, поэтому решения читают целые
  токены, строки или весь ввод сразу.

## Оптимизированные решения

`1413_simulation_optimized.java`. Java сохраняет целые счётчики направлений цифровой клавиатуры и останавливается на первом нуле, читая блоками по 4096 байт. Каждая координата равна straight+diagonal/sqrt(2). Коэффициент диагонали представлен C/10^18, где C=707106781186547524=floor(10^18/sqrt(2)); восемнадцать дробных знаков выводятся целочисленно. Разбиение C на 707106781*10^9+186547524 удерживает произведения в long, floorDiv/floorMod правильно обрабатывают знак и заём около нуля. При числе ходов до 10^6 погрешность коэффициента меньше 1e-12, ниже допуска 1e-10; преобразования double нет. Это определённая математическая константа, а не сохранённые ответы. Время O(I) по прочитанным байтам, дополнительная память фиксирована. Короткая учебная версия с плавающей точкой сохранена.

Accepted точного исходника Java 1.8 №11327528: 0.093 с / 376 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 3/49, память 1/49. При памяти меньше 1024 КБ строгий допуск учитывает только время: первые десять мест или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка: первого места по обеим метрикам. Прежний документированный оптимизированный запуск №11307336: 0.109 с / 936 КБ; это отдельная историческая пара, не текущий замер данного исходника. Учебные версии сохранены без изменений.

- `1413_simulation_optimized.java`: 0.093 s / 376 KB; сохранённая учебная база `1413_simulation.java`: 0.093 s / 5804 KB.

Оптимизированное решение на Go считает клавиши в повторно используемом
буфере на 4 КБ вместо чтения всех нажатий, которых до 10⁶, в память
сразу: {1413_simulation_optimized.go}.

Оптимизированное решение на Python читает ввод кусками по 8 КБ и считает
цифры каждого куска через `bytes.count` вместо чтения всех нажатий,
которых до 10⁶, в память сразу; после первого 0 остаток ввода читается,
но не считается: {1413_simulation_optimized.py}.

Оптимизированное решение на Rust считает клавиши в повторно используемом
буфере на 4 КБ вместо чтения всех нажатий, которых до 10⁶, в вектор
сразу: {1413_simulation_optimized.rs}.

### Измеренный выигрыш

Каждая оптимизированная версия имеет Accepted и сокращает время или
память минимум на 30% относительно базовой версии на том же языке.
Базовые исходники сохранены. Отрицательное сокращение означает рост
расхода. Звёздочка относится только к рейтинговой цели.

- `1413_simulation_optimized.go`: сокращение времени +0.00%; сокращение
  памяти +68.46%; база: `1413_simulation.go`.

- `1413_simulation_optimized.py`: сокращение времени +16.13%; сокращение
  памяти +82.94%; база: `1413_simulation.py`.

- `1413_simulation_optimized.rs`: сокращение времени +0.00%; сокращение
  памяти +88.58%; база: `1413_simulation.rs`.

`1413_simulation_optimized.cpp`. Направления подсчитываются в повторно используемом буфере на 8 КБ; на первом нуле подсчёт прекращается. Девять счётчиков сохраняются, целые осевые и диагональные вклады объединяются один раз с коэффициентом sqrt(1/2) для диагоналей. Время O(n), дополнительная память O(1), весь ввод в строке не хранится.

По сравнению с `1413_simulation.cpp`: время 0.015 s → 0.015 s; память 1832 KB → 92 KB.
