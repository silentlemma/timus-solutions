# 1494. Монобильярд

[Timus 1494](https://acm.timus.ru/problem.aspx?space=1&num=1494) · сложность 90 · simulation

Автор оригинальной задачи — Алексей Самсонов; XIII командный чемпионат школьников Свердловской области по программированию, 14 октября 2006 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Шары 1, 2, …, N (1 ≤ N ≤ 100000) нужно закатить в единственную лузу
именно в этом порядке. Время от времени ревизор забирал из лузы
последний закатившийся шар, а в конце забрал все шары. По порядку, в
котором ревизор забирал шары, нужно вывести «Cheater», если шары не
могли быть закачены в правильном порядке, и «Not a proof» иначе.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

N, затем N шаров в порядке, в котором их забирал ревизор.

## Выходные данные

«Cheater» или «Not a proof».

## Примеры

### Пример 1

Ввод:

```
2
2
1
```

Вывод:

```
Not a proof
```

### Пример 2

Ввод:

```
3
3
1
2
```

Вывод:

```
Cheater
```

## Решение

Луза — это стек: шары кладутся как 1, 2, …, N, а ревизор всегда берёт
верхний. Повторяем игру: закатываем шары по порядку и после каждого
забираем шары, пока сверху лежит следующий шар из списка ревизора.
Ожидание помочь не может: шар не сверху остаётся закрыт, пока не уйдёт
всё, что над ним. Если так удаётся забрать весь список, порядок был
возможен. `O(N)`.

Подводные камни:

- шар под более поздним шаром не может выйти первым: 3, 4, 1, 2
  невозможно (тесты 02, 05);
- если забрать все шары только в конце, порядок обратный, а если
  забирать каждый сразу — прямой; оба возможны (gen4, gen5);
- одной перестановки двух шаров в настоящей игре обычно хватает, чтобы
  она стала невозможной (gen3).

## Оптимизированные решения

Оптимизированные решения моделируют лузу во время чтения: для каждого
вынутого шара закатывают шары до этого номера, после чего сверху лузы
должен лежать именно он, а первое несовпадение завершает программу.
Поэтому порядок шаров не хранится; лузой служит массив-стек. C++
разбирает числа через `getchar` (0.031 с вместо 0.093 с и 512 КБ вместо
1540 КБ), Go разбирает их вручную, пишет ответ без `fmt` и хранит лузу в
заранее выделенном массиве `int32`, поскольку номера шаров не больше
100 000 (1312 КБ вместо 7684 КБ при том же времени), Java читает блоки
по 4 КБ и разбирает их вручную вместо `StreamTokenizer` (844 КБ вместо
1300 КБ при том же времени), Python разбирает построчно и хранит лузу в
`array` (832 КБ вместо 15568 КБ, хотя время растёт с 0.140 с до
0.171 с), а Rust разбирает вручную из буфера на 4 КБ (604 КБ вместо
2704 КБ при том же времени).
