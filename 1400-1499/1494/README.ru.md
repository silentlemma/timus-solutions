# 1494. Монобильярд

[Timus 1494](https://acm.timus.ru/problem.aspx?space=1&num=1494) · сложность 90 · simulation

Автор оригинальной задачи — Алексей Самсонов; XIII командный чемпионат школьников Свердловской области по программированию, 14 октября 2006 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Шары 1, 2, …, N (1 ≤ N ≤ 100000) нужно закатить в единственную лузу
именно в этом порядке. Время от времени ревизор забирал из лузы
последний закатившийся шар, а в конце забрал все шары. По порядку, в
котором ревизор забирал шары, нужно вывести «Cheater», если шары не
могли быть закачены в правильном порядке, и «Not a proof» иначе.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

N, затем N шаров в порядке, в котором их забирал ревизор.

## Выходные данные

«Cheater» или «Not a proof».

## Примеры

### Пример 1

Ввод:

```
2
2
1
```

Вывод:

```
Not a proof
```

### Пример 2

Ввод:

```
3
3
1
2
```

Вывод:

```
Cheater
```

## Решение

Луза — это стек: шары кладутся как 1, 2, …, N, а ревизор всегда берёт
верхний. Повторяем игру: закатываем шары по порядку и после каждого
забираем шары, пока сверху лежит следующий шар из списка ревизора.
Ожидание помочь не может: шар не сверху остаётся закрыт, пока не уйдёт
всё, что над ним. Если так удаётся забрать весь список, порядок был
возможен. `O(N)`.

Подводные камни:

- шар под более поздним шаром не может выйти первым: 3, 4, 1, 2
  невозможно (тесты 02, 05);
- если забрать все шары только в конце, порядок обратный, а если
  забирать каждый сразу — прямой; оба возможны (gen4, gen5);
- одной перестановки двух шаров в настоящей игре обычно хватает, чтобы
  она стала невозможной (gen3).

## Оптимизированные решения

`1494_bitmask_simulation.py`. Стек ожидающих шаров представлен упорядоченными непустыми 32-битными пакетами, а не отдельной целочисленной ячейкой на шар. Новый максимум добавляет только пропущенный диапазон; прежний шар должен совпасть со старшим установленным битом последнего пакета перед удалением. Индекс и маска хранятся вместе: N-битное число не копируется на каждом шаге, пустые слова не сканируются. При N<=100000 пакет помещается в 44 бита; суммарное время O(N), память O(ceil(N/32)) пакетов плюс ввод по 4096 байт. Детерминированный алгоритм bitmask_simulation отличается от сохранённых явных стеков. Текущий замер сделан на PyPy; Accepted прежнего стека на CPython остаётся отдельной парой.

Точный исходник: PyPy 3.10 x64 Accepted #11327514: 0.14 s / 3764 KB. Сохранённые места в группе компилятора от 2026-11-20, время затем память: 20/164; 1/164. Строгий допуск учитывает и время, и память при памяти от 1024 КБ: первые десять или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка — первого места по обеим метрикам. Сохранённый прежний вариант имеет собственную парную посылку #11326685 (Python 3.12 x64): 0.14 s / 4160 KB; замеры и рантаймы не смешиваются. Все учебные исходники сохранены без изменений.

- `1494_bitmask_simulation.py`: 0.14 s / 3764 KB; сохранённая учебная база `1494_simulation.py` (Python 3.12 x64): 0.14 s / 15568 KB.

`1494_simulation_optimized.py`. Луза моделируется при чтении каждого наблюдаемого шара: последовательно добавляются ещё не закатившиеся шары до него, затем сверху должен быть именно он; первое противоречие завершает проверку. Стек — заранее выделенный список Python на N ячеек вместо упакованного беззнакового массива. Каждый шар добавляется и удаляется не более раза: время O(N), память O(N) плюс токены текущей строки. Отдельный порядок ввода не хранится; обычная читаемая симуляция сохранена.

Accepted точного исходника CPython 3.12 №11326685: 0.14 с / 4160 КБ. Сохранённая выборка актуальных компиляторов от 2026-11-20: место по времени 20/164, по памяти 1/164. Обе обязательные метрики проходят строгий критерий первых десяти мест или топ 15%, процентная граница округляется вверх. Звёздочка относится к отдельной цели Python — первому месту по обеим метрикам.

Прежняя документированная оптимизированная посылка №11303753 (Python 3.12 x64) имела 0.171 с / 832 КБ. У текущего запуска CPython 3.12 зафиксированы меньшее время и большая память. Это разные парные измерения судьи; сравнение включает выбор интерпретатора и разброс запусков.

- `1494_simulation_optimized.py`: 0.14 s / 4160 KB; сохранённая учебная база `1494_simulation.py` (Python 3.12 x64): 0.14 s / 15568 KB.

Оптимизированные решения моделируют лузу во время чтения: для каждого вынутого шара закатывают шары до этого номера, после чего сверху лузы должен лежать именно он, а первое несовпадение завершает программу. Поэтому порядок шаров не хранится; лузой служит массив-стек. C++ разбирает числа через `getchar` (0.031 с вместо 0.093 с и 512 КБ вместо 1540 КБ), Go разбирает их вручную, пишет ответ без `fmt` и хранит лузу в заранее выделенном массиве `int32`, поскольку номера шаров не больше 100 000 (1312 КБ вместо 7684 КБ при том же времени), Java читает блоки по 4 КБ и разбирает их вручную вместо `StreamTokenizer` (844 КБ вместо 1300 КБ при том же времени), а Rust разбирает вручную из буфера на 4 КБ (604 КБ вместо 2704 КБ при том же времени).
