# 1416. Для служебного пользования…

## Задача

Связный граф имеет n вершин (2 ≤ n ≤ 500) и m рёбер стоимостью от 0
до 1000, между двумя вершинами не больше одного ребра. Нужно вывести
стоимость минимального остовного дерева и стоимость следующего по
стоимости остовного дерева (она может совпадать с первой) или −1, если
другого остовного дерева нет.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

Первая строка: n вершин и m неориентированных рёбер, 2≤n≤500, 1≤m≤n(n−1)/2. Следующие m строк содержат концы a,b из 1..n и стоимость w из 0..1000. Петель и параллельных рёбер нет, граф связный.

## Выходные данные

«Cost: » и первая стоимость, затем «Cost: » и вторая.

## Проверка

Репозиторий сравнивает весь вывод точно после удаления только конечных пробельных символов: две строки, Cost: и стоимости первого и второго остова. Регистр, двоеточие, следующий пробел и внутренний перевод строки значимы. Вторая стоимость может равняться первой; -1 нужен лишь при отсутствии другого набора рёбер остова.

## Примеры

### Пример 1

Ввод:

```
4 6
1 2 2
2 3 2
3 4 2
4 1 2
1 3 1
2 4 1
```

Вывод:

```
Cost: 4
Cost: 4
```

### Пример 2

Ввод:

```
3 2
1 2 2
2 3 2
```

Вывод:

```
Cost: 4
Cost: -1
```

## Решение

Второе по стоимости остовное дерево отличается от некоторого
минимального ровно одним ребром: входит ребро не из дерева и уходит
самое тяжёлое ребро на пути по дереву между его концами. Поэтому
вторая стоимость — минимальная плюс наименьшее w − (самое тяжёлое ребро
на пути) по рёбрам вне дерева, и −1, если все рёбра в дереве.

При не более 500 вершинах алгоритм Прима на матрице стоимостей работает
за O(n²). Самые тяжёлые рёбра на всех путях по дереву получаются
попутно: когда вершина v присоединяется через родителя p ребром
стоимости c, для каждой уже добавленной вершины u
heaviest(u, v) = max(heaviest(u, p), c). `O(n² + m)`.

Подводные камни:

- второе дерево может стоить столько же, сколько первое (тест 01);
- если граф сам является деревом, второго дерева нет (тесты 02, 03,
  gen2);
- стоимости бывают нулевыми (тесты 04, 06).

## Оптимизированные решения

Компактная версия C++ сохраняет ту же схему Прима и хранит обе матрицы в 16-битных ячейках. После добавления ребра в дерево оно помечается в матрице весов как отсутствующее. Обе вершины уже в дереве, поэтому это не влияет на дальнейшие обновления Прима. В конце остаётся проверить только рёбра вне дерева, и при нулевой прибавке можно сразу остановиться.

Быстрый набор использует проходящие простые Java/Python и оптимизированные C++, Go и Rust. Простые Go/Rust сохранены для обучения, но не проходят текущие пределы памяти и не объявляются проходящими быстрыми исходниками. Одинаковые копии не нужны. Исторические пары Accepted остаются у соответствующих версий.

## Особенности языков

Простые реализации хранят матрицы весов, максимального ребра пути и принадлежности остову, список рёбер и O(n) состояния Прима: O(n²+m) вспомогательной памяти. Полные парсеры, особенно Python и простой Rust, дополнительно сохраняют I байт ввода/токенов, итого O(n²+m+I). Компактный C++ использует две матрицы uint16, помечает рёбра остова отсутствующими и просматривает матрицу без отдельного списка рёбер/матрицы принадлежности, память O(n²). Сторож отсутствия больше всех весов≤1000. Оптимизированный Go сохраняет графовые структуры, но пополняет входной буфер 8192 байта; Rust использует ограниченный ввод, 32-битные поля рёбер и 64-битные суммы. Алгоритмическое время всех O(n²+m).

Единые [критерии](../../RATING_CRITERIA.md) не сравнивают память только строго ниже 1024 КБ. В кэше оптимизированный C++ проходит обе метрики 1/89 и 2/89, простая Java — обе 1/14. Простая Python проходит пределы третьего из восьми точных соперников 0.52095 s / 53847.60 КБ. Один соперник Go даёт 1.8860 s / 9117.20 КБ: оптимизированные 8892 КБ проходят, простые 10568 КБ не проходят память. Один соперник Rust даёт 0.1610 s / 7015 КБ: оптимизированные 3908 КБ проходят, простые 9656 КБ — нет. Чужие времена меньше 0.015 s исключаются, нижний предел применяется только к нашим.

В `1416_graphs_parsing_implementation_optimized.go` комментарии помощников теперь описывают пополняемый ввод и форматированный вывод только %d; прежняя ёмкость токена 128 байт получила имя. Значения, алгоритм и содержательные пояснения сохранены.

В `1416_graphs_implementation_optimized.rs` только именованы требуемые линтером константы; значения, алгоритм и комментарии прежние. Accepted #11328963 и парные метрики относятся к предыдущим точным байтам.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
