# 1401. Игроки

[Timus 1401](https://acm.timus.ru/problem.aspx?space=1&num=1401) · сложность 159 · constructive

Автор оригинальной задачи — Алексей Самсонов; XII командный чемпионат школьников Свердловской области по программированию, 15 октября 2005 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Нужно замостить доску 2ⁿ × 2ⁿ, 1 ≤ n ≤ 9, без одной клетки уголками из
трёх клеток. Вывести доску с 0 на выбитой клетке и номером фигуры на
каждой остальной, фигуры пронумерованы от 1 до (4ⁿ − 1) / 3, или -1,
если замостить нельзя.

Ограничение времени: 2 секунды. Ограничение памяти: 64 МБ.

## Входные данные

n, затем строка x и столбец y выбитой клетки, 1 ≤ x, y ≤ 2ⁿ; левая
верхняя клетка — (1, 1).

## Выходные данные

2ⁿ строк по 2ⁿ чисел. Подходит любое замощение.

## Примеры

### Пример 1

Ввод:

```
2
1 1
```

Вывод:

```
0 1 3 3
1 1 4 3
2 4 4 5
2 2 5 5
```

## Решение

Замощение всегда существует, делением пополам. Разобьём доску на четыре
четверти; выбитая клетка лежит в одной из них. Положим уголок на три
клетки у середины доски, принадлежащие трём другим четвертям. Теперь
каждая четверть — доска 2ⁿ⁻¹ × 2ⁿ⁻¹ ровно с одной занятой клеткой, то
есть та же задача, а доска 1 × 1 ничего не требует. Решения держат ещё
не замощённые квадраты в стеке вместо рекурсии, каждый со своей занятой
клеткой, и нумеруют фигуры в порядке укладки. `O(4ⁿ)`.

Подводные камни:

- ответ никогда не равен -1;
- доска 512 × 512 — это 262 144 числа, поэтому вывод буферизуется
  (сгенерированные тесты).

Тесты проверяются программой, которая требует 0 только на выбитой
клетке и каждое число от 1 до (4ⁿ − 1) / 3 ровно на трёх клетках,
образующих уголок внутри квадрата 2 × 2.

## Оптимизированные решения

Оптимизированное решение на C++ заполняет глобальный массив `int`
512 × 512 вместо `vector` из `vector` и использует рекурсию вместо стека
квадратов: вызов кладёт фигурку одного квадрата и спускается в его
четверти, глубина не больше n ≤ 9. Четверти обходятся в обратном
порядке, поэтому фигурки получают те же номера, что и со стеком. Клетки
печатаются по одной через `printf`, а не собираются сначала всей доской
в `string`: {1401_constructive_optimized.cpp}.

Оптимизированное решение на Go хранит доску в клетках `int32` вместо
64-битного `int`, ведь номера фигурок не больше (4⁹ − 1) / 3 = 87 381,
что вдвое уменьшает доску, и форматирует каждое число через
`strconv.AppendInt` в один и тот же срез байтов, а не создаёт строку для
каждой клетки: {1401_constructive_optimized.go}.

Оптимизированное решение на Java использует рекурсию вместо того, чтобы
класть в стек объект `Square` для каждого квадрата: вызов кладёт фигурку
одного квадрата и спускается в его четверти, глубина не больше n ≤ 9, а
четверти обходятся в обратном порядке, поэтому фигурки получают те же
номера, что и со стеком. Ввод читается через `StreamTokenizer` вместо
`Scanner`, а доска выводится построчно через `BufferedWriter`, причём
для каждой строки заново используется один и тот же `StringBuilder`, а
не собирается сначала целиком: {1401_constructive_optimized.java}.

Оптимизированное решение на Python хранит каждую строку в `array("I")`
из 4-байтовых беззнаковых клеток, которые вмещают номера фигурок до
(4⁹ − 1) / 3 = 87 381, вместо списка целых объектов. Оно рекурсивно
спускается в четверти, глубина не больше n ≤ 9, вместо стека кортежей,
обходит их в обратном порядке, чтобы фигурки получили те же номера, и
выводит доску построчно, а не склеивает её в одну строку:
{1401_constructive_optimized.py}.

Оптимизированное решение на Rust строит доску так же, но пишет числа
прямо в `BufWriter`, а не форматирует сначала всю доску в `String`
размером примерно до 1.5 МБ: {1401_constructive_optimized.rs}.
