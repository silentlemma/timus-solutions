# 1125. Отмена перекрашиваний на целых расстояниях в сетке

[Timus 1125](https://acm.timus.ru/problem.aspx?space=1&num=1125) · сложность 236 · bitmask

Автор оригинальной задачи — Дмитрий Филимоненков; VI студенческое соревнование по программированию УрГУ, 21 октября 2001 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Поле из `M × N` единичных клеток (`0 ≤ M, N ≤ 50`) раскрашено в чёрный
(`B`) и белый (`W`). Каждый раз, когда клетку посещают, все клетки, центры
которых находятся на целом расстоянии от её центра, меняют цвет, включая
саму посещённую клетку (расстояние 0). По конечным цветам и числу
посещений каждой клетки (до `2·10^9`) вывести начальные цвета.

Ограничение времени: 0,25 секунды. Ограничение памяти: 64 МБ.

## Входные данные

`M N`, затем `M` строк конечных цветов, затем `M` строк по `N` чисел
посещений.

## Выходные данные

`M` строк начальных цветов.

## Проверка

Строки цветов сравниваются по токенам. И прямая Python-симуляция,
и новый Python с масками независимо проверены на 5748 полях каждый
перебором пар клеток с точной проверкой целого расстояния. Оракул не
использует масок и группировки осей. Перебраны цвета и чётности для
2×2 и 2×3, все чётности с двумя одноцветными результатами для 3×3;
есть пустые и узкие поля, случайные поля, максимальные нечётные,
чётные и случайные посещения 50×50 и одиночные нечётные посещения.

Каждая из восьми добавленных программ — пять симуляций и три новые
реализации с масками — прошла 11 входов репозитория и 78 фактических
дополнительных запусков в Docker, получила Accepted для точного исходника.
Сохранённые выводы и коды возврата повторно сверяются с независимо
пересчитанными ответами перебора пар и связаны с SHA. Число 5748 относится
к Python, а не к каждому машинному исходнику. На четырёх локальных
стресс-входах симуляции CPython получено до 0,0687 с CPU и 17288 КБ RSS
при лимитах 0,25 с/64 МБ; метрики судьи учитываются отдельно.

## Решение

Основной учебный алгоритм непосредственно моделирует изменения.
Смена цвета — XOR с единицей: две смены отменяются, порядок посещений
не важен. Оставим только чётность каждого счётчика. Построим все знаковые
смещения `(dr,dc)` в возможных пределах поля, для которых квадрат длины
является полным квадратом, включая `(0,0)`. Для каждой клетки, посещённой
нечётное число раз, переключим все не вышедшие за поле клетки по этим смещениям.

У каждой подходящей пары «источник–цель» ровно одно такое смещение,
поэтому её вклад учтён один раз. Эти же переключения восстанавливают
начальные цвета из конечных: смена цвета обратна самой себе. При сторонах
до 50 смещений `K≤405`. Их построение занимает `O((M+N)²)` простых
проверок, моделирование — `O(MNK)` времени; память `O(MN+K)`.
Все пять новых реализаций используют обычные клетки и циклы по координатам,
без сдвигов масок строк, и получили собственные Accepted.

Расстояние ноль включается. Для счётчиков до двух миллиардов нужна только
чётность, ввод помещается в знаковое 32-битное целое. При нулевом размере
выводим `M` пустых строк. Все прежние реализации с масками сохранены.

## Оптимизированные решения

Смена цвета — XOR с единицей: две смены отменяются, порядок посещений
не важен. Оставим от числа посещений только чётность. Пусть `R[r]` —
битовая маска нечётных посещений строки `r`. Для целевой строки сложим
через XOR сдвинутые исходные строки по всем смещениям `(dr,dc)`, для которых
`dr²+dc²` — полный квадрат, и оставим младшие `N` бит. Каждая пара
«источник–цель» учитывается один раз. Обратная смена цвета совпадает
с прямой, поэтому XOR найденной чётности с конечной раскраской даёт начальную.

Все пять прежних Accepted-версий перебирают знаковые смещения, включая
`(0,0)`. Для поля 50×50 их 405; меньшему полю нужно подмножество.
Время `O(MN+MK)` операций над масками для `K` смещений, включая ввод,
вывод и построение смещений. При `N≤50` машинная строка помещается
в 64-битное слово. Python использует длинные целые: цена сдвига и XOR
зависит от числа разрядов. Машинные версии хранят `O(MN+M+K)` слов/символов;
прежний Python также хранит все токены и числа посещений —
`O(MN+M+K)` объектов. Все исходные файлы сохранены.

Расстояние ноль тоже целое. Для счётчиков до двух миллиардов нужен лишь
младший бит; ввод помещается в знаковое 32-битное целое. При нулевом
размере выводим `M` пустых строк: восстанавливать клетки не требуется.

Три новые реализации сохраняют алгоритм чётности и масок строк,
поэтому названы `_optimized`. Объединим оси и четыре знака каждого
строго положительного смещения. Обозначим XOR всех строк через `C`,
маску младших `N` единиц — через `F`. Источники в целевой строке дают
`F`, если `popcount(R[r])` нечётно; источники в тех же столбцах дают `C`.
Начальная клетка здесь учтена дважды, поэтому ещё раз прибавим XOR `R[r]`,
чтобы получить нужный один вклад.

Для каждой пары `dr>0,dc>0` с целой длиной вычислим
`T = R[r−dr] XOR R[r+dr]`, заменяя вышедшую за поле строку нулём.
Прибавим `(T<<dc) XOR (T>>dc)`: все четыре знака учитываются ровно один
раз, оси и начало к этим слагаемым не относятся. В конце оставим столбцы
поля. Положительных пар не более `P=52` вместо 405 знаковых смещений.
Время `O(MN+MP)` операций над масками. Храним цвета, маски строк и `P` пар.
C++/Java используют ещё фиксированную таблицу 5000 квадратов; множество
квадратов Python занимает `O(M+N)` элементов. Промежуточная маска Python
может иметь `2N−1` бит: это не одно машинное слово. Машинные сдвиги меньше
64, отброшенные старшие биты не влияют на младшие `N`; Java применяет `>>>`.

## Особенности языков

Все пять новых `simulation` — предпочитаемые простые базы. Текущее
сравнение оптимизации ведётся с симуляцией на том же языке. Обе масочные
версии Python занимают 0,046 против 0,093 с: выигрыш 50,5% по времени.
Прежняя использует 900 против 564 КБ — на 59,6% больше, сгруппированная
580 против 564 КБ — на 2,8% больше. Обе допущены по времени с явной
платой по памяти.

Сгруппированные маски C++ используют 132 против 136 КБ симуляции —
экономия лишь 2,9%; Java — 424/536 КБ, лишь 20,9%, при равном времени
в каждой паре. Их текущая роль — Accepted-альтернативы. Имена `_optimized`
относятся к сохранённым парам исходного алгоритма с масками, где реальная
экономия памяти составляла 71,1% и 56,2%. Это исторические сравнения,
а не текущие проценты относительно симуляции. Файлы не удалены,
не переименованы и не продублированы; одно имя не даёт статуса оптимизации.

Снимок от 2 ноября 2026 года: простая C++ — 1/1 среди 55 отфильтрованных
записей других авторов, простая Java — 1/1 среди одной, сгруппированный
Python — 1/1 среди восьми. Прежний Python с масками — 1/3: звёздочка
сохраняется, хотя другая Python-версия достигла цели. Выборки Go/Rust
пусты: это формальное покрытие. Цель C++ — верхние 15% либо первые
десять мест по обеим метрикам; других языков — первое место по обеим.
Для каждого семейства есть подходящий исходник.
