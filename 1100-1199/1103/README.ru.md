# 1103. Окружность через три карандаша, делящая остальные пополам

[Timus 1103](https://acm.timus.ru/problem.aspx?space=1&num=1103) · сложность 504 · geometry

Автор оригинальной задачи — Катя Овечкина; Tetrahedron Team Contest, май 2001 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

`N` карандашей стоят в целых точках (`N` нечётно, `3 ≤ N ≤ 5000`,
координаты по модулю не больше `10^8`). Никакие три не лежат на одной
прямой, никакие четыре — на одной окружности. Нужно выбрать три
карандаша так, чтобы внутри окружности через них оказалось ровно
`(N − 3) / 2` остальных карандашей и столько же снаружи. Если такой
окружности нет, вывести `No solution`.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

`N`, затем `N` строк `x y`.

## Выходные данные

Координаты трёх карандашей, по одному карандашу в строке.

## Проверка

Подходит любая правильная окружность. Проверяющая программа убеждается,
что три точки — разные карандаши, и считает карандаши внутри и снаружи
окружности точным целочисленным определителем.

## Примеры

### Пример 1

Ввод:

```
7
0 0
1 0
2 -1
2 1
1 1
0 2
-3 -1
```

Вывод:

```
-3 -1
2 -1
1 1
```

## Решение

Решение есть всегда. Возьмём `A` — самый нижний карандаш (из самых
нижних самый левый) — и `B`, его соседа по выпуклой оболочке, выбранного
так, что все остальные карандаши лежат слева от прямой `AB`. Тогда любая
окружность через `A` и `B` делит эту полуплоскость одинаково: карандаш
`P` внутри окружности через `A`, `B` и `C` ровно тогда, когда он видит
отрезок `AB` под большим углом, чем `C`. Все углы `APB` меньше 180° и,
поскольку никакие четыре карандаша не лежат на одной окружности, все
различны. Отсортируем остальные `N − 2` карандаша по этому углу и
возьмём средний как `C`: `(N − 3) / 2` карандашей видят `AB` под большим
углом и лежат внутри, столько же — под меньшим и лежат снаружи.
`O(N log N)`.

Сравниваем углы без плавающей точки. Для P обозначим
dot=(A-P)·(B-P), cross=cross(P,A,B)>0. Их отношение — cot угла APB.
На (0,180 градусов) котангенс строго убывает. Порядок углов возрастающий,
поэтому котангенсов — убывающий: P перед Q тогда и только тогда, когда
dot_P*cross_Q > dot_Q*cross_P. Неравенство сохранено и верно; обращение
всего порядка тоже даёт тот же медианный элемент.

C++ выбирает медиану через std::nth_element без полной сортировки.
Таблица даёт консервативный худший случай O(N log N) для закреплённого
GCC 13.2: логарифмический предел глубины разбиений включает выбор кучей.
Безусловный худший O(N) не обоснован. Все реализации хранят O(N) точек
и ключей, плюс сохранённый ввод и рабочую память сортировки/выбора, где она есть.

Тонкие места:

- координаты доходят до `10^8`, поэтому `dot` и `cross` ограничены
  по модулю `8 · 10^16` и `4 · 10^16`, а их произведения — `3.2 · 10^33`, далеко за 64 бита;
- сравнивать углы через `atan2` рискованно: два далёких карандаша могут
  видеть `AB` под углами, разница которых меньше ошибки округления;
- `B` должен быть соседом `A` по оболочке; для произвольной второй точки
  карандаши по разные стороны от `AB` не упорядочиваются одним углом.

Ответы проверены точным определителем «точка в окружности» на всех
тестах, включая случайные наборы из тысяч карандашей на всём диапазоне
координат.

## Оптимизированные решения

`1103_geometry_optimized.java`. Сохраняются опорное ребро выпуклой оболочки и окружность по медианному углу. Координаты, скалярные и положительные векторные произведения, индексы сортировки хранятся в примитивных массивах. Вместо создания BigInteger в компараторе произведения сравниваются точно: сначала знаки, затем беззнаковые старшая и младшая половины произведений64 на64, старшая собирается из32-битных частей. Предел координат10^8 сохраняет скалярные и векторные произведения ниже2^63, модули безопасны, полное произведение помещается в128 бит. Вещественных углов и epsilon нет. Итеративное слияние примитивных индексов требует O(N log N) времени и O(N) памяти; прежний медианный критерий корректен при отсутствии трёх коллинеарных и четырёх лежащих на окружности точек.

По сравнению с `1103_geometry.java`: время 0.140 s → 0.078 s; память 7336 KB → 688 KB.

Быстрый Go сохраняет опорное ребро оболочки и возрастание угла.
При положительных векторных произведениях сначала сравнивает знаки dot
(ноль неотрицателен), затем точные модули через старшее/младшее слова
math/bits.Mul64, обращая сравнение для двух отрицательных произведений.
Точки и ключи в одном массиве. Детерминированная медиана трёх не гарантирует
сокращение интервала в фиксированное число раз, которое дало бы линейную
суммарную работу. Явный предел 2*bit_length(N-2) разбиений ограничивает
их работу O(N log N); сортировка остатка также O(N log N). Память O(N).
Оценка не предполагает случайный pivot или геометрическое убывание.

Кэшированный аудит подтверждает базу C++ только по месту времени
ниже 1 МиБ, Python — по обеим метрикам эталона малой выборки точного
компилятора. Простые Java/Rust не проходят; отдельная быстрая Java
проходит по месту времени, быстрый Rust ниже 1 МиБ — по эталону времени.
Быстрый Go ещё не проходит временную цель, его маркер сохранён.
Применяются общие [рейтинговые критерии](../../RATING_CRITERIA.md),
без отдельного первого места и одинаковых копий; учебные версии сохранены.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1103_geometry_implementation_optimized.rs`. Используется один вектор точек: две выбранные точки оболочки переносятся в начало, угловая медиана выбирается на месте в оставшемся срезе. Точные сравнения i128 заменяют копии точек и ключей. Токены читаются через ограниченный нативный байтовый буфер; короткие хранятся внутри объекта, дополнительная память выделяется только длинным. Десятичный разбор сохраняет знаковые границы без хранения всего командного ввода. Точка входа C напрямую вызывает решение и сбрасывает вывод Rust перед возвратом; архивная реализация с обычной точкой входа сохранена.

Accepted #11328975 (Rust 1.75 x64): **0.015 s / 236 KB**. Архивное сравнение: `1103_geometry.rs` (Rust 1.75 x64) — 0.015 s / 1160 KB (#11279171).

Текущая редакция 1103_geometry_implementation_optimized.rs только даёт
имя прежней встроенной ёмкости токена 32 байта. Геометрический алгоритм, простой
исходник и содержательные комментарии сохранены.

## Особенности языков

Учебные C++/Rust сравнивают произведения в 128 битах и выбирают через
nth_element/select_nth_unstable_by. Учебные Go/Java сортируют с длинными
произведениями; Python тоже использует точные неограниченные целые.
Отдельные быстрые Go/Java вместо этого сравнивают точные двухсловные
модули. Эти особенности относятся к названным версиям, а не всем исходникам.

Записи 18 ноября 2026 года описывают исторический срез. Текущее
сравнение исключает чужие времена ниже 0.015 s до выбора когорты,
а наши меньшие времена только для сравнения поднимает до этого порога.
Парные замеры Accepted остаются исходными. Применяется текущая общая политика.

`1103_geometry_optimized.java`: место по времени 1/16, по памяти 1/16 в этой сопоставимой выборке.

Текущий допуск задают общие [рейтинговые критерии](../../RATING_CRITERIA.md):
обычные топ-10/топ-15% либо эталон малой выборки точного компилятора,
когда он применим; ниже 1 МиБ — только время. Выигрыш 30% и отдельное
первое место по языку не дают допуск. Содержательные учебные версии
сохраняются без звёздочек целей оптимизации.

Описанные выше ревизии исходников уже получили собственные Accepted. В таблицах решений указаны итоговые номера посылок и парные измерения времени и памяти для соответствующих файлов; прежние наблюдения относятся к предыдущим ревизиям. Все содержательные простые реализации сохранены.
