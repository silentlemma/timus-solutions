# 1178. Разбить города на пары непересекающимися прямыми дорогами

[Timus 1178](https://acm.timus.ru/problem.aspx?space=1&num=1178) · сложность 151 · geometry

Автор оригинальной задачи — Павел Атнашев; третье личное первенство УрГУ по программированию, Екатеринбург, 16 февраля 2002 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Чётное число `N ≤ 10000` городов стоит в целых точках с координатами до
`10⁹` по модулю, никакие три не лежат на одной прямой. Соединить их
попарно прямыми дорогами, чтобы каждый город был ровно в одной дороге и
никакие две дороги не пересекались.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

`N`, затем `N` строк, в каждой две координаты города.

## Выходные данные

`N/2` строк, в каждой номера двух городов, которые соединяет дорога.

## Проверка

Принимается любой план, в котором каждый город ровно в одной паре и
никакие две дороги не встречаются; проверяющая программа сравнивает
дороги с перекрывающимися диапазонами по `x`.

## Примеры

### Пример 1

Ввод:

```
4
0 2
1 1
3 4
4 4
```

Вывод:

```
1 3
2 4
```

## Решение

Отсортируем города по `x` и соединим первый со вторым, третий с
четвёртым и так далее. Каждая дорога лежит в своей вертикальной полосе
между `x` своих концов, и полосы разных дорог пересекаются не больше чем
по одной граничной прямой. На этой прямой у каждой дороги только конец, и
концы — разные города, так что там дороги не встречаются. Дорога может
быть вертикальной, если её города имеют одинаковый `x`, но тогда на этой
прямой нет других городов, ведь никакие три не лежат на одной прямой.
Значит, никакие две дороги не встречаются. `O(N log N)`.

Тонкие места:

- равные `x` не требуют особой заботы, хотя решения упорядочивают их по
  `y`, чтобы вывод был воспроизводимым;
- координаты достигают `10⁹` и помещаются в 32-битные числа,
  а решение их только сравнивает.

Каждый выведенный план прошёл проверяющую программу на всех тестах,
включая десять тысяч городов на кониках с множеством общих `x`.

## Оптимизированные решения

Оптимизированное решение на Java разбирает числа вручную из буфера на
4 КБ, а не собирает все строки в одну строку для `StringTokenizer`, и
сортирует простой массив `long` вместо упакованных номеров `Integer` с
компаратором. Каждый ключ — это `x + 10⁹`, не больше 2·10⁹, то есть
31 бит, сдвинутое над 14-битным индексом города (он меньше 10000 < 2¹⁴).
В ключе только `x`: раз никакие три города не лежат на одной прямой,
общий `x` есть не более чем у двух, и один проход после сортировки
меняет местами такую соседнюю пару, если их `y` идут не по порядку:
{1178_geometry_optimized.java}.

Оптимизированное решение на Python полагается на то, что каждый город
стоит в своей строке, и читает строки по одной, а не разбивает весь
ввод. Каждый город упакован в одно целое — `x + 10⁹` и `y + 10⁹` по
31 биту над 14-битным номером города, — так что обычный `sort`
упорядочивает города по `(x, y)` без функции-ключа и кортежей, а пары
выводятся сразу, без списка строк: {1178_geometry_optimized.py}.

Оптимизированное решение на Rust разбирает числа вручную из буфера на
4 КБ, а не читает весь ввод в `String` и вектор всех чисел. Оно
сортирует кортежи `(x, y, номер)` из `i32`, которых хватает для
координат до `10⁹` по модулю, через `sort_unstable`, не требующую
дополнительного буфера, и выводит через `BufWriter`:
{1178_geometry_optimized.rs}.
