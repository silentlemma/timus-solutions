# 1184. Самые длинные равные куски, на которые можно разрезать кабели

[Timus 1184](https://acm.timus.ru/problem.aspx?space=1&num=1184) · сложность 244 · binary_search

Авторы оригинальной задачи — Владимир Пинаев и Роман Елизаров; полуфинал ACM ICPC Северо-Восточной Европы 2001–2002.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Из N кабелей нужно нарезать не менее K частей одной длины с точностью
до целого сантиметра. Каждая часть берётся из одного кабеля, соединять
остатки нельзя. Найдите наибольшую длину. `1≤N,K≤10000`. Длина каждого
кабеля от 1 м до 100 км включительно, задана точно до сантиметра.
Лимит времени — 1 секунда, памяти — 64 МБ.

## Входные данные

Первая строка содержит N и K. В каждой из следующих N строк записана
длина одного кабеля в метрах, ровно с двумя цифрами после десятичной точки.

## Выходные данные

Выведите наибольшую допустимую длину в метрах ровно с двумя дробными
цифрами. Если даже положительная целосантиметровая длина не даёт K частей,
выведите `0.00`.

## Проверка

Сравнивается единственный десятичный токен с ровно двумя дробными
цифрами. Каждая новая программа прошла 13 входов репозитория и 39
независимых дополнительных входов на целевом компиляторе или интерпретаторе.
Все 156 фактических дополнительных выводов и кодов завершения заново
сверены с точным рациональным эталоном: объединяем убывающие последовательности
`c/1,c/2,...` всех кабелей, берём K-е по величине значение и округляем
вниз до сантиметра. Такой эталон перебирает критические длины без
двоичного поиска по допустимости. Python-кандидат также запущен на
2889 наборах хоста; в малых случаях независимо проверена каждая целая
длина. Проверены 1,13 м, ответ 0,00, N/K=10000, сумма 10¹¹, максимум
длины, явные плюсы и сужение только после 64-битного минимума. 2889 —
запуски Python, не нативных программ. У четырёх публикуемых исходников
есть собственные Accepted точных байтов.

## Решение

Читаем длины как целые сантиметры c. При ровно двух дробных цифрах
удаление точки даёт точное число; двоичный float с умножением на 100
может ошибиться. Допустимы `100≤c≤10⁷`.

При положительной пробной длине L кабель даёт `floor(c/L)` частей.
Сумма `F(L)=Σ floor(c/L)` не возрастает, поэтому условие `F(L)≥K`
монотонно. Простые версии ищут наибольшее подходящее целое L двоичным
поиском от нуля до длины самого длинного кабеля. Ноль — признак
отсутствия положительного ответа, на него никогда не делим. Верхняя
середина положительна и при нулевой нижней границе, если поиск делает шаг.

Если L подходит, подходят все меньшие положительные длины. Если нет,
не подходят все большие. Сохраняя допустимую нижнюю сторону и отбрасывая
невозможную, получаем максимум при завершении. Выводим `L/100` и остаток
двумя цифрами, с ведущим нулём. Время `O(N log C)`, память `O(N)`,
где `C=max(c)≤10⁷`. Хранимые токены ввода также входят в память.
Нулевой ответ возможен, хотя каждый исходный кабель не короче метра.

## Оптимизированные решения

Файлы `_optimized` сохраняют тот же точный целочисленный двоичный
поиск, с доказанными более узкими границами и компактным вводом.
Пусть M — максимум, S — сумма длин. Один самый длинный кабель даёт
K частей длины `floor(M/K)`, поэтому `low=M/K` допустим при положительном
значении; ноль остаётся служебным ответом. Для любого допустимого L
верны `L≤M` и `K·L≤S`, значит `high=min(M,floor(S/K))`. Эти границы
не отсекают оптимум.

Пока low<high, берём `mid=(low+high+1)/2`; он положителен даже при low=0.
Счёт частей прекращаем после достижения K: остальные слагаемые
неотрицательны, результат проверки не изменится. Работа часто меньше,
но худшая оценка остаётся `O(N log C)`. Отдельные длины и границы
помещаются в 32 бита. Сумма S достигает `10¹¹`, поэтому нативные версии
накапливают её в 64 битах; счёт частей также широкий. В частности,
`S/K` сначала сравниваем с M в 64 битах, потом сужаем. Регрессия
`S/K=2³²+100` выявляет неверное сужение до взятия минимума.

C++ и Java читают ограниченные буферы байтов сразу в 32-битные массивы,
пропуская точку числового токена. Java устраняет строку всего ввода,
массив long и локализованное форматирование. Rust использует ограниченный
буфер и Vec из u32 без полной строки ввода и замен в каждом токене.
CPython читает предписанные строки кабелей в `array('I')`, не удерживая
все токены и список отдельных объектов int. Буферы ограничены, массив
длин остаётся линейным. Все пять понятных баз сохранены побайтово.

Память Accepted точных байтов: C++ 168 против 280 КБ, меньше на 40,0%;
Java 448 против 6284 КБ, меньше на 92,9%; Python 516 против 1580 КБ,
меньше на 67,3%; Rust 220 против 420 КБ, меньше на 47,6%. C++
0,031→0,015 с различаются лишь на один шаг таймера судьи: время само
по себе не используется для допуска. Java 0,125→0,093 с; Python остаётся
0,078 с, Rust — 0,015 с. Все четыре версии проходят критерий по
измеренной памяти независимо от шума таймера.

## Особенности языков

Все пять прежних реализаций сохраняют прямолинейный двоичный поиск.
Новый Python принят в CPython 3.12, метрики PyPy не подставляются.
C++, Java и Rust достигли текущего рейтингового профиля. Python второй
по времени и первый по памяти в снимке, поэтому допущенная строка
сохраняет звёздочку и пространство для улучшения. Для Go нет допустимых
чужих посылок: база даёт формальное покрытие, не доказательство
превосходства. Для C++ цель — топ 15% либо первые десять мест по обеим
метрикам, для остальных — первое место по обеим. Каждый выигрыш памяти
сравнивается со своей неизменённой простой Accepted-базой на том же языке.
