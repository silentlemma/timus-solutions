# 1190. 只标出部分含量的巧克力配料表能否诚实

[Timus 1190](https://acm.timus.ru/problem.aspx?space=1&num=1190) · 难度 338 · greedy

原题作者 Leonid Volkov，出自 2002 年 3 月 2 日第五届中学生团体程序设计锦标赛。

[English](README.md) · [Русский](README.ru.md) · **中文** · [Español](README.es.md)

## 任务

配料表按含量不增的顺序列出 `N ≤ 5000` 种配料；其中一些标出了含量，单位是万分之
一（百分之一的百分之一）。每种配料的真实含量是 1 到 10000 之间的整数，且总和恰为
100%。判断是否存在与顺序和所有标出值都相符的真实含量。

时间限制：1 秒。内存限制：64 MB。

## 输入

`N`，然后对每种配料给出名称、`0`，或者 `1` 及其含量。

`1 ≤ N ≤ 5000`。名称互不相同，长度为 1 到 16 个字符，只能包含英文字母、连字符
和下划线。标出含量是 1 到 10000 之间的整数，并保证按其在配料表中的出现顺序不增，
即使中间有未标出含量的配料也是如此。

## 输出

`YES` 或 `NO`。

## 评测方式

仓库测试精确比较输出记号，记号之间的空白分隔不影响结果。

## 样例

### 样例 1

输入：

```
4
Water 0
Cocoa-butter 0
Cocoa-powder 1 4000
Lecithin 0
```

输出：

```
NO
```

## 解法

输入保证标出含量已经按不增顺序排列；下面的两次扫描依赖这一前提。

由于含量沿列表向下不增，一个未标出含量的配料至少等于它下方最近的标出值（没有则
为 1），至多等于它上方最后一个标出值（没有则为 10000）。标出值是固定的。所有含量
都取最小值，得到总和最小的合法不增序列；都取最大值，得到总和最大的序列。

两者之间的每个总和也都能达到：从最小序列出发，把第一个含量逐一增加到它的最大值，
再增加第二个，依此类推；序列始终保持不增，每一步总和增加一。所以答案为 `YES`
当且仅当最小总和不超过 10000 且最大总和不小于 10000。`O(N)`。

注意事项：

- 未知含量也至少为 1，这可能使最小总和超过 100%（测试 `06`）；
- 标出含量递增的输入违反输入保证，不能作为两次扫描方法的反例；
- 若上方没有标出值，未知含量最多可以到 100%，而不只到第一个标出值；
- 完全没有标出值的配料表总是诚实的，因为 `N ≤ 5000` 个至少为 1 的含量放得进 10000。

答案已在 2000 份随机配料表和全部六个已保存测试上与精确的动态规划判定程序比对，
生成的测试也已检查。

## 优化解法

C++ 和 Go 读到下一个已知配料占比时，立即处理此前连续未知的占比。当前已知值是这段的下界，前一个已知值是上界。末尾未知段的下界为一。只保留段长、前一个占比和总和的两个边界，辅助空间为常数。

已通过评测的基础实现 [1190_greedy.java](1190_greedy.java), [1190_greedy.py](1190_greedy.py), [1190_greedy.rs](1190_greedy.rs) 也满足快速版本的要求：在保存的比较快照中，时间和内存均符合前 15% 或前十名的排名收录规则。直接复用这些源文件，不创建相同副本。星号标记尚未达到该语言目标排名的版本。

`1190_greedy_optimized.java`. Java 保留简单版本所述的算法和数据结构。固定字节缓冲区与 FastInput 替代 Scanner 及其正则表达式、区域设置处理。整数记号直接解析；需要字符串时仍进行 UTF-8 解码，十进制记号仍显式转换为数值。仅在需要前瞻时保存一个记号，输出算法不变。这样减少通用解析开销；表中列出算法工作量，输入扫描与字节数成正比，并使用有界输入缓冲区。

与 `1190_greedy.java` 相比：时间 0.171 s → 0.14 s；内存 6296 KB → 1 308 KB。
