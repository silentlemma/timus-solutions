# 1106. Разбиение графа, при котором у каждой вершины есть сосед на другой стороне

[Timus 1106](https://acm.timus.ru/problem.aspx?space=1&num=1106) · сложность 74 · bfs

Автор оригинальной задачи — Дмитрий Филимоненков; Tetrahedron Team Contest, май 2001 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Неориентированный граф имеет `N ≤ 100` вершин, и у каждой вершины есть
хотя бы один сосед. Разбить вершины на две группы так, чтобы у каждой
вершины был сосед в другой группе. Если это невозможно, вывести `0`.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

`N`, затем `N` строк: строка `i` перечисляет соседей вершины `i` и
заканчивается `0`. Списки симметричны.

## Выходные данные

Размер первой группы, затем во второй строке её вершины через одиночные
пробелы.

## Проверка

Подходит любое правильное разбиение. Проверяющая программа убеждается,
что перечисленные вершины различны и их число совпадает с размером, и что
у каждой вершины, в первой группе или нет, есть сосед на другой стороне.

## Примеры

### Пример 1

Ввод:

```
7
2 3 0
3 1 0
1 2 4 5 0
3 0
3 0
7 0
6 0
```

Вывод:

```
4
1 4 5 6
```

## Решение

Разбиение существует всегда, так что `0` не выводится никогда. Запустим
BFS из каждой ещё не достигнутой вершины и отправим каждую вершину в
группу по чётности её глубины в дереве BFS. Вершина, не являющаяся
корнем, оказывается по другую сторону от своего родителя; у корня есть
хотя бы один сосед, и этот сосед — его ребёнок в дереве на глубине 1.
Важны только рёбра дерева, поэтому нечётные циклы не мешают. `O(N + M)`
для `M` пар друзей.

Тонкие места:

- это не проверка на двудольность: треугольник нельзя правильно
  раскрасить в два цвета, но он прекрасно делится как одна вершина против
  двух;
- в графе может быть несколько компонент, и каждой нужен свой корень BFS.

Ответы проверены проверяющей программой на всех тестах и на сотнях
случайных графов всех четырёх видов генератора.

## Оптимизированные решения

Оптимизированные решения (Go, Java) разбирают ввод вручную из буфера,
хранят соседей каждой вершины в байтах — вершин не больше 100 — и ведут
BFS по обычному массиву в роли очереди. Команда вершины хранится как 1
или 2, а 0 означает, что вершина ещё не достигнута, так что один массив
заменяет и отметки о посещении, и цвета. Java собирает соседей вершины в
буфер из `n` байт и затем копирует их в массив точного размера: строка
перечисляет соседей своей вершины среди остальных `n - 1` вершин,
каждого по одному разу, поэтому в ней меньше `n` элементов. Go: 948 КБ
вместо 1480 КБ при том же времени; Java: 0.093 с вместо 0.125 с и
420 КБ вместо 748 КБ.

Оптимизированное решение на Python разбирает ввод построчно, хранит
списки смежности и стороны в `bytearray` (вершин не больше 100) и
обходит обычный список как очередь: 548 КБ вместо 964 КБ при том же
времени.

## Особенности языков

- Rust берёт каждый список через `take_while` на общем итераторе
  токенов.
