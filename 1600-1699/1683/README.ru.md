# 1683. Холодильник

[Timus 1683](https://acm.timus.ru/problem.aspx?space=1&num=1683) · сложность 137 · greedy

Автор оригинальной задачи — Станислав Васильев; X открытое личное первенство УрГУ, 28 февраля 2009 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Бумажную полоску шириной 1 см и длиной n см складывают в квадрат
1 × 1 см из n слоёв. При каждом сгибе от левого края отмеряется целое
число сантиметров, и эта часть загибается направо, так что левый край
сдвигается на отмеренную длину. Найти наименьшее число сгибов и
отмеренные длины.

## Входные данные

n (1 ≤ n ≤ 10⁹).

## Выходные данные

Число сгибов, затем отмеренные длины по порядку. Подходит любая
кратчайшая последовательность.

## Проверка

В репозитории используется проверяющая программа, принимающая любой вывод с указанными свойствами. Проверка репозитория требует оптимальное число складок из эталона и ровно столько целых длин. Для каждой x выполняется1<=x<=current-x, затем current уменьшается на x; итоговая длина равна единице. Принимается любая кратчайшая допустимая последовательность.

## Примеры

### Пример 1

Ввод:

```
12
```

Вывод:

```
4
5 3 2 1
```

## Решение

Загнуть x см полоски длины L можно, только если загнутая часть
помещается на остальной, x ≤ L − x, и тогда остаётся полоска длины
L − x ≥ ⌈L / 2⌉. Значит, никакой сгиб не уменьшает полоску больше чем
вдвое с округлением вверх, а загибание ⌊L / 2⌋ каждый раз ровно этого
и достигает: число сгибов — наименьшее m с 2ᵐ ≥ n. `O(log n)`.

Подводные камни:

- при n = 1 сгибы не нужны: выводятся 0 и пустой список;
- 5 3 2 1 из примера — один из многих ответов, поэтому чекер сравнивает
  количество и воспроизводит сгибы.

Чекер воспроизводит каждый сгиб и сравнивает количество с жадным.

## Оптимизированные решения

`1683_greedy_optimized.py`. Сохраняется складывание floor(length/2) слева с остатком ceil(length/2). Допустимая складка не уменьшает полосу быстрее, поэтому минимум равен ceil(log2 n), включая ноль складок при n=1. Выполняется O(log n) шагов с ограниченными целыми при n<=10^9. Число складок считается как (n-1).bit_length() до построения длин. Все строки длин по-прежнему сохраняются и склеиваются, поэтому дополнительная память вывода остаётся O(log n). Самостоятельная программа для судьи явно сбрасывает stdout перед os._exit(0), пропуская обычное завершение интерпретатора. Выигрыш памяти подтверждён её собственным Accepted. Сама смена способа завершения не улучшает асимптотику, а её эффект в среде выполнения не гарантируется на других платформах. Простая версия сохранена без изменений.

По сравнению с `1683_greedy.py`: время 0.125 s → 0.125 s; память 372 KB → 208 KB.

`1683_greedy_optimized.rs`. Сохраняется складывание floor(length/2) слева с остатком ceil(length/2). Допустимая складка не уменьшает полосу быстрее, поэтому минимум равен ceil(log2 n), включая ноль складок при n=1. Выполняется O(log n) шагов с ограниченными целыми при n<=10^9. Первый проход делений считает складки, второй повторяет те же шаги с непосредственным выводом. Vec<String> и склейка ответа не нужны: O(1) дополнительного состояния и два прохода O(log n). Rust-версия читает и пишет через среду выполнения C, без сохранения декодированной входной String и построения форматированной строки ответа. Простой исходник с Accepted сохранён.

По сравнению с `1683_greedy.rs`: время 0.015 s → 0.062 s; память 244 KB → 52 KB.

Оптимизированное решение на C++ хранит сгибы в массиве фиксированного
размера на 30 чисел на стеке вместо растущего `std::vector`. При
n ≤ 10⁹ < 2³⁰ не больше 30 делений пополам сводят полоску к 1 см, так
что массива всегда хватает и программа сама ничего не выделяет в куче:
{1683_greedy_optimized.cpp}.

Оптимизированное решение на Java читает единственную строку через
`BufferedReader` и переводит её в число через `Long.parseLong` вместо
того, чтобы создавать `Scanner`, чьи регулярные выражения и данные
локали обходятся гораздо дороже 30 делений пополам:
{1683_greedy_optimized.java}.
