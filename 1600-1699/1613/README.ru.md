# 1613. Для любителей статистики

[Timus 1613](https://acm.timus.ru/problem.aspx?space=1&num=1613) · сложность 141 · binary_search

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Трамваи каждого из n городов (1 ≤ n ≤ 69 999) перевезли за год некоторое
число людей, от 1 до 10⁹ − 1. Для каждого из q запросов (1 ≤ q ≤ 69 999)
`l r x` скажите, есть ли среди городов с номерами от l до r такой, что
перевёз ровно x человек. Выведите строку из q символов: `1` — да,
`0` — нет.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

n, n чисел, q, затем q строк `l r x`, где 1 ≤ l ≤ r ≤ n и 1 ≤ x < 10⁹.

## Выходные данные

Строка ответов.

## Примеры

### Пример 1

Ввод:

```
5
1234567 666666 3141593 666666 4343434
5
1 5 3141593
1 5 578202
2 4 666666
4 4 7135610
1 1 1234567
```

Вывод:

```
10101
```

## Решение

Отсортируем пары (число, номер города). Города с числом x тогда идут
одним блоком, по возрастанию номеров. Для запроса двоичный поиск
находит первую пару, не меньшую (x, l): ответ «да», если её число равно
x, а город не больше r. `O((n + q) log n)`.

Подводные камни:

- ответ — одна строка без разделителей;
- город нужно найти не раньше l, а не просто где-нибудь с числом x
  (тест 04).

## Оптимизированные решения

Оптимизированное решение на C++ разбирает числа вручную из буфера на
4 КБ вместо `scanf` и упаковывает каждую пару в один `uint64_t`: число
пассажиров, меньшее 10⁹ < 2³⁰, над 17 битами номера города, так как
`n ≤ 69 999 < 2¹⁷`. Массив постоянного размера из таких ключей
сортируется как обычные числа, запрос — это один `lower_bound` для
`(x << 17) + l` и сравнение с `(x << 17) + r`, а каждый ответ выводится
через `putchar`, а не собирается в `std::string`:
{1613_binary_search_optimized.cpp}.

Оптимизированное решение на Go разбирает числа побайтно из
`bufio.Reader` вместо `bufio.Scanner` с буфером на 1 МБ и `strconv.Atoi`
и заменяет четыре среза `int` — числа пассажиров, города и порядок —
одним срезом `uint64` с упакованными парами: число пассажиров, меньшее
10⁹ < 2³⁰, над 17 битами номера города, так как `n ≤ 69 999 < 2¹⁷`.
Запрос — это один `sort.Search` для `(x << 17) + l` и сравнение с
`(x << 17) + r`, а ответы пишутся прямо в `bufio.Writer`:
{1613_binary_search_optimized.go}.

Оптимизированное решение на Java разбирает числа вручную из буфера на
64 КБ вместо `StreamTokenizer` и упаковывает каждую пару в один `long`,
число пассажиров над 17 битами номера города (`n ≤ 69 999 < 2¹⁷`).
Сортировке простого массива `long` не нужны ни объект `int[]` на каждый
город, ни компаратор, а запрос — это один `Arrays.binarySearch` для
`(x << 17) | l`: {1613_binary_search_optimized.java}.

Оптимизированное решение на Python читает ввод кусками по 8 КБ и
преобразует токены кусок за куском, а не разбивает весь ввод сразу.
Каждая пара упакована в одно целое, число пассажиров над 17 битами
номера города (`n ≤ 69 999 < 2¹⁷`), так что отсортированный список
хранит простые целые вместо кортежей, а ответы собираются в `bytearray`
вместо списка строк: {1613_binary_search_optimized.py}.

Оптимизированное решение на Rust разбирает числа вручную из буфера на
4 КБ, а не читает весь ввод, примерно до 2 МБ, в `String`;
отсортированные пары и двоичный поиск те же:
{1613_binary_search_optimized.rs}.
