# 1671. Паутина Ананси

[Timus 1671](https://acm.timus.ru/problem.aspx?space=1&num=1671) · сложность 105 · dsu

Автор оригинальной задачи — Дмитрий Полетаев (подготовка — Алексей Самсонов); Ural SU Contest, Петрозаводские летние сборы, август 2008 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Паутина состоит из N узлов и M нитей между парами узлов. Q нитей рвут по
одной в заданном порядке. После каждого обрыва нужно вывести, на сколько
кусочков (связных частей) распадается паутина.

## Входные данные

N и M (2 ≤ N ≤ 100000, 1 ≤ M ≤ 100000), M нитей — пары различных
узлов с номерами от 1 до N, затем Q (1 ≤ Q ≤ M) и номера рвущихся нитей,
все различные; нити нумеруются от 1 до M в порядке ввода.

## Выходные данные

Q чисел кусочков через пробел.

## Примеры

### Пример 1

Ввод:

```
4 4
1 2
2 3
1 3
3 4
3
2 4 3
```

Вывод:

```
1 2 3
```

### Пример 2

Ввод:

```
3 1
1 2
1
1
```

Вывод:

```
3
```

## Решение

Следить за разрывами трудно, а соединять легко с помощью системы
непересекающихся множеств, поэтому процесс идёт задом наперёд. Начнём с
паутины после всех обрывов: соединим все нити, которые не рвутся. Затем
пройдём по обрывам от последнего к первому: текущее число кусочков —
ответ после этого обрыва, а потом нить возвращается на место. Каждое
соединение двух разных множеств уменьшает число на единицу. Со сжатием
путей это `O((N + M) log N)`.

Подводные камни:

- одни и те же два узла могут соединять несколько нитей, и обрыв одной
  из них ничего не меняет (тест 03);
- ответ после обрыва — это число до возвращения этой нити.

Ответы совпадают с пересчётом кусочков поиском после каждого обрыва на
200 малых случайных паутинах.

## Оптимизированные решения

Оптимизированное решение на C++ разбирает числа вручную из блоков по
8 КБ, прочитанных через `fread`, вместо вызова `scanf` для каждого,
объединяет по размеру, храня в корне размер его множества со знаком
минус, чтобы деревья оставались неглубокими, записывает каждый ответ на
место его обрыва, когда этот обрыв уже обработан, вместо второго массива
и печатает ответы через `printf`, а не собирает их в строку:
{1671_dsu_optimized.cpp}.

Оптимизированное решение на Go разбирает числа побайтово из
буферизованного reader на 64 КБ и печатает их через `strconv` в writer
на 64 КБ вместо `fmt.Fscan` и `fmt.Fprint`; система непересекающихся
множеств та же: {1671_dsu_optimized.go}.

Оптимизированное решение на Java разбирает числа вручную из блоков по
8 КБ вместо `StreamTokenizer`, объединяет по размеру, храня в корне
размер его множества со знаком минус, чтобы деревья оставались
неглубокими, записывает каждый ответ на место его обрыва, когда этот
обрыв уже обработан, вместо второго массива и печатает цифры через
байтовый буфер на 8 КБ, а не собирает вывод в `StringBuilder`:
{1671_dsu_optimized.java}.

Оптимизированное решение на Python читает ввод построчно и хранит концы
нитей и номера обрывов в массивах 32-битных беззнаковых целых, которых
хватает, ведь эти числа не больше 100000, а не держит каждый токен ввода
как байтовую строку; оно объединяет по размеру, храня в корне размер его
множества со знаком минус, чтобы деревья оставались неглубокими, и
записывает каждый ответ на место его обрыва, когда этот обрыв уже
обработан, вместо второго списка: {1671_dsu_optimized.py}.

Оптимизированное решение на Rust разбирает числа прямо из байтов ввода,
а не собирает их сначала в вектор, хранит нити как пары `u32`, а
родителей как `i32` вместо `usize` (этих типов хватает, ведь N и M не
больше 100000), объединяет по размеру, храня в корне размер его
множества со знаком минус, чтобы деревья оставались неглубокими,
записывает каждый ответ на место его обрыва, когда этот обрыв уже
обработан, и печатает через `BufWriter`, а не склеивает вектор строк:
{1671_dsu_optimized.rs}.
