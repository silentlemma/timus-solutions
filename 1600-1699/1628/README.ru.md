# 1628. Белые полосы

[Timus 1628](https://acm.timus.ru/problem.aspx?space=1&num=1628) · сложность 164 · implementation

Автор оригинальной задачи — Александр Ипатов; XIII открытый командный чемпионат УрГУ по программированию.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Календарь — таблица m × n: строка i — неделя, столбец j — день недели.
Некоторые k клеток закрашены чёрным (неудачные дни), остальные белые.
Отрезок — прямоугольник клеток 1 × l или l × 1. Нужно посчитать белые
полосы: максимальные по включению белые отрезки.

## Входные данные

В первой строке m, n и k (1 ≤ m, n ≤ 30000, 0 ≤ k ≤ 60000). В каждой из
следующих k строк — чёрная клетка x y (1 ≤ x ≤ m, 1 ≤ y ≤ n); клетки
различны.

## Выходные данные

Количество белых полос.

## Примеры

### Пример 1

Ввод:

```
3 5 4
1 1
1 5
2 2
3 3
```

Вывод:

```
8
```

### Пример 2

Ввод:

```
5 1 2
2 1
3 1
```

Вывод:

```
2
```

## Решение

В каждой строке чёрные клетки делят её на белые участки, и в каждом
столбце так же. Участок длины 2 и больше — полоса. Одиночная белая
клетка устроена иначе: это отрезок 1 × 1 сразу в обоих направлениях,
поэтому она считается один раз и только если не растёт ни в одну
сторону, то есть её соседи по строке и по столбцу все чёрные или за
краем таблицы. Иначе клетка уже лежит в более длинной полосе.

Итак, строки считают свои участки длины не меньше 2 плюс одиночные
клетки, закрытые сверху и снизу, а столбцы — только участки длины не
меньше 2. Каждая строка и каждый столбец сортируют свои чёрные клетки,
а множество проверяет соседей: в C++ упорядоченное, в остальных — хеш-множество.
C++: `O(m + n + (m + k) log(k + 1))`; остальные: `O(m + n + k log k)`.

Подводные камни:

- одиночную белую клетку нельзя считать дважды, по разу на направление
  (тест 05);
- при одной строке или одном столбце каждая белая клетка закрыта краем
  в другом направлении (второй пример);
- в полностью белой таблице при m, n > 1 есть m + n полос, так что
  строки и столбцы без чёрных клеток тоже считаются (тест 06).

Ответы совпадают с независимой принятой реализацией на 120 случайных
календарях и на самом большом.

## Оптимизированные решения

Оптимизированное решение на C++ хранит два плоских массива ключей вместо
`vector` на каждую строку и столбец и `set` пар: `x · (n + 2) + y`
упорядочивает чёрные клетки по строкам, `y · (m + 2) + x` — по столбцам.
После сортировки один проход по каждому массиву обходит все строки или
все столбцы, а одиночная белая клетка проверяется сверху и снизу
двоичным поиском ключей её соседей в массиве строк. Ключи меньше
`30000 · 30002 + 30001 < 2³¹`, ведь m, n ≤ 30000, поэтому помещаются в
`int`. Числа разбираются вручную из буфера на 4 КБ, который пополняется
через `fread`: {1628_implementation_optimized.cpp}.

Оптимизированное решение на Go хранит два плоских среза ключей вместо
среза на каждую строку и столбец и хеш-множества клеток:
`x · (n + 2) + y` упорядочивает чёрные клетки по строкам,
`y · (m + 2) + x` — по столбцам. После сортировки один проход по каждому
срезу обходит все строки или все столбцы, а одиночная белая клетка
проверяется сверху и снизу двоичным поиском ключей её соседей в срезе
строк. Числа разбираются вручную из буфера на 4 КБ вместо `fmt.Fscan`:
{1628_implementation_optimized.go}.

Оптимизированное решение на Java хранит два плоских массива ключей `int`
вместо массива на каждую строку и столбец и `HashSet` ключей `Long`:
`x · (n + 2) + y` упорядочивает чёрные клетки по строкам,
`y · (m + 2) + x` — по столбцам. После сортировки один проход по каждому
массиву обходит все строки или все столбцы, а одиночная белая клетка
проверяется сверху и снизу двоичным поиском ключей её соседей в массиве
строк. Ключи меньше `30000 · 30002 + 30001 < 2³¹`, ведь m, n ≤ 30000,
поэтому помещаются в `int`. Числа разбираются вручную из блоков ввода по
4 КБ: {1628_implementation_optimized.java}.

Оптимизированное решение на Python хранит два плоских списка целых
ключей вместо списка на каждую строку и столбец и множества кортежей
координат: `x · (n + 2) + y` упорядочивает чёрные клетки по строкам,
`y · (m + 2) + x` — по столбцам. После сортировки один проход по каждому
списку обходит все строки или все столбцы, а одиночная белая клетка
проверяется сверху и снизу через `bisect_left` по ключам её соседей в
списке строк. Ввод читается кусками по 4 КБ, а не целиком:
{1628_implementation_optimized.py}.

Оптимизированное решение на Rust хранит два плоских вектора ключей `i32`
вместо вектора на каждую строку и столбец и хеш-множества клеток:
`x · (n + 2) + y` упорядочивает чёрные клетки по строкам,
`y · (m + 2) + x` — по столбцам. После сортировки один проход по каждому
вектору обходит все строки или все столбцы, а одиночная белая клетка
проверяется сверху и снизу двоичным поиском ключей её соседей в векторе
строк. Ключи меньше `30000 · 30002 + 30001 < 2³¹`, ведь m, n ≤ 30000,
поэтому помещаются в `i32`. Числа разбираются вручную из буфера на 4 КБ
вместо чтения всего ввода в `String`:
{1628_implementation_optimized.rs}.
