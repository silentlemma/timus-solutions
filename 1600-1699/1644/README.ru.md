# 1644. Куча орехов

[Timus 1644](https://acm.timus.ru/problem.aspx?space=1&num=1644) · сложность 100 · implementation

Автор оригинальной задачи — Алексей Самсонов; осеннее первенство школьников, октябрь 2008 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

В каждом из n экспериментов Попугай съедал от 3 до 9 орехов и
записывал, остался ли голодным или наелся. Сытость монотонна: от
большего числа орехов голоднее не станешь. Известно, что десяти орехов
всегда хватает, а двух никогда. Нужно найти наименьшее число орехов,
которого наверняка хватит, или сообщить, что записи противоречат друг
другу.

## Входные данные

n (0 ≤ n ≤ 100), затем n строк: число орехов и `hungry` или
`satisfied`.

## Выходные данные

Наименьшее число орехов, которого наверняка хватит, или `Inconsistent`.

## Проверка

Тесты репозитория точно сравнивают токены вывода; пробельные разделители между ними несущественны.

## Примеры

### Пример 1

Ввод:

```
4
4 hungry
7 satisfied
5 hungry
8 satisfied
```

Вывод:

```
7
```

### Пример 2

Ввод:

```
2
6 hungry
5 satisfied
```

Вывод:

```
Inconsistent
```

## Решение

Возьмём наибольшее «голодное» количество, начиная с 2, и наименьшее
«сытое», начиная с 10. Записи согласуются с монотонным порогом ровно
тогда, когда второе больше; тогда ответ — наименьшее «сытое» количество,
ведь меньшее никогда не давало сытости. Иначе `Inconsistent`. `O(n)`.

Подводные камни:

- без записей ответ 10 (тест 03), и только с «голодными» записями ответ
  тоже 10 (тест 04);
- одно и то же количество, записанное двумя способами, — противоречие
  (тест 06).

Ответы совпадают с независимой принятой реализацией на 180 случайных
наборах записей.

## Оптимизированные решения

`1644_implementation_optimized.java`. Java хранит две монотонные границы: максимальное число при голоде, изначально 2, и минимальное при сытости, изначально 10. Ответ различается по первой букве; остаток токена пропускается без создания строки. При hungry>=full последующие наблюдения уже не исправят противоречие, поэтому Inconsistent выводится сразу. Иначе итоговая верхняя граница — минимальное заведомо достаточное число; без наблюдений ответ 10. Фиксированные байтовые буферы и прямой вывод дают в худшем случае O(N) времени и O(1) дополнительной памяти.

Accepted точного исходника Java 1.8 №11327467: 0.109 с / 412 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 17/121, память 3/121. При памяти меньше 1024 КБ строгий допуск учитывает только время: первые десять мест или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка: первого места по обеим метрикам. Прежний документированный оптимизированный запуск №11303630: 0.125 с / 400 КБ; это отдельная историческая пара, не текущий замер данного исходника. Учебные версии сохранены без изменений.

- `1644_implementation_optimized.java`: 0.109 s / 412 KB; сохранённая учебная база `1644_implementation.java`: 0.125 s / 1708 KB.

`1644_implementation_optimized.py` используется побайтово без изменений, без второго исходника и нового алгоритма. Accepted точного исходника на CPython 3.12 №11327032: 0.078 с / 736 КБ. Сохранённая выборка актуальных компиляторов семейства Python от 2026-11-20: место по времени 3/53, по памяти 50/53. Поскольку здесь меньше 1024 КБ, строгий критерий первых десяти мест или топ 15% учитывает только время; звёздочка сохраняет отдельную рейтинговую цель языка. У того же файла есть прежний Accepted на PyPy 3.10 №11325477: 0.156 с / 212 КБ. Это парные замеры разных запусков: CPython даёт выбранный результат по времени и рейтингу, PyPy расходует меньше памяти. Прежние замечания об экономии памяти в этом разделе относятся к этому замеру PyPy, а не к строке CPython. Все учебные исходники сохранены без изменений.

`1644_implementation_optimized.py`. Сохраняются максимум наблюдений hungry и минимум full с начальными 2 и 10. Перебираются ровно n пар число/байтовый ответ без двух списочных срезов с шагом. Граница full выводится только когда строго больше hungry. Алгоритму нужны два экстремума, но токены входа остаются: время O(n), общая память O(I) для размера входа I. В строке Accepted указаны фактическая среда судьи и парные время/память. Вывод сбрасывается до os._exit(0), пропускающего завершение интерпретатора; измеренный выигрыш памяти относится к этой среде и не означает асимптотического ускорения.

По сравнению с `1644_implementation.py`: время 0.109 s → 0.156 s; память 444 KB → 212 KB.

Оптимизированное решение на C++ читает через `scanf` в небольшой массив
`char` вместо `iostream` и `std::string` и различает два слова по первой
букве: 128 КБ вместо 388 КБ при том же времени.

`1644_implementation_optimized.rs`. Обновляются лишь наибольшее наблюдение «голоден» и наименьшее «сыт». Два слова ответа из условия различаются по первому байту, оставшаяся часть токена пропускается без выделения строки. Интервал согласован тогда и только тогда, когда верхняя граница больше нижней. Время O(N), дополнительное состояние O(1). Rust использует среду выполнения C для ввода-вывода, без целых декодированных строк String и форматирования Rust. Простой принятый исходник сохранён без изменений.

По сравнению с `1644_implementation.rs`: время 0.015 s → 0.031 s; память 220 KB → 64 KB.

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Приведённые ниже места относятся к новым версиям; прежние исходники сохраняют собственные исторические метрики Accepted.

Прежнее сравнение PyPy: `1644_implementation_optimized.py`: место по времени 53/53, по памяти 1/53 в этой сопоставимой выборке.

`1644_implementation_optimized.rs`: сопоставимых чужих результатов недостаточно для рейтингового вывода; допуск основан на измеренном улучшении относительно простой версии.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
