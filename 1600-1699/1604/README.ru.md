# 1604. В Стране Дураков

[Timus 1604](https://acm.timus.ru/problem.aspx?space=1&num=1604) · сложность 139 · greedy

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Есть k видов знаков ограничения скорости, nᵢ знаков вида i, всего не
больше 10000 знаков. Нужно расставить их все вдоль трассы так, чтобы
водителям приходилось как можно чаще менять скорость: смена происходит
на первом знаке и на каждом знаке, отличном от предыдущего. Подходит
любой лучший порядок.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

k, затем n₁, …, nₖ, где 1 ≤ k ≤ 10000, каждое nᵢ положительно,
а их сумма не больше 10000.

## Выходные данные

Виды знаков в порядке вдоль трассы.

## Примеры

### Пример 1

Ввод:

```
2
2 2
```

Вывод:

```
1 2 1 2
```

## Решение

Менять скорость как можно чаще — значит иметь как можно меньше равных
соседей. Пусть m — наибольшее количество, а n — общее. Остальные n − m
знаков делят m знаков самого частого вида не больше чем на n − m + 1
групп, так что равных соседей не меньше max(0, 2m − n − 1).

Жадный порядок достигает этой оценки: всегда ставится вид, у которого
осталось больше всего знаков, если только он не был предыдущим знаком;
тогда ставится вид со вторым по величине остатком. Куча выдаёт оба за
`O(log k)`, так что весь порядок строится за `O(n log k)`.

Тесты проверяет чекер, который считает равных соседей и сравнивает их с
оценкой. Сама оценка сверена с полным перебором всех порядков для
небольших наборов знаков.

Подводные камни:

- равных соседей не избежать ровно при 2m > n + 1, и жадность ставит
  их вместе в конце (тест 05); при 2m = n + 1 равных соседей ещё можно
  избежать (тесты 02 и 04);
- если всегда брать самый частый вид, не глядя на предыдущий знак, он
  повторится; если брать виды по очереди, не глядя на количества, другие
  виды могут кончиться слишком рано (тест 07).

## Оптимизированные решения

Оптимизированное решение на C++ упаковывает вид и число его знаков в
один `int`, число·2¹⁴ + вид: оба не больше 10000, то есть меньше
2¹⁴ = 16384, так что поля не перекрываются, а сравнение упакованных
чисел сравнивает сначала количества, потом виды, как и для пар. Куча —
это массив фиксированного размера на 10000 таких чисел под управлением
`std::push_heap` и `std::pop_heap` вместо `priority_queue` из пар, а
виды печатаются через `printf` по мере выбора, а не собираются в строку:
{1604_greedy_optimized.cpp}.

Оптимизированное решение на Go реализует свою кучу на срезе знаков с
запасом на k элементов вместо `container/heap`, который превращает
каждый добавляемый и извлекаемый знак в значение `interface{}` и
выделяет под него память. Числа разбираются побайтно из `bufio.Reader`
вместо `fmt.Fscan`: {1604_greedy_optimized.go}.

Оптимизированное решение на Java передаёт `PriorityQueue` обычный класс
`Comparator` вместо лямбды, первое использование которой подгружает
дополнительную машинерию среды выполнения. Когда вид ставится на дорогу,
его массив всё равно извлечён из кучи, поэтому решение уменьшает счётчик
прямо в нём и возвращает его обратно вместо создания нового массива на
каждый знак. Виды выводятся через `BufferedWriter` вместо
`StringBuilder`: {1604_greedy_optimized.java}.

Оптимизированное решение на Python упаковывает элемент кучи
(−число, вид) в одно целое −число·(k + 1) + вид вместо кортежа: вид
лежит от 1 до k, ниже основания k + 1, поэтому целые сравниваются точно
так же, как кортежи, а `divmod` восстанавливает оба поля. Оно читает
ввод как байты, освобождает список токенов перед основным циклом и
пишет виды порциями по 256 вместо хранения всего порядка в памяти:
{1604_greedy_optimized.py}.

Оптимизированное решение на Rust пишет каждый вид через `BufWriter` по
мере выбора вместо того, чтобы собирать до 10000 строк в `Vec` и
склеивать их в ещё одну строку: {1604_greedy_optimized.rs}.
