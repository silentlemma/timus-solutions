# 1727. 万事通的魔法数

[Timus 1727](https://acm.timus.ru/problem.aspx?space=1&num=1727) · 难度 202 · greedy

原题作者 Ivan Burmistrov，出自 2009 年乌拉尔地区程序设计团队竞赛。

[English](README.md) · [Русский](README.ru.md) · **中文** · [Español](README.es.md)

## 任务

找出一组互不相同、小于 10⁵ 的正整数，使它们所有数字之和为 n；若不存在则输出 −1。

## 输入

n（0 < n < 10⁵）。

## 输出

集合的大小，然后是其中的数；或者 −1。任何符合要求的集合都可以。

## 评测方式

使用构造检查器，不与单一样例逐字比较。检查声明数量、正整数小于
100000、无重复、全部十进制数字和等于目标。五份新源码各通过 13 个仓库
Docker 输入，并各有自身精确 SHA 的 Accepted；C++ 格式修订也单独通过 13
个输入。新 Python 实际执行 265 个输入；另对全部 99999 个合法目标检查了
前缀及余量模型。这不是每门语言各执行 99999 次。包括 1、9、45、46、99999
以覆盖小数字补齐及两个阶段。

## 样例

### 样例 1

输入：

```
17
```

输出：

```
3
7 12 43
```

## 解法

设 `s(x)` 为十进制数字和、`L=100000`。简单贪心版本先为所有 `i<L`
计算 `s(i)=s(i//10)+i%10`，再从 `L−1` 递减；数字和不超过剩余目标就选取。
每个数只访问一次，故输出互不相同且范围合法。时间及数字和表为 `O(L)`，
另外保存 `q` 个输出数需要 `O(q)` 空间。

为什么必能完成？区间 `[90000,99999]` 内单个数字和至多 45，整个区间之和为
`9·10000+4·45·1000=270000`。若遍历完此区间余量仍至少为 45，那么区间内
每个数此前都能选入；但不可能从 `n<100000` 减去 270000 仍非负。因此余量
在区间内已降到 45 以下，之后不会增加。遍历至尚未使用的个位数 `9,8,…,1`
时，可贪心表示任何 0 到 45 的余量。在数字 `d` 前保持
`remainder≤d(d+1)/2`；能选 `d` 就选，随后保持 `d−1` 对应的界，最终为零。
所以无需输出 −1。

五个简单算法全部保留。仅 C++ 按仓库配置精确格式化，并另获自身 Accepted
及新测量；其他四份源码逐字节不变，原 C++ 字节也有备份。

## 优化解法

新构造不用完整数字和表及长扫描。余量大于 45 时，从 99999 开始连续
取数，按需计算每个数字和。五位数的数字和至多 45，每次必能放入。由 270000
的区间总和界可知，此阶段在降至 90000 前已结束，远离个位数。再用不同数字
9 到 1 贪心补齐。两阶段范围不交，余量不变量证明总和正确。题目允许任意
合法集合，不要求最少元素。

若大数有 `D` 位、输出 `q` 个数，则时间 `O(qD+D)`、输出空间 `O(q)`；这里
`D=5`，时间即 `O(q)`，没有 `O(L)` 预处理表。算法不同，命名 `constructive`，
不复制旧扫描为 `_optimized`。五个语言版本相对各自当前基础代码均达到至少
30% 的内存改善。Python 记录时间从 0.093 秒增至 0.109 秒，准入依据是内存。
Rust 的 0.046→0.031 秒仅一个计时刻度，不用作可靠加速证据。

实测内存减少：C++ 66.4%，Go 43.9%，Java 61.9%，Python 43.0%，Rust 76.6%。

## 各语言说明

表中 Accepted 测量绑定精确源码字节；比较基线是当前简单版本，包括
新获 Accepted 的 C++ 格式修订。2026 年 11 月 2 日排名快照采用既定编译器
和其他作者过滤：C++ 要求两指标均前 15% 或均前十名，其余语言族均要求
两项第一。星号表示达到改善准入但尚未达到排名目标。没有竞争者只构成形式
覆盖，不能证明竞争优势。
