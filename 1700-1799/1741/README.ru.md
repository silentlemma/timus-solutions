# 1741. Монстр общения

[Timus 1741](https://acm.timus.ru/problem.aspx?space=1&num=1741) · сложность 289 · dp

Автор оригинальной задачи — Алексей Самсонов (подготовка — Марина Мухачёва); XIV Открытый командный чемпионат УрГУ по программированию.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Лицензионный клиент версии 1 нужно довести до версии n. Каждое
обновление переводит версию x в версию y > x и имеет размер. Пиратское
обновление навсегда делает клиент пиратским; взломанное ставится на
любой клиент; лицензионное — только на клиент, который ещё
лицензионный. Найти наименьший суммарный размер обновлений или
сообщить, что версии n не достичь.

## Входные данные

n и m (2 ≤ n ≤ 10⁴, 1 ≤ m ≤ 10⁴), затем m обновлений `x y d s`
(1 ≤ x < y ≤ n, 1 ≤ d ≤ 10⁶), где s — `Pirated`, `Cracked` или
`Licensed`.

## Выходные данные

`Online` и наименьший суммарный размер или `Offline`.

## Проверка

Вывод сравнивается по токенам; лишние пробельные символы не важны.

## Примеры

### Пример 1

Ввод:

```
3 4
1 3 10 Licensed
1 2 2 Pirated
2 3 3 Licensed
2 3 6 Cracked
```

Вывод:

```
Online
8
```

### Пример 2

Ввод:

```
3 1
1 2 10 Licensed
```

Вывод:

```
Offline
```

## Решение

Обновления только повышают версию, поэтому версии можно обрабатывать по
возрастанию, каждую после всего, что к ней ведёт. Состояние — версия и
то, лицензионный ли ещё клиент или уже пиратский. Из каждого
достигнутого состояния пиратское обновление ведёт в пиратское
состояние своей цели, взломанное сохраняет состояние, а лицензионное
допустимо только из лицензионного. Ответ — меньшее из двух значений у
версии n. `O(n + m)`.

В первом примере пиратское 1 → 2 за 2 и взломанное 2 → 3 за 6 дают 8,
дешевле лицензионного 1 → 3 за 10; лицензионное 2 → 3 за 3 не может идти
после пиратского.

Подводные камни:

- сумма доходит примерно до 10¹⁰, больше, чем вмещают 32 бита;
- взломанное обновление оставляет лицензионный клиент лицензионным;
- неважно, будет ли версия n лицензионной.

Ответы совпадают с независимой принятой реализацией — поиском
кратчайшего пути — на 200 случайных наборах.

## Оптимизированные решения

`1741_dp_optimized.go`. Сохраняется динамика на DAG с двумя состояниями: ноль — лицензия сохранена, один — пиратская версия. Версии идут по возрастанию, поскольку любое обновление ведёт в большую; P переводит в один, C сохраняет состояние, L недоступно из одного. Рёбра хранятся плоскими массивами прямой звезды: концы и ссылки int32, вид byte, вес int64, вместо вложенных срезов структур с выравниванием. Стоимости остаются int64, поскольку сумма пути может превысить 32 бита. Для различения трёх заданных слов достаточно первой буквы, но токен потребляется целиком. Время и память O(n+m), включая инициализацию. Переносимые os.Stdin.Read/os.Stdout.Write и прямое преобразование целых используют фиксированные буферы ввода и вывода по 4096 байт. Частичная запись обрабатывается до повторного использования буфера. Исходный простой вариант с Accepted сохранён.

По сравнению с `1741_dp.go`: время 0.046 s → 0.031 s; память 3284 KB → 1 184 KB.

Сохраняется DP по DAG возрастающих версий с чистым и пиратским состояниями лицензии. Плоские массивы рёбер заменяют контейнеры вершин и объекты рёбер. Пиратское обновление переносит минимум двух состояний только в пиратское; взломанное сохраняет каждое состояние, лицензированное принимает лишь чистое. Ветвление по типу делается один раз на обновление. Стоимости путей требуют 64 бит, номера вершин и поля рёбер компактны. Очередь с приоритетом и обход Дейкстры не нужны.

- `1741_dp_optimized.cpp`: 0.015 s / 196 KB; база `1741_dp.cpp`: 0.031 s / 1068 KB; изменение относительно базы: время -51.6%, память -81.6%.
- `1741_dp_optimized.java`: 0.093 s / 748 KB; база `1741_dp.java`: 0.156 s / 5788 KB; изменение относительно базы: время -40.4%, память -87.1%.
- `1741_dp_optimized.py`: 0.109 s / 972 KB; база `1741_dp.py`: 0.109 s / 6872 KB; изменение относительно базы: время -0.0%, память -85.9%.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1741_dp_parsing_optimized.py`. Два состояния динамики хранятся в плоском виде, типы символов — в байтах. Внутренний цикл по двум состояниям заменён явными переходами без изменения рекуррентности. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.

Accepted #11328660 (Python 3.12 x64): **0.093 s / 5352 KB**. Архивное сравнение: `1741_dp.py` (Python 3.12 x64) — 0.109 s / 6872 KB (#11308920).

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Приведённые ниже места относятся к новым версиям; прежние исходники сохраняют собственные исторические метрики Accepted.

`1741_dp_optimized.go`: сопоставимых чужих результатов недостаточно для рейтингового вывода; допуск основан на измеренном улучшении относительно простой версии.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
