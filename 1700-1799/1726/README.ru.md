# 1726. Кто ходит в гости…

[Timus 1726](https://acm.timus.ru/problem.aspx?space=1&num=1726) · сложность 120 · sorting

Автор оригинальной задачи — Денис Дублённых; Уральская региональная командная олимпиада по программированию 2009.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

n членов комитета живут на перекрёстках города-решётки и ходят друг к
другу по улицам кратчайшим путём. Каждый ходит к каждому одинаково
часто. Найти среднее расстояние, округлённое вниз.

## Входные данные

n (2 ≤ n ≤ 10⁵) в первой строке, затем n строк с координатами x и y
(1 ≤ x, y ≤ 10⁶).

## Выходные данные

Среднее расстояние между домами двух членов комитета, округлённое вниз.

## Примеры

### Пример 1

Ввод:

```
3
10 10
20 20
10 20
```

Вывод:

```
13
```

## Решение

Кратчайший путь по улицам имеет длину |dx| + |dy|, поэтому сумма по
всем парам распадается на сумму |x_i − x_j| и сумму |y_i − y_j|.
Отсортируем x: i-е значение (считая с 0) не меньше каждого из i
предыдущих, поэтому добавляет i·x_i минус их сумму, которую хранит
накопленный итог. С y так же. Среднее по n(n − 1)/2 парам — эта сумма,
делённая на число пар и округлённая вниз. `O(n log n)`.

В примере расстояния равны 20, 10 и 10, так что среднее — 40/3, после
округления вниз 13.

Подводные камни:

- сумма доходит примерно до 5·10¹⁵, когда половина домов стоит в одном
  дальнем углу, а половина — в другом, поэтому нужны 64 бита;
- перебор всех пар требует около 5·10⁹ шагов, это слишком много.

Средние совпадают с суммой по всем парам на 300 маленьких случайных
картах и с независимой принятой реализацией на больших тестах.

## Оптимизированные решения

Оптимизированное решение на C++ хранит координаты в статических массивах
`int`, которых хватает, ведь координаты не больше 10⁶, вместо векторов
`long long` и разбирает 2·10⁵ чисел вручную из блоков по 4 КБ,
прочитанных через `fread`, вместо вызова `scanf` для каждого; суммы
по-прежнему считаются в `long long`: {1726_sorting_optimized.cpp}.

Оптимизированное решение на Go разбирает 2·10⁵ чисел вручную из
буферизованного reader на 64 КБ вместо `fmt.Fscan`, который и есть
медленная часть простой программы: {1726_sorting_optimized.go}.

Оптимизированное решение на Python читает строки пачками примерно по
64 КБ в массивы 32-битных целых, которых хватает, ведь координаты не
больше 10⁶, а не держит каждый токен ввода как байтовую строку и два
списка целых Python. Кроме того, каждая сумма считается без цикла на
Python: в отсортированном порядке `i`-е из `n` значений (с нуля) не
меньше `i` предыдущих и не больше `n − 1 − i` последующих, поэтому
входит в сумму с весом `2i − (n − 1)`, и `sum(map(mul, …))` по
отсортированным значениям и `range` весов целиком выполняется на C:
{1726_sorting_optimized.py}.

Оптимизированное решение на Rust разбирает числа вручную из блоков по
4 КБ, а не читает весь ввод в строку, и хранит координаты в `u32`,
которого хватает, ведь они не больше 10⁶, вместо `i64`; суммы считаются
в `u64`: {1726_sorting_optimized.rs}.
