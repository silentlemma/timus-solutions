# 1728. Проклятие Team.GOV

[Timus 1728](https://acm.timus.ru/problem.aspx?space=1&num=1728) · сложность 524 · implementation

Автор оригинальной задачи — Евгений Курпилянский (идея — Михаил Рубинчик); Уральская региональная командная олимпиада по программированию 2009.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Ефремов и Канторов выбирают третьего участника из списка претендентов.
Сила команды — сумма рейтингов её участников. Если выбранный состав уже
выступал на каком-то прошлом турнире, Ефремов не приходит; если и
состав без него уже выступал, команду дисквалифицируют. Выбрать
претендента, дающего самую сильную выступающую команду, или сообщить,
что при любом выборе команду дисквалифицируют.

## Входные данные

n (1 ≤ n ≤ 100) прошлых составов: размер от 1 до 3 и фамилии в
алфавитном порядке; в каждом составе есть Канторов, в каждом составе из
трёх — Ефремов. Затем рейтинги Ефремова и Канторова, m (1 ≤ m ≤ 100) и
m претендентов с рейтингами. Рейтинги от 1 до 666.

## Выходные данные

`Win` и претендент, дающий самую сильную команду, или `Fail`. Подходит
любой лучший претендент.

## Проверка

В репозитории используется проверяющая программа, принимающая любой вывод с указанными свойствами. Проверяющая программа применяет правила отказа и дисквалификации к каждому кандидату. Fail принимается ровно при отсутствии допустимых кандидатов; иначе нужны Win и кандидат с максимальной силой оставшейся команды. При равенстве подходит любой оптимальный выбор.

## Решение

Предпочтительные более простые C++, Go и Rust используют два множества фамилий третьих участников. В каждом прошлом составе есть Канторов, а в каждой тройке — и Ефремов, поэтому третья фамилия однозначно задаёт нужную пару или тройку. Для тройки добавляем её в множество полных составов, для пары — в множество пар; одиночный Канторов и пара Ефремов/Канторов кандидатам не мешают. Если фамилии нет среди троек, сила re+rk+r. Если она есть среди троек, но отсутствует среди пар, сила rk+r; если есть в обоих — дисквалификация. Выбираем любого с максимальной силой. Фамилии сравниваются целиком с учётом регистра. Ожидаемое время O((n+m)L), L≤50, память множеств O(nL). Исходный общий подход сортирует до трёх фамилий, хранит канонический ключ полного состава, проверяет тройку, при повторе убирает Ефремова и проверяет пару. Все пять исходных Accepted сохранены; Java/Python продолжают использовать этот подход как базовый.

## Оптимизированные решения

`1728_implementation_optimized.java`. Сохраняются карта прошлых участий в парах/тройках и поиск максимальной допустимой силы команды. Для ASCII-имён переиспользуются байтовый и символьный буферы токена с копированием в неизменяемый String; остальные имена по-прежнему декодируются как UTF-8. Win/Fail и выбранное имя выводятся байтами. При I байтах ввода и U уникальных именах ожидаемое время O(I+N+M); память для текста и состояния зависит от суммарной длины имён и ёмкости буфера. Оценка HashMap ожидаемая, без гарантии худшего случая.

Accepted точного исходника Java 1.8 №11327746: 0.093 с / 508 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 2/19, память 3/19. При памяти меньше 1024 КБ строгий допуск учитывает только время: первые десять мест или топ 15%, равенства делят место, процентный порог округляется вверх. Звёздочка остаётся для отдельной цели языка: первого места по обеим метрикам. Прежний документированный оптимизированный запуск №11324823: 0.125 с / 928 КБ; это отдельная историческая пара, не текущий замер данного исходника. Учебные версии сохранены без изменений.

- `1728_implementation_optimized.java`: 0.093 s / 508 KB; сохранённая учебная база `1728_implementation.java`: 0.14 s / 2172 KB.

Быстрая версия Go использует те же два множества фамилий, стандартные дескрипторы, фиксированные буферы ввода и вывода и 50 байтов на фамилию. Быстрый Rust читает фамилии через стандартный ввод C и хранит оба признака состава в одной таблице фиксированного размера с открытой адресацией. При коллизии сравнивает фамилии целиком. Множества фамилий на C++ также входят в быстрый набор. Java и Python используют принятые базовые программы. Прежние C++, Go и Rust, которые хранят канонические составы, перечислены в других принятых подходах. Звёздочка отмечает быстрый исходник ниже рейтинговой цели своего языка.

Принятые базовые реализации [1728_implementation.java](1728_implementation.java), [1728_implementation.py](1728_implementation.py) также закрывают быстрый набор: в сохранённом срезе сравнения они уже удовлетворяют рейтинговому критерию включения — топ 15% или первые десять мест одновременно по времени и памяти. Используются те же исходники без одинаковых копий. Звёздочка отмечает версию, которая пока не достигла целевого рейтинга своего языка.

### Новые принятые версии

Для версий ниже применяются единые [рейтинговые критерии](../../RATING_CRITERIA.md) и Accepted точного исходника. Более ранние обсуждения производительности описывают исторические посылки и срезы, а не отдельное действующее правило допуска. Содержательные простые и прежние отличающиеся реализации сохранены.

`1728_implementation_optimized.py`. Самостоятельная программа сбрасывает оба выходных потока перед os._exit(0), чтобы после записи полного ответа не выполнять завершение интерпретатора. Это изменение завершения процесса, а не математического алгоритма; простая версия сохранена.

Accepted #11328591 (Python 3.12 x64): **0.078 s / 824 KB**. Архивное сравнение: `1728_implementation.py` (Python 3.12 x64) — 0.109 s / 548 KB (#11289392).

## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Учебные алгоритмы сохранены. Перепроверенные базовые версии используют собственные новые метрики и ID Accepted точного исходника; эти проверки не считаются оптимизациями.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
