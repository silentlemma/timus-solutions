# 1783. Ядерная гонка

[Timus 1783](https://acm.timus.ru/problem.aspx?space=1&num=1783) · сложность 473 · simulation

Автор оригинальной задачи — Павел Атнашев; XV Открытый командный чемпионат УрГУ по программированию.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Одна страна планирует иметь ровно aᵢ боеголовок к концу месяца i. Её
соперник начинает с нуля и в начале месяца i, зная планы
aᵢ, …, aᵢ₊ₘ₋₁, выбирает наименьшее целое изменение xᵢ, при котором
изменение запаса на xᵢ в каждый из следующих m месяцев держало бы его
не ниже плана в конце каждого из них. Выполняется только изменение
этого месяца; в следующем месяце выбор делается заново. Вывести
x₁, …, xₙ.

## Входные данные

n и m (1 ≤ n ≤ 10000, 1 ≤ m ≤ 50), затем a₁, …, aₙ₊ₘ₋₁
(0 ≤ aᵢ ≤ 10⁵).

## Выходные данные

x₁, …, xₙ.

## Примеры

### Пример 1

Ввод:

```
4 3
0 0 4 2 1 0
```

Вывод:

```
2 1 1 -1
```

## Решение

При запасе s в начале месяца i после t месяцев одинакового изменения x
запас равен s + t·x и должен быть не меньше aᵢ₊ₜ₋₁. Поэтому x — наибольшее
из ⌈(aᵢ₊ₜ₋₁ − s)/t⌉ по t = 1…m. Затем запас растёт на x, и следующий месяц
повторяет то же. Округлять нужно вверх и для отрицательных чисел, где
обычное целочисленное деление во многих языках округляет к нулю.
`O(n·m)`.

В примере первый приказ должен за три месяца дотянуть до 4: 2. С
запасом 2 следующие планы 0, 4, 2 требуют ⌈2/2⌉ = 1; затем с 3 планы 4,
2, 1 требуют 1; затем с 4 планы 2, 1, 0 позволяют −1.

Подводные камни:

- приказы бывают отрицательными, когда планы падают;
- ⌈−3/2⌉ равно −1, а не −2 и не 0, поэтому деление должно явно
  округлять вверх;
- каждый раз выполняется только первый из планируемых месяцев.

Ответы совпадают с независимой принятой реализацией на 60 случайных
случаях — от нескольких месяцев до 10000 месяцев случайных,
волнообразных и редких всплесков в планах.

## Оптимизированные решения

Принятые версии только с форматированием: `1783_simulation.java` #11327472, `1783_simulation.cpp` #11327473, `1783_simulation.py` #11327474, `1783_simulation.rs` #11327475. Каждая строка таблицы относится к точной версии файла и её собственным парным времени/памяти; форматированию не приписывается ускорение.

`1783_simulation_optimized.cpp`. Сохраняется точный максимум знаковых округлений вверх по тому же кольцу до 50 будущих планов. Деление delta/t выполняется только при delta>best*t: для целого best это равносильно ceil(delta/t)>best даже при отрицательном delta. Неотрицательное деление использует (delta+t-1)/t, отрицательное — усечение к нулю. Планы и запас в 0..100000, t<=50: best*t помещается в знаковый int. Фиксированные буферы ввода/вывода по 16 КиБ сопровождают прежние O(nm) времени и O(m) памяти планов.

Accepted точного исходника G++ 13.2 x64 №11326998: 0.015 с / 104 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 1/43, память 1/43; обе метрики в первой десятке, звёздочка не нужна. При памяти меньше 1024 КБ строгий допуск учитывает только время. Прежний оптимизированный запуск №11315303: 0.031 с / 88 КБ. Это независимые парные замеры; новая зафиксированная память выше. У сохранённой учебной C++-версии собственный текущий Accepted №11327473: 0.031 с / 264 КБ; алгоритм не менялся.

C++/Go сохраняют точный максимум m знаковых округлений вверх, но читают планы потоком в кольцо до50 целых. Сначала читаем m планов, затем после выполненного заказа заменяем истёкший слот следующим планом и двигаем начало: кольцо содержит ровно текущее окно. Индекс оборачивается проверкой границы, без остатка на каждом элементе. При delta≥0 используем (delta+t−1)/t, при отрицательном delta — деление к нулю, равное округлению вверх. Планы и запас остаются в 0…100000, хватает знаковых32 бит. Время O(nm), планы занимают O(m) вместо O(n+m), ввод-вывод ограничен. Базы сохранены; Java, Python и Rust используют подходящие базы.

Сохранённые принятые учебные исходники [1783_simulation.java](1783_simulation.java), [1783_simulation.py](1783_simulation.py), [1783_simulation.rs](1783_simulation.rs) также проходят строгий критерий первых десяти мест или топ 15% по требуемым метрикам в сохранённом сравнении. Текущие точные парные замеры, включая версии только с форматированием, приведены в таблице. Алгоритмы не менялись, одинаковые оптимизированные копии не добавляются. Звёздочка обозначает отдельную рейтинговую цель языка.
