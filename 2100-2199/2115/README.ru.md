# 2115. Упорядочить шеренгу не более чем одной перестановкой

[Timus 2115](https://acm.timus.ru/problem.aspx?space=1&num=2115) · сложность 228 · sorting

Автор оригинальной задачи — Иван Смирнов; Вузовско-академическая олимпиада по информатике 2019.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Дана последовательность `1≤n≤100000` ростов `0≤a[i]≤10⁹`.
Определите, упорядочена ли она уже нестрого по возрастанию либо убыванию.
Иначе найдите один обмен двух различных позиций, который даёт любой из
этих порядков, либо установите, что одного обмена недостаточно. Равные
значения допустимы. Лимит времени — 1 секунда, памяти — 256 МБ.

## Входные данные

Первая строка содержит n, вторая — n ростов в текущем порядке.

## Выходные данные

Если последовательность уже монотонна в любом направлении, выведите
`Nothing to do here`. Иначе выведите `Yes`, затем в следующей строке
два различных номера с единицы, обмен которых создаёт любой нужный
порядок. Разрешён любой верный обмен. Если такого нет, выведите `No hope`.

## Проверка

Проверяем обязательный вердикт либо выполняем указанный обмен двух
различных номеров с единицы и проверяем любой монотонный порядок.
Разные правильные обмены допустимы. Каждая из пяти выбранных программ
на своём целевом языке прошла 15 входов репозитория и 100 дополнительных.
Все 500 дополнительных выводов и кодов завершения заново сверены
с независимой проверкой через отсортированные цели, без правила границ
нарушений. Точный выбранный Python дополнительно выполнен на 10876
входах хоста: все 9840 массивов длины 1..8 над `{0,1,10⁹}`, 1000
случайных, случаи серий равных и конструкции длины 99999/100000,
включая длинную строку, переносы токенов и EOF. Эти запуски не выдаются
за нативные. У пяти быстрых файлов и трёх версий после форматирования
есть собственные Accepted точных байтов.

## Примеры

### Пример 1

Ввод:

```
3
150 160 170
```

Вывод:

```
Nothing to do here
```

### Пример 2

Ввод:

```
4
140 160 150 170
```

Вывод:

```

```

## Решение

Простые версии сортируют копию для неубывающей цели, а её разворот
даёт невозрастающую цель. Совпадение с любой означает, что ничего менять
не надо. Иначе для каждой цели собираем несовпадающие позиции. Обмен
меняет только две позиции: несовпадений должно быть ровно два, i,j,
с перекрёстными значениями `a[i]=target[j]`, `a[j]=target[i]`. Эти условия
и достаточны: все прочие позиции уже совпадают. Проверка обеих целей
полна. Время `O(n log n)`, массивы `O(n)` плюс сохранённый ввод.

Все пять алгоритмов с сортировкой остаются. Байты Go и Python не меняются;
C++, Java и Rust получают лишь точный вывод форматтера репозитория,
каждый со своим новым Accepted. Исходные байты до форматирования
сохранены в локальных резервных копиях публикации. Метрики таблиц
относятся к фактическим байтам исходников.

## Оптимизированные решения

Файлы `two_pointers` обходятся без сортировки и копий целей.
Для неубывания найдём первое нарушение `a[p]>a[p+1]`, от p сдвинемся
влево по равным значениям до l. Найдём последнее нарушение
`a[q-1]>a[q]`, от q сдвинемся вправо по равным до r. Обменяем l,r
и проверим порядок целиком. При неудаче восстановим массив и повторим
для невозрастания, сравнивая `direction*a[i]` при direction=−1.
Значения остаются в `[-10⁹,10⁹]`, внутри знаковых 32 бит.
Если исходный массив уже монотонен, сразу выдаётся требуемая фраза
об отсутствии работы, без лишнего обмена.

Почему концы обязательны? Пусть обмен i<j исправляет возрастающий
порядок. Изначально на концах H>L, а все неизменённые значения между
ними лежат от L до H. Первое нарушение находится на правом краю серии
H, начинающейся в i. Раньше i эта серия продолжаться не может: прежнее
значение H перед новым L нарушило бы порядок. Значит, расширение влево
от первого нарушения восстанавливает i. Аналогично последнее нарушение
на левом краю серии L, заканчивающейся в j. После j серия продолжаться
не может: новый H превысил бы следующую L. Расширение вправо даёт j.
Таким образом, любой возможный обмен обязан совпасть с проверяемым.
Полная проверка доказывает достаточность, неудача обоих направлений —
невозможность. Серии равных нельзя игнорировать, например в `1,2,2,1`.

Полных проходов константное число: `O(n)` времени и `O(1)` состояния
поиска сверх хранимой последовательности из `O(n)` ячеек. Go и Rust
дополнительно сохраняют весь ввод, а Python при split временно держит
целую длинную строку токенов. Эту память тоже учитываем, не называя её
константной. C++ читает буфером байтов и хранит один 32-битный вектор;
Java — один int-массив; Python — `array('i')` вместо списка объектов int.
Отсортированная и развёрнутая цели не строятся.

По сравнению с актуальными Accepted-базами того же языка C++ снижает
время 0,109→0,015 с на 86,2%, память 2532→520 КБ на 79,5%. Go снижает
время 0,140→0,046 с на 67,1%; память 5696→4052 КБ уменьшается лишь
на 28,9%, допуск идёт по времени. Java снижает память 3644→848 КБ
на 76,7%. Rust — 3504→2140 КБ на 38,9%; изменение 0,062→0,046 с
составляет один шаг таймера и не используется как доказательство
ускорения. Python снижает память 15740→8564 КБ на 45,6%, но время
растёт 0,140→0,203 с на 45,0%. Он допущен по памяти, не по времени,
и сохраняет звёздочку недостигнутой рейтинговой цели.

## Особенности языков

Это другой, линейный алгоритм: файлы называются `two_pointers`
и сосуществуют с простыми `sorting`. Для C++ и Python выбраны более
сильные Accepted-ревизии пачки009. Прежние варианты пачки002 с теми же
предложенными именами остаются только в локальных снимках и отчётах,
публичных дублей нет.

C++, Java, Go и Rust достигли текущего рейтингового профиля. Для Go
и Rust нет допустимых чужих посылок: это формальное покрытие, не
доказательство превосходства. CPython 3.12 первый по памяти, но 17-й
по времени в снимке и отмечен звёздочкой. Нативные версии сравниваются
с новыми принятыми отформатированными базами, где они есть; старые метрики
не приписываются новым байтам. Поддержан весь диапазон, включая n=1,
все равные, нули и 10⁹.
