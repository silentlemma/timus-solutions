# 2108. Замыкание набора фигурок по правилам желаний

[Timus 2108](https://acm.timus.ru/problem.aspx?space=1&num=2108) · сложность 461 · bitmask

Автор оригинальной задачи — Кирилл Бороздин; Чемпионат УрФУ среди юниоров 2016.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Есть n коллекционных фигурок. Каждое из m желаний гласит: как только
есть все фигурки набора A, хочется и все фигурки набора B. Начиная с уже
имеющихся фигурок, найдите наименьший набор, удовлетворяющий всем
желаниям, то есть набор, получаемый исполнением желаний, пока не
захочется ничего нового. Ограничения: 0.9 секунды и 64 МБ.

## Входные данные

n и m, 1 ≤ n ≤ 1000, 0 ≤ m ≤ 4000, затем m строк с наборами A и B в
виде строк из n нулей и единиц, и имеющийся набор в том же формате.

## Выходные данные

Итоговый набор в том же формате.

## Примеры

### Пример 1

Ввод:

```
6 4
111000 101000
110000 111000
010000 100000
000010 000001
010100
```

Вывод:

```
111100
```

## Решение

Набор, удовлетворяющий всем желаниям и содержащий имеющиеся фигурки,
обязан содержать каждую фигурку, к которой ведёт какая-то цепочка
желаний, а набор ровно из этих фигурок удовлетворяет всем желаниям.
Поэтому повторяются проходы по желаниям: желание, у которого A лежит
внутри имеющегося набора, добавляет B. Проход, который ничего не
добавил, завершает процесс, а любой другой добавляет хотя бы одну
фигурку, так что проходов не больше n + 1.

Наборы — битсеты из 64-битных слов: «A внутри имеющегося набора» — это
A AND NOT owned = 0, а добавление B — OR, обе операции по n / 64 слов.
Вся работа — O(n · m · n / 64), около 6 · 10⁷ операций над словами.

В примере имеющиеся фигурки 2 и 4 включают третье желание, которое
добавляет 1; затем второе желание добавляет 3, и результат — 111100.

## Оптимизированные решения

Принятые версии только с форматированием: `2108_bitmask.py` #11327499. Каждая строка таблицы относится к точной версии файла и её собственным парным времени/памяти; форматированию не приписывается ускорение.

`2108_graphs_bitmask.cpp`. Сохраняются упакованные битовые наборы правил по предпосылкам, счётчики и очередь с однократным добавлением фигурок. Только буфер ввода C++ увеличен до 64 КиБ, чтобы реже читать плотные строки правил; логика замыкания и ограниченные массивы прежние. Пустые предпосылки запускаются после чтения всех правил. Время с вводом O(nm+n+m); матрицы занимают O(n ceil(m/64)+m ceil(n/64)) машинных слов, плюс счётчики и очередь. Буфер обменивает память на меньшее число чтений, не вводя новый алгоритм.

Accepted точного исходника G++ 13.2 x64 №11326657: 0.062 с / 1140 КБ. Сохранённое сравнение компиляторов от 2026-11-20: время 5/46, память 3/46; обе метрики в первой десятке, звёздочка не нужна. Память не меньше 1024 КБ: требуются и пройдены места по времени и памяти. Прежний оптимизированный запуск №11315229: 0.093 с / 1080 КБ. Это независимые парные замеры; новая зафиксированная память выше. У сохранённой учебной C++-версии собственный текущий Accepted №11294887: 0.046 с / 1808 КБ; алгоритм не менялся.

Новые C++, Go и Rust транспонируют предпосылки в битовые наборы правил для каждой фигурки и хранят число недостающих предпосылок правила. Каждую новую фигурку ставим в очередь ровно один раз; при обработке уменьшаем счётчики содержащих её правил. Нулевой счётчик запускает правило один раз и добавляет ещё не полученные следствия. Правила с пустыми предпосылками запускаются после чтения всего ввода. Получается наименьшее замыкание: добавляют только разрешённые правила, а в конце каждое разрешённое правило уже выполнено. Повторных полных раундов нет. С чтением время O(nm+n+m), упакованная память O(n⌈m/64⌉+m⌈n/64⌉+n+m). При максимумах две матрицы занимают 1016000 байтов, без миллионов отдельных рёбер. Go/C++ выделяют ограниченные максимальные массивы; Rust — векторы по входным размерам и ограниченный C runtime вместо сохранения текста ввода. Базы сохранены; Java/Python используют подходящие базы.

Принятая версия Go 1.14 x64 заняла 0.125 с при 0.062 с у базовой и использовала 1 284 KB при 18712 KB у базовой.

Сохранённые принятые учебные исходники [2108_bitmask.java](2108_bitmask.java), [2108_bitmask.py](2108_bitmask.py) также проходят строгий критерий первых десяти мест или топ 15% по требуемым метрикам в сохранённом сравнении. Текущие точные парные замеры, включая версии только с форматированием, приведены в таблице. Алгоритмы не менялись, одинаковые оптимизированные копии не добавляются. Звёздочка обозначает отдельную рейтинговую цель языка.

## Особенности языков

Эти замечания относятся к базовым реализациям.

Решение на Python транспонирует задачу, потому что проходы там слишком
медленны, когда цепочка желаний перечислена в обратном порядке. Для
каждой фигурки строится множество желаний, которым она нужна, в виде
одного большого целого (столбец матрицы строк A). Дерево отрезков по
фигуркам хранит объединение этих множеств по ещё отсутствующим
фигуркам — ровно множество ещё не включённых желаний. Каждый раунд
исполняет все новые включённые желания и обнуляет листья только что
полученных фигурок. Каждое желание исполняется не более одного раза,
а лист каждой фигурки обнуляется не более одного раза.

Пусть w — число бит в разряде большого целого Python, N = ceil(n / w),
M = ceil(m / w), L = 1 + ceil(log2 n). При m > 0 время составляет
O(nm + (nL + m)M + nN): чтение и транспонирование требуют O(nm),
обновления дерева и проверки готовности — O(nLM), перебор включённых
желаний — O(mM), перебор новых фигурок — O(nN). Объединение результатов
требует O(mN), что уже покрывается O(nm). При m = 0 время — O(n).

Ловушка (тест 15, пустые результаты): желание, которое ничего не
добавляет, всё равно надо обработать. Перебор установленных битов в Python
не занимает константное время на бит: `mask & -mask` и `mask ^= low`
просматривают разряды целого. При n = 1 и m = 4000 желаниях A = B = 0
ответ остаётся 0, но перебор включённых желаний требует Θ(m² / w)
операций над разрядами. Поэтому оценка O(n^2 m / 64) для повторных
проходов не описывает решение на Python.
