# 1589. 推箱子

[Timus 1589](https://acm.timus.ru/problem.aspx?space=1&num=1589) · 难度 14456 · astar, greedy

原题作者 Stanislav Vasiliev 与 Sergey Pupyrev，出自 2007 年 10 月 27 日在叶卡捷琳堡举行的 ACM ICPC 2007–2008 NEERC 东部分区赛。

[English](README.md) · [Русский](README.ru.md) · **中文** · [Español](README.es.md)

## 任务

一个不超过 8 × 8 的推箱子关卡：墙 `#`、目标 `.`、箱子 `$`（在目标上为
`*`）和玩家 `@`（在目标上为 `+`）。玩家在空格上行走，走进箱子时可以一次
推动一个箱子，但不能拉。输出一个让所有箱子都到达目标的方案：移动
`u`、`d`、`l`、`r`，推箱子的移动用大写，总数不超过 10 000。解一定存在，
任何合法方案都被接受。

时间限制：5 秒。内存限制：64 MB。

## 输入

逐行给出关卡；各行长度可以不同，墙外可以有空格。

## 输出

一行方案。

## 样例

### 样例 1

输入:

```
########
#@  $ .#
########
```

输出:

```
rrRR
```

### 样例 2

输入:

```
######
##   .#
#@  ###
#   * #
#   $ #
#     #
#######
```

输出:

```
dddrrrruLdlUUUluRR
```

## 解法

搜索以推动为单位，而不是以步为单位。状态是箱子集合加上玩家能走到的
区域（用其中编号最小的格子表示）；两者合成一个 64 位键，区域通过位掩码
扩张求得。
这里有两种解法：贪心解法，单个带死锁检查的最佳优先搜索（C++、Go、Java、Rust）；以及 astar
解法，一串带区域死锁表的搜索，快得多（全部五种语言）。

贪心搜索按 `推动数 + 20·h` 取状态，其中 h 是各个单独的箱子到达不同目标所需推动数之和的
最小值（匈牙利算法）；权重很大，使搜索几乎是贪心的。以下情况的状态被丢弃：

- 有箱子会落在死格上，单个箱子从那里到不了任何目标；
- 不在目标上的箱子保持冻结：即使逐步拿掉所有可移动的箱子，也没有箱子能沿任一轴移动；
  或者即使拿掉玩家能推动的所有箱子并扩大玩家区域，玩家也推不动任何箱子；
- 匹配没有有限代价；
- 包含被移动箱子的某组二、三或四个箱子单独无法解开：对每组这样的箱子，有一张表由从
  所有同样大小的目标组出发的拉动搜索建成，记录从哪些玩家格子出发它们能解开。

围栏是玩家进不去、边界上有未完成的箱子或内部有目标的区域；若其边界上的推动全部朝里
（去掉外面的箱子后仍是这些推动），就只尝试这些推动。见过的状态存放在开放寻址的键集合中，
节点存放在一个平铺的数组里；方案按每个节点记录的移动复原，推动之间的步子由广度优先行走给出。

在论坛上的一个密集关卡（36 格上有 13 个箱子）中，从起点可达的状态超过
3 000 万，从已解局面可达的有 2 200 万，但两边都有的只有约 6 300 个；
贪心搜索在那里需要 1.8 秒。

astar 这串搜索按同样的下界（这里记作 H）排列状态，目标上冻结的箱子视为墙，
除子集表外以同样的方式剪枝。各阶段：

1. 廉价试探：一次正向搜索和一次从目标出发的拉动搜索，各 128 次展开，
   然后把棋盘旋转四次，每次 64 次展开。大多数关卡到此结束。
2. 把棋盘取为各种旋转和反射中最小的一种，再加两项检查进行搜索。区域表：
   对沿地面每一边、宽三格的条带，从条带内的目标出发做拉动搜索，其间箱子
   可以离开条带、也可以有新箱子进入，记录下条带仍能完成的每个条带内箱子
   集合和每个玩家区域；条带未被记录的状态是死的。填充顺序：保留冻结箱子，
   把箱子从已解局面的目标上拉走，可以看出哪些目标必须最后填；与这些剩余
   都对不上的状态是死的。优先级为 `H + 30·M - 深度`，其中 M 是离最近剩余
   还缺的箱子数，于是搜索沿着填充顺序向深处走。它在 600 000 个状态或
   1 秒后停止。
3. 若这一步失败，或者它的方案超过 10 000 步，就释放它的内存，从头开始
   第二串搜索：同样的试探，然后是带有移动箱子附近所有三个、再到五个箱子
   子集的表的搜索（这些表由只含这些箱子、冻结箱子视为墙的拉动搜索建成），
   最后是在玩家精确位置和行走代价上的 A*，它使每个方案都不超过 10 000 步。

每个方案在输出前都会完整回放一遍。在那个密集关卡上，区域检查和填充顺序检查使这串搜索
只展开 2 700 个状态。

表中 P 为预处理时间，E 为展开状态数，B 为箱子数。

易错点：

- 箱子可能已经都在目标上：输出空行（测试 03）；
- 玩家可能从目标上出发（`+`），行可能以空格开头（测试 04）；
- 目标上的箱子若忽略其他箱子仍与玩家被墙隔开，就永远不会动，
  会被排除在搜索之外（测试 05）；
- 按区域搜索得到的方案可能超过 10 000 步：在一个生成的关卡上它长达
  44 895 步，而不加限制地精确搜索更短的方案需要超过 170 MB；
- 限制给贪心搜索留下的余地很小：在评测上最多 3.8 秒和 57 MB。

方案在这里的测试和 2 291 个生成的关卡上都通过了检查器，贪心解法每个不超过 2.4 秒和 63 MB；
`1589_astar.cpp` 还在另外 12 000 个关卡上检查过，其中许多是专门演化出来破坏区域搜索的，
每个都不超过 0.71 秒和 20 MB。

## 各语言说明

- Go、Java 和 Rust 逐步照搬 C++；它们的方案与 C++ 逐字节相同。
- 贪心的 Java 用简单的循环给箱子子集编号，并把所有缓冲区放在基本类型数组里：最初的版本在评测第 88 个测试上超时。
- Python 在 PyPy 下运行 astar 这串搜索，为了速度做了几处改动：只保留第一次试探（其余五次在难关卡上最多花 0.5 秒，主要用于 JIT 编译），第二串搜索不做试探，第一阶段限制为 4.5 秒和 300 000 个状态，并让 JIT 少编译（`trace_limit=3000`，不展开循环）：在难关卡上几乎一半时间花在编译上。子状态的匹配从父状态的最优势出发只做一次增广，条带表随每次拉动更新子集序号，带穿越惩罚的距离使用为每组冻结箱子预先算好的拉动。贪心搜索在 C++ 中就要 3.8 秒，Python 无法做到，而此前的 Python 搜索在评测第 55 到 67 个测试上超时。
