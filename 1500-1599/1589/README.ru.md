# 1589. Сокобан

[Timus 1589](https://acm.timus.ru/problem.aspx?space=1&num=1589) · сложность 14456 · astar, greedy

Авторы оригинальной задачи — Станислав Васильев и Сергей Пупырев; ACM ICPC 2007–2008, NEERC, Восточный подрегион, Екатеринбург, 27 октября 2007 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Уровень сокобана не больше 8 × 8 клеток: стены `#`, цели `.`, ящики
`$` (`*` на цели) и игрок `@` (`+` на цели). Игрок ходит по свободным
клеткам и может толкать по одному ящику, шагая в него, но не тянуть.
Выведите план, после которого все ящики стоят на целях: ходы `u`, `d`,
`l`, `r`, заглавные, если ход толкает ящик, не больше 10 000 ходов.
Решение всегда существует, принимается любой верный план.

Ограничение времени: 5 секунд. Ограничение памяти: 64 МБ.

## Входные данные

Уровень по строкам; строки могут быть разной длины и иметь пробелы за
стенами.

## Выходные данные

Одна строка с планом.

## Примеры

### Пример 1

Ввод:

```
########
#@  $ .#
########
```

Вывод:

```
rrRR
```

### Пример 2

Ввод:

```
######
##   .#
#@  ###
#   * #
#   $ #
#     #
#######
```

Вывод:

```
dddrrrruLdlUUUluRR
```

## Решение

Поиск идёт по толчкам, а не по шагам. Состояние — множество ящиков и
область, куда может дойти игрок, обозначенная своей наименьшей клеткой;
всё помещается в один 64-битный ключ, а область находится наращиванием
битовой маски. Здесь два решения: жадное — один поиск по наилучшему с
проверками тупиков (C++, Go, Java, Rust), и astar — цепочка поисков с
таблицами тупиков по областям, гораздо быстрее (все пять языков).

Жадный поиск берёт состояния по `толчки + 20·h`, где h — наименьшее
суммарное число толчков, за которое одиночные ящики доходят до разных
целей (венгерский алгоритм); большой вес делает поиск почти жадным.
Состояние отбрасывается, если:

- ящик встаёт на мёртвую клетку, откуда одиночный ящик не доходит ни до
  одной цели;
- ящики не на целях остаются замёрзшими: ни один не может сдвинуться ни
  по одной оси, даже если по шагам убирать все подвижные ящики, или ни
  один не может толкнуть игрок, даже если убирать все ящики, которые он
  может толкнуть, и расширять его область;
- у паросочетания нет конечной стоимости;
- какое-то множество из двух, трёх или четырёх ящиков со сдвинутым
  ящиком нельзя решить само по себе: для каждого такого множества
  таблица, построенная поисками вытягиваниями от всех наборов целей того
  же размера, хранит клетки игрока, откуда это возможно.

Загон — область, куда игрок не может войти, с нерешённым ящиком на
границе или целью внутри; если все толчки на его границе направлены
внутрь (и остаются теми же без внешних ящиков), пробуются только эти
толчки. Просмотренные состояния хранятся в множестве ключей с открытой
адресацией, узлы — в плоском массиве; план восстанавливается по ходу,
записанному в каждом узле, а шаги между толчками даёт обход в ширину.

На плотном уровне с форума, 13 ящиков на 36 клетках, из начала достижимо
больше 30 миллионов состояний и 22 миллиона из решённой позиции, но с
обеих сторон лежит лишь около 6 300; жадному поиску там нужно 1,8 с.

Цепочка astar упорядочивает состояния по той же оценке, здесь H, считая
замёрзшие ящики на целях стенами, и отсекает состояния так же, кроме
таблиц подмножеств. Этапы:

1. Дешёвые пробы: прямой поиск и поиск вытягиваниями от целей, по 128
   раскрытий, затем доска в четырёх поворотах по 64 раскрытия.
   Большинство уровней заканчивается здесь.
2. Доска в наименьшем из поворотов и отражений ищется ещё с двумя
   проверками. Таблицы областей: для полосы шириной в три клетки вдоль
   каждой стороны пола поиск вытягиваниями от целей полосы, в котором
   ящики могут уходить из полосы и входить в неё, записывает каждое
   множество ящиков полосы и каждую область игрока, из которых полосу
   ещё можно закончить; состояние, чья полоса не записана, мертво.
   Порядок заполнения: вытягивание ящиков с целей решённой позиции, при
   котором замёрзшие ящики остаются, показывает, какие цели придётся
   заполнять последними; состояние, не совпадающее ни с одним из таких
   остатков, мертво. Приоритет — `H + 30·M - глубина`, где M — число
   ящиков, недостающих до ближайшего остатка, так что поиск идёт вглубь
   вдоль порядка заполнения. Он останавливается после 600 000 состояний
   или 1 с.
3. Если это не удалось или план длиннее 10 000 ходов, его память
   освобождается и с нуля начинается вторая цепочка: те же пробы, затем
   поиски с таблицами всех подмножеств ящиков из трёх, а потом из пяти
   рядом со сдвинутым ящиком (построенными поисками вытягиваниями только
   с этими ящиками, замёрзшие ящики — стены), и наконец A* по точным
   клеткам игрока и стоимостям ходьбы, который держит каждый план в
   пределах 10 000 ходов.

Каждый план проигрывается перед выводом. На плотном уровне проверки
областей и порядка заполнения позволяют цепочке раскрыть 2 700
состояний.

В таблице P — время предобработки, E — раскрытые состояния, B — ящики.

Подводные камни:

- ящики могут уже стоять на целях: выведите пустую строку (тест 03);
- игрок может начинать на цели (`+`), а строки — с пробелов (тест 04);
- ящик на цели, отделённый от игрока стенами без учёта других ящиков,
  никогда не сдвинется и исключается из поиска (тест 05);
- план поиска по областям может превысить 10 000 ходов: на одном из
  сгенерированных уровней он вышел длиной 44 895, а точный поиск более
  короткого без ограничений потребовал больше 170 МБ;
- лимиты оставляют жадному поиску мало запаса: до 3,8 с и 57 МБ на
  сервере жюри.

Планы проходят программу проверки на здешних тестах и на 2 291
сгенерированном уровне, жадные — не дольше 2,4 с и не больше 63 МБ на
каждом; планы `1589_astar.cpp` — ещё на 12 000 уровнях, многие из
которых выведены так, чтобы ломать поиск по областям, не дольше 0,71 с и
не больше 20 МБ на каждом.

## Особенности языков

- Go, Java и Rust повторяют C++ шаг за шагом; их планы побайтно
  совпадают с планами C++.
- Жадная Java нумерует подмножества ящиков простыми циклами и держит все
  буферы в массивах примитивов: первая версия превышала лимит на тесте
  88 жюри.
- Python выполняет цепочку astar под PyPy с несколькими изменениями ради
  скорости: только первая проба (остальные пять на трудных уровнях
  стоили до 0,5 с, в основном на компиляцию JIT), без проб во второй
  цепочке, первый этап ограничен 4,5 с и 300 000 состояний, а JIT
  настроен компилировать меньше (`trace_limit=3000`, без развёртки
  циклов): на трудных уровнях почти половина времени уходила на
  компиляцию. Паросочетание потомка продолжается от оптимальных
  потенциалов родителя одним дополнением, таблицы полос обновляют номер
  подмножества вместе с каждым вытягиванием, а расстояния со штрафом за
  пересечение используют заранее посчитанные вытягивания для каждого
  набора замёрзших ящиков. Жадный поиск, которому даже на C++ нужно
  3,8 с, для Python недостижим, а прежние поиски на Python превышали
  лимит на тестах жюри с 55 по 67.
