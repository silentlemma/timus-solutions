# 1589. Сокобан

[Timus 1589](https://acm.timus.ru/problem.aspx?space=1&num=1589) · сложность 28561 · bidirectional

Авторы оригинальной задачи — Станислав Васильев и Сергей Пупырев; ACM ICPC 2007–2008, NEERC, Восточный подрегион, Екатеринбург, 27 октября 2007 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

Уровень сокобана не больше 8 × 8 клеток: стены `#`, цели `.`, ящики
`$` (`*` на цели) и игрок `@` (`+` на цели). Игрок ходит по свободным
клеткам и может толкать по одному ящику, шагая в него, но не тянуть.
Выведите план, после которого все ящики стоят на целях: ходы `u`, `d`,
`l`, `r`, заглавные, если ход толкает ящик, не больше 10 000 ходов.
Решение всегда существует, принимается любой верный план.

Ограничение времени: 5 секунд. Ограничение памяти: 64 МБ.

## Входные данные

Уровень по строкам; строки могут быть разной длины и иметь пробелы за
стенами.

## Выходные данные

Одна строка с планом.

## Примеры

### Пример 1

Ввод:

```
########
#@  $ .#
########
```

Вывод:

```
rrRR
```

### Пример 2

Ввод:

```
######
##   .#
#@  ###
#   * #
#   $ #
#     #
#######
```

Вывод:

```
dddrrrruLdlUUUluRR
```

## Решение

Поиск идёт по толчкам, а не по шагам. Состояние — множество ящиков и
область, куда может дойти игрок, обозначенная своей наименьшей клеткой;
всё помещается в один 64-битный ключ, а область находится наращиванием
битовой маски.

Два поиска по наилучшему встречаются посередине: толчки от начала и
вытягивания от решённой позиции (ящики на целях, игрок в любой свободной
области). У них общая таблица с открытой адресацией на 2²² ключей, и
состояние, найденное обоими, сшивает две половины плана. Каждый поиск
берёт состояния по `g + 3h`, где h — сумма расстояний в толчках от
каждого ящика до ближайшей цели (или стартовой клетки); паросочетание
ящиков с клетками, куда они ещё могут попасть, находит ящики, которые
нельзя расставить все. Открытые списки — корзины, связанные через
таблицу, так что память фиксирована.

Основная работа — отсечение мёртвых позиций:

- мёртвые клетки, откуда одинокий ящик никогда не дойдёт до цели;
- замёрзшие ящики: ящик не на цели, зажатый по обеим осям стенами,
  мёртвыми клетками или другими замёрзшими ящиками;
- загоны: если игрок не может попасть в область, а все толчки ящиков
  вокруг неё направлены внутрь, один из этих толчков нужен, и
  пробуются только они (а если область не решена и ни один толчок
  сейчас невозможен, состояние мёртвое);
- малые подмножества: для каждого набора из двух–четырёх ящиков
  таблица, построенная поиском только с этими ящиками, говорит, можно ли
  их одних ещё решить (для обратного поиска — достичь из начала). Пары
  и тройки проверяются со всеми ящиками, четвёрки — только рядом со
  сдвинутым.

План восстанавливается по ходу, записанному при каждом ключе, а шаги
между толчками даёт обход в ширину. `O(S · B)` для S посещённых
состояний (не больше примерно 3,7 миллиона) и B ящиков.

Подводные камни:

- ящики могут уже стоять на целях: выведите пустую строку (тест 03);
- игрок может начинать на цели (`+`), а строки — с пробелов (тест 04);
- ящик на цели, до которого игрок не добирается, никогда не сдвинется и
  считается стеной (тест 05).

Планы проверены на здешних тестах и примерно на 1 500 сгенерированных
уровнях, и решения решают каждый случайный уровень, который решает
независимая принятая реализация.

## Особенности языков

- Go обращается к таблице один раз на новое состояние и считает номера
  малых подмножеств прямо по номерам клеток ящиков: первая версия,
  примерно в 1,4 раза медленнее C++, сдавалась через 4,6 с на тесте 92
  жюри, который C++ решает за 2,2 с. Ищет Go до 4,85 с.

- Java держит таблицу на 2²¹ ключей, чтобы JVM уложилась в 64 МБ, и
  ускорена так же, как Go. Она отмечает всю область игрока сразу, как
  только находит её, строит таблицы подмножеств битовыми операциями и
  хранит маски прямо в ключах; это сократило тест 92 жюри с более чем
  5 с до 4,34 с.

- Python хранит состояния в компактных массивах и запускается под PyPy;
  CPython в разы медленнее. На наших тестах он тратит около 0,5 с, но
  превышает лимит 5 с на тесте 62 жюри, который гораздо тяжелее: C++
  тратит 2,2 с на тесте 92. Пробовались три разных поиска на Python:
  этот двунаправленный, он же с перезапусками лучшего первого поиска и
  назначением ящиков на цели минимальной стоимости (тест 55) и жадный
  поиск по такому назначению с мёртвыми клетками, замороженными ящиками,
  загонами и таблицами пар и троек ящиков (тест 56). На одинаковом числе
  состояний Python под PyPy примерно в 35 раз медленнее C++, так что для
  прохождения нужен поиск, посещающий гораздо меньше состояний. Решение
  оставлено с пометкой TLE: все наши тесты оно проходит, но не
  претендует на то, что уложится во время на каждом тесте жюри.
