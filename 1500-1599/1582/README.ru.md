# 1582. Букмекеры

[Timus 1582](https://acm.timus.ru/problem.aspx?space=1&num=1582) · сложность 123 · math

Автор оригинальной задачи — Сергей Пупырев, подготовка — Владимир Яковлев; ACM ICPC 2007–2008, NEERC, Восточный подрегион, Екатеринбург, 27 октября 2007 года.

[English](README.md) · **Русский** · [中文](README.zh.md) · [Español](README.es.md)

## Задача

У матча три исхода с лучшими коэффициентами k₁, k₂ и k₃ (0.01 … 100):
ставка x на верный исход приносит k·x, неверная — ничего. Нужно
распределить ставки на общую сумму 1000 фунтов по трём исходам так,
чтобы в худшем случае получить как можно больше, и вывести эту сумму,
округлённую до целого.

Ограничение времени: 1 секунда. Ограничение памяти: 64 МБ.

## Входные данные

k₁, k₂ и k₃.

## Выходные данные

Гарантированная выплата, округлённая.

## Проверка

Тесты репозитория сравнивают полный текст вывода, игнорируя только конечные пробельные символы. Значимые пробелы, переводы строк, регистр и пунктуация сохраняются.

## Примеры

### Пример 1

Ввод:

```
3.5 3.5 3.5
```

Вывод:

```
1167
```

### Пример 2

Ввод:

```
1.25 10.0 5.75
```

Вывод:

```
931
```

## Решение

Поставим xᵢ на исход i, x₁ + x₂ + x₃ = 1000; исход i приносит kᵢ·xᵢ.
Чтобы гарантировать выплату P, каждый исход должен приносить не меньше
P, то есть xᵢ ≥ P / kᵢ, и сложение трёх неравенств даёт
1000 ≥ P·(1/k₁ + 1/k₂ + 1/k₃). Ставки xᵢ = P / kᵢ достигают этой
границы, поэтому наибольшая гарантированная выплата равна

P = 1000 / (1/k₁ + 1/k₂ + 1/k₃).

Читаем каждую десятичную дробь точно как a / 10ˢ. Начиная с N = 1 и
D = 0, для каждого коэффициента обновляем D = D·a + N·10ˢ, затем
N = N·a. Теперь P = 1000·N / D. Используем длинные целые числа и
двоичным поиском находим наибольшее целое m, для которого
2·1000·N ≥ (2m − 1)·D: точные половины округляются вверх без ошибок
вещественной арифметики. Ответ не превосходит ⌊1000·100 / 3⌋, поэтому
число шагов поиска постоянно. Для L десятичных цифр во входе (после
раскрытия экспоненты, если она есть) время — `O(L^2)`, память — `O(L)`.

Подводные камни:

- при всех коэффициентах больше 3 гарантированная выплата больше ставки,
  как в первом примере;
- точная половина округляется вверх: коэффициенты 2, 10 и 25 дают
  1562.5 и ответ 1563, а `printf("%.0f")` округлил бы к чётному и вывел
  1562 (тест 08);
- двоичная арифметика может превратить точную половину в чуть меньшее
  число: коэффициенты 0.02, 0.02 и 0.03 дают ровно 7.5 и ответ 8
  (тест 10). Число знаков после запятой не ограничено, поэтому нужна
  точная арифметика, а не добавление эпсилон.

## Оптимизированные решения

`1582_math_optimized.py`. Точная рациональная сумма выплат сохраняется, но округляется напрямую как floor((2*1000*numerator+denominator)/(2*denominator)) вместо двоичного поиска выплаты. Десятичная и научная записи разбираются из байтов, нулевая набивка убирается до степеней, целые коэффициенты строятся группами по девять цифр. Группировка обходит ограничение преобразования коэффициента без потери точности и округления половины вверх. Указанный Accepted получен на PyPy 3.10. Показатель степени всё ещё разбирается через int(), поэтому чрезмерная нулевая набивка показателя может вызвать ограничение преобразования на CPython; неограниченная поддержка такого ввода на CPython не заявляется. I — размер входа, D — размер нормализованных целых операндов; память O(I+D), стоимость длинной арифметики зависит от D. Положительные коэффициенты и три исхода прежние; до выхода вывод сбрасывается.

По сравнению с `1582_math.py`: время 0.078 s → 0.109 s; память 532 KB → 292 KB.

Оптимизированное решение на Java читает три коэффициента через
`BufferedReader` и `StringTokenizer` вместо `Scanner` с его
регулярными выражениями и данными локали. Арифметика остаётся точной,
коэффициенты по-прежнему попадают в `BigDecimal`, а сравнения идут в
`BigInteger`, так что дешевле становится только чтение ввода:
{1582_math_optimized.java}.

### Измеренный выигрыш

Каждая оптимизированная версия имеет Accepted и сокращает время или
память минимум на 30% относительно базовой версии на том же языке.
Базовые исходники сохранены. Отрицательное сокращение означает рост
расхода. Звёздочка относится только к рейтинговой цели.

- `1582_math_optimized.java`: сокращение времени +14.68%; сокращение
  памяти +57.08%; база: `1582_math.java`.

`1582_math_optimized.cpp`. Сохраняются точная рациональная арифметика и округление половин вверх, без epsilon с плавающей точкой. Неотрицательные целые хранятся в разрядах u32 по основанию 10^9; ведущие и конечные десятичные нули и научный масштаб нормализуются до построения массивов разрядов. Для P=1000N/D накапливаются N,D, затем ограниченный округлённый ответ ищется по 2000N >= (2m-1)D с умножениями на малый коэффициент. Точные половины округляются вверх. Если B — длина исходного ввода, Q — нормализованная десятичная точность коэффициентов и их произведений, школьная арифметика требует O(B+Q²) времени и O(B+Q) памяти. Сырой буфер цифр всё ещё занимает O(B); заполняющие нули не разворачиваются в большие массивы разрядов.

По сравнению с `1582_math.cpp`: время 0.031 s → 0.015 s; память 388 KB → 156 KB.

`1582_math_optimized.rs`. Сохраняются точная рациональная арифметика и округление половин вверх, без epsilon с плавающей точкой. ## Особенности языков

Новые исходники сравниваются по срезу от 18 ноября 2026 года с другими авторами на текущих компиляторах судьи. Порогов по ID посылки или дате нет. Ничьи делят место, времена меньше 0.015 с при сравнении считаются 0.015 с. Приведённые ниже места относятся к новым версиям; прежние исходники сохраняют собственные исторические метрики Accepted.

`1582_math_optimized.cpp`: место по времени 1/103, по памяти 7/103 в этой сопоставимой выборке.

`1582_math_optimized.py`: место по времени 23/34, по памяти 1/34 в этой сопоставимой выборке.

`1582_math_optimized.rs`: сопоставимых чужих результатов недостаточно для рейтингового вывода; допуск основан на измеренном улучшении относительно простой версии.

Звёздочка означает недостигнутую рейтинговую цель: для C++ нужны первые десять мест либо топ 15% одновременно по обеим метрикам; для остальных семейств — первое место по обеим. Отдельный критерий допуска может выполняться по рейтингу или улучшению, в том числе при снижении времени либо памяти минимум на 30%.
